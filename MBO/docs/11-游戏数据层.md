## 0. 结论摘要（先看这张表）

| 问题 | 实测结论 |
|---|---|
| 权威数据能不能从 v160.7 直接读出来 | **能，而且是最好的一条路**。`out/_server160.jar` 起官方服务端（JRE 21）+ Rhino JS 反射遍历 `Vars.content`，**84.8 s** 全量 dump **447 方块 / 22 物品 / 11 液体**，全程不读源码、不猜字段名、不需要 git 仓库对应版本 |
| `data/game/blocks.json` 能不能当配方源 | **不能**。`craftTime` **447/447 全是 -1**（导出脚本 `out/_dump_game.py` 硬编码 `-1.0`，不是游戏事实）；它的 `consumers` 有 115 条带 IO，但其中主体是**耗电项**（107 个方块真耗电），真「配方输入」只有 29 个方块有 |
| 一个方块「完整配方」覆盖多少 | 有 `craftTime` 的方块 **33 个**；同时有输入+产出的 **27 个**（= 生产求解要建模的全部配方方块）；另有 2 个走 `results` 的随机副产物方块（separator / disassembler） |
| 配方的时间单位 | `craftTime` = **帧**（60 fps），一次/s = `60 / craftTime`。例：silicon-smelter `craftTime=40` → **1.5 次/s**；graphite-press `90` → 0.667 次/s |
| 耗电/发电的单位 | `ConsumePower.usage` 与 `PowerGenerator.powerProduction` 都是**每 tick**，**×60 = 游戏 UI 显示的 /s**。例：blast-drill `3/tick = 180/s`；combustion-generator `1/tick = 60/s` |
| 原版有没有多物品产出配方 | **没有**。33 个配方里 `outputItems` 长度最大 **1**；副产物只有两种形态：`results`（separator/disassembler，**按 amount 权重随机出一条**）、多**液体**产出（electrolyzer 一次出 2 种液体） |
| 物流参数齐不齐 | 齐到可算：传送带 **5 / 10 / 10 items/s**（conveyor / titanium / armored），duct 系列 **4 items/s**；10 个钻头全部有 `drillTime`，8 个有 `tier`；电力节点 `laserRange/maxNodes` = 6/10、15/15、40/2；泵 `pumpAmount` 0.1167 / 0.2 / 0.22 / 0.3333 / 0.11 / 0.25 |
| 与 `data/game/blocks.json` 一致率 | 名字 **447/447 = 100%**、尺寸 **100%**、类别 **100%**、建造成本 `requirements` **100%**、`hasPower` **425/447 = 95.1%**；`craftTime` 旧表 **0%**（全 -1） |
| 与 `docs/游戏速查/方块配方.md` 一致率 | 只收录 **115/447** 方块（332 个没有）；尺寸 **115/115 = 100%**；耗电数字 **107/107 等于 per-tick 原值**（该表把「每 tick」写成 `/s`，**系统性偏小 60 倍**）；输入 **14/45 = 31.1%**；写出来的产出 **19/19 = 100%**，但 96 行写「—」的里有 **10 行游戏确有产出**（只记物品、漏 `results` 和液体产出） |
| 结论：用哪份数据 | **`MBO/spikes/data/gamedata.json` 为唯一真相源**；`data/game/*.json` 降级为「名字/尺寸/建造成本」对照表；`方块配方.md` **禁止用于数值计算**（耗电单位错、覆盖 1/4、输入列混建造成本） |
| 还差什么 | 3 个 StackConveyor 的 items/s（要按公式推）、钻头「逐矿种 × 液体加成」的成品速率表、sorter/unloader/mass-driver 的吞吐语义、热量（heat）与 neoplasia 反应堆产热、模组 content id 重映射 |

## 2. v160.7 权威数据获取方案

### 2.1 首选方案（已走通）：起真 jar + Rhino 反射

- **为什么以 jar 为权威**：jar 里就是玩家实际跑的那套 `Blocks.java` 编译产物；`Vars.content` 是游戏自己初始化出来的实例，`craftTime/usage/drillTime` 等字段是**运行时真值**（含 `init()` 之后的补全，例如 `outputItem → outputItems`）。
- **为什么不用源码数值**：本仓库 `Mindustry-Source/` 是 **v159.3**（`git describe --tags` = v159.3，HEAD = 58118440b "Fixed music fade issue"），与 v160.7 有实打实的数值差。例：`conveyor` 在 v159.3 源码是 `speed=0.046f, displayedSpeed=6.5f`（`Blocks.java:2068`），v160.7 jar 实测 **0.035 / 5**。**从源码抄数字会错**，源码只能用来解释字段语义。
- **版本自证**：dump 出的 `meta` 直接读 `Version.build / modifier / buildDate / type` = `160 / release / "October 8, 2026 00:21 AM" / release-160`，写进 `gamedata.json.meta`，可机器校验。
- **成本**：单次 **84.8 s**（JVM 冷启动 + Vars 初始化约 4 s，其余为 9 批 × 50 方块的逐字段反射）。无外网依赖、无 Gradle、不需要反编译。

### 2.2 备选方案（未走通、作为兜底）：解析 `Blocks.java` 源码

- 做法：正则/AST 读 `Mindustry-Source/core/src/mindustry/content/Blocks.java` + `Items.java` + `Liquids.java`，映射 `new GenericCrafter("silicon-smelter"){{ ... }}` 匿名初始化块里的字段赋值。
- **阻碍（实测判断，未投入完整实现）**：
  1. 源码版本是 v159.3，**必须先把 jar 的 447 个名字与源码对齐**，再逐条核对数值差（conveyor 已经不一致）；
  2. 配方输入是链式调用 `consumes.item(Items.coal, 1)` / `consumeLiquid(...)` / `consumePower(...)`，产出是 `outputItems = { ... }`、`results = {...}`，`craftTime` 在匿名块里，**要写一个 Java 语法子树解析器**才能稳；
  3. `init()` 里的派生（`outputItem → outputItems`）、`Item.hardness` 交叉引用都藏在父类，静态解析拿不到运行时最终值。
- 结论：**能用但精度 C**，只在「jar 与 JRE 都缺失」时启用；若要启用，先做 §6 的三方比对来量化误差。

### 2.3 版本对齐策略

1. **数据以 jar 为准**，`gamedata.json.meta` 记录 `gameVersion/versionBuild/versionModifier/buildDate/jarBytes`（后续应加 jar 的 SHA-256）。
2. **源码只作语义字典**：字段含义、公式（`60/craftTime`、`drillTime = (base + 50×hardness)/multiplier`、`usage×60`）参考 v159.3 行号，**数值一律不抄**。
3. **升级流程固定**：换 jar → 重跑 `extract_game_data.py` → 重跑 `compare_data.py` → 若 `onlyGamedata`/`onlyLegacy` 非空或一致率下跌，才人工介入。**不手工改 gamedata.json**。
4. 与蓝图层的衔接见 `10-蓝图层与语料盘点.md`：蓝图里的 Content id 是隐式版本 id，快照必须带 `contentMap`（见 §7.3）。

### 3.3 核心手法：**零字段清单的公有字段反射**

不写「我要 craftTime、我要 drillTime」这种清单（v159↔v160 字段增删会直接崩），而是对每个 `Content` 实例**反射所有公有字段**：

```js
function fields(o, skip){                       /* 沿 getClass() 向上，类名以 mindustry 开头才继续 */
  var out=[], c=o.getClass(), guard=0;
  while(c!=null && guard++<12){
    if((''+c.getName()).indexOf('mindustry')!=0) break;
    var fs=c.getDeclaredFields();               /* 跳过 static / 非 public */
    for(...){ if(static||!public) continue;
      try{ f.setAccessible(true); v=f.get(o); }catch(e){ continue; }
      var s=fmt(v, f.getType().getName());      /* 只序列化可判定类型 */
      if(s!==null) out.push(f.getName()+'='+s); }
    c=c.getSuperclass();
  }
  return out.join('\t');
}
```

`fmt()` 只放行：`boolean → 1/0`、数值、`String`、`Content` 子类 → `''+v.name`、`ItemStack[]/LiquidStack[] → [i:name:amount;l:name:amount]`、enum → `name()`、`Class → getName()`；其余（texture/drawer/lambda）返回 `null` 丢弃。这样 **v159.3 与 v160.7 的字段差异不会让 dump 失败**，新增字段自动进 `raw`。

## 5. 关键语义（下游求解必须按这些公式算）

### 5.1 时间：`craftTime` 是帧

```
每秒循环数 cps = 60 / craftTime
某产物速率 = 每次产出量 × cps          (items/s)
某原料消耗 = 每次消耗量 × cps          (items/s 或 liquid/s)
```
例：silicon-smelter `craftTime=40, coal×1, sand×2 → silicon×1`：cps=1.5 → 产 silicon **1.5/s**，耗 coal 1.5/s、sand 3.0/s、电 30/s（0.5/tick×60）。
**注意**：反向推「要 3 silicon/s → 2 台硅炉」必须用 `ceil(3 / 1.5)`，即 **2 台**（不能浮点）。

### 5.2 电力：`usage`/`powerProduction` 是每 tick，`hasPower` 不是耗电

- `ConsumePower.usage`（`world/consumers/ConsumePower.java:10`）= **每 tick 可处理功率**；游戏 UI 的 `/s` = `usage × 60`（`PowerGenerator.java:67` 的 `powerProduction*60f` 就是同一约定）。
- `Block.hasPower`（`Block.java:49`）只表示「**能否接入电网**」：`PowerNode` 的 `hasPower=true` 但 `usage=null`（不耗电）；`Block.consumesPower`（`Block.java:53`）**默认 true**，直接拿它会得到 429 个假耗电方块 —— 必须用 `usage != null` 判定。
- 净电力：`Σ(powerProduction×60 × 建筑数) − Σ(usage×60 × 建筑数)`；电池只是 `capacity`（`ConsumePower.capacity`），不是源/荷。
- 有 20 个方块 `outputsPower=true`（发电机 + 节点 + 电池 + 太阳能），**发电机 15 个**才是真正注入功率的源。

### 5.3 钻头：速率依赖矿种硬度

```
getDrillTime(item) = (drillTime + hardnessDrillMultiplier × item.hardness) / drillMultipliers(item)
基础速率 items/s   = 60 / getDrillTime × size²          （Drill.java:181 stats 用 60/drillTime×size²）
爆速上限：item.hardness ≤ tier 才能采（Drill.java:231 canMine）
液体加成：liquidBoostIntensity（多数 1.6）在使用液体时对 drillTime 做除算
```

## 7. 给 L0 快照的 schema 建议

### 7.1 表结构（`GameData`）

```python
@dataclass(frozen=True)
class Stack:            item: str; amount: float          # items 用 amount，liquids 用 amount(L)
@dataclass(frozen=True)
class Recipe:
    craft_time_frames: int                # 帧（**整数，L0 唯一存法**；与 docs/01 §2.4 一致）
    @property
    def cycles_per_second(self) -> float: # 批/秒 = 60/craft_time_frames，不落盘
        return 60.0 / self.craft_time_frames
    inputs:    tuple[Stack, ...]          # 每次循环消耗（含液体）
    outputs:   tuple[Stack, ...]          # 每次循环产出（含液体）
    random_results: tuple[Stack, ...]     # results：每次随机出一条，权重=amount
    power_consumption: float              # /s (= usage×60)
@dataclass(frozen=True)
class DrillSpec:  tier: int | None; drill_time: float; hardness_multiplier: float = 50.0
                  liquid_boost: float = 1.6; size: int
@dataclass(frozen=True)
class ConveyorSpec: items_per_second: float | None; speed_tiles_per_tick: float; capacity: int
@dataclass(frozen=True)
class PowerNodeSpec: laser_range: float; max_nodes: int
@dataclass(frozen=True)
class BlockSpec:  name: str; content_id: int; size: int; category: str; family: str
                  requirements: tuple[Stack, ...]      # 建造成本
                  recipe: Recipe | None
                  power_usage_per_second: float | None # 耗电（None=不耗）
                  power_production_per_second: float | None
                  drill: DrillSpec | None; conveyor: ConveyorSpec | None
                  node: PowerNodeSpec | None; pump_amount_per_second: float | None
@dataclass(frozen=True)
class ItemSpec:   name: str; hardness: int; cost: float; explosiveness: float
                  flammability: float; radioactivity: float; charge: float
@dataclass(frozen=True)
class LiquidSpec: name: str; heat_capacity: float; viscosity: float
                  temperature: float; gas: bool; flammability: float; explosiveness: float
@dataclass(frozen=True)
class GameData:   meta: dict; items: dict[str, ItemSpec]; liquids: dict[str, LiquidSpec]
                  blocks: dict[str, BlockSpec]          # key = name（不要用 id）
                  ore_blocks: dict[str, str]            # floor → item
                  liquid_blocks: dict[str, str]         # floor → liquid
```

### 7.2 必须带的版本与溯源字段（写进 `meta`）

| 键 | 语义 |
|---|---|
| `gameVersion` / `versionBuild` / `versionModifier` / `buildDate` | 自证版本，例 `release-160 / 160 / release / "October 8, 2026 00:21 AM"` |
| `jarPath` / `jarBytes` / `jarSha256` | 溯源（**sha256 待补**，下一步加） |
| `counts` | `items/liquids/blocks`，用于变更检测（≠22/11/447 即需人工看） |
| `dumpSeconds` / `generator` | 可复现性 |
| `coverage` | 本次覆盖率字典（§4 的数字），流水线健康检查用 |

### 7.3 Content id 与模组

- **不要用 `id` 当主键**：`Content.id` 是初始化顺序，加一个模组方块就整体偏移；构建/求解一律用 `name`。`id` 只在**解码蓝图**时用，且必须配合 `contentMap`。
- 快照应按 `contentMap` 结构落：`{"item": {"copper": 0, ...}, "liquid": {...}, "block": {...}}`，这正是 `.msch` 的 tag 格式（见 10 号文档 §6.3）。这样蓝图里的 id 可以**双向重映射**到任意版本/模组环境。
- 模组方块：本次 dump 是**纯原版 jar**（无 mods 目录），447 条即原版全集。支持模组的路径是「同一套反射脚本 + 指定 `-Dmindustry.data.dir` 与 mods」，**同一份代码可复用**，但要求快照分「vanilla」与「vanilla+mods」两套并记录 mod 列表+版本。

### 7.4 求解接口（下游最小面）

```
buildings_needed(product, rate) = ceil(rate / (per_craft_output × 60/craft_time))
raw_materials(buildings)        = Σ buildings × per_craft_input × 60/craft_time
power_balance(factory)          = Σ generators×prod×60×eff − Σ consumers×usage×60
drill_rate(drill, ore)          = 60 / ((drill_time + 50×item.hardness) / multiplier) × size²
```

## 8. 坑清单（按踩到的顺序）

1. **`craftTime` 全 -1 是导出脚本的 bug，不是游戏事实**。真值 33 个方块有；`out/_dump_game.py` 里 Python 硬编码了 `-1.0`。别再拿旧 json 说「游戏没给 craftTime」。
2. **`hasPower` 不是「耗电」**：`Block.consumesPower` 默认 `true`（`Block.java:53`），直接用它统计会得到 429 个假耗电方块。判据是 `consPower != null` / `usage != null`（`Block.java:1483`）。
3. **反射里 `Items.copper.getClass()` 是 `mindustry.content.Items$1`**（匿名子类），按类名 `== "mindustry.type.Item"` 判类型会**把 itemDrop/liquidDrop 全丢掉**。用 `instanceof Content`。
4. **console 单次输出 >~10k 行会被截断**：症状是只 dump 到 272/447 个方块、字段残缺。必须**分批**（本次 50 个/批，共 9 批）+ 每批一个哨兵（`print('SDONE')`）。
5. **`itemCapacity`/`liquidCapacity` 的默认值是 10**（447 里 437/446 个 >0），**不代表能存东西**；容量只在 `hasItems==true` / `hasLiquids==true` 时有意义。
6. **`Conveyor.speed`（tiles/tick）≠ items/s**：items/s 看 `displayedSpeed`；`Duct.speed` 又**直接就是 items/s**（同样是数字 4、5，语义完全不同）。
7. **`StackConveyor`（plastanium/surge conveyor）没有 `displayedSpeed`**，items/s 要用「堆叠数×speed」推，本次标记为缺。
8. **js 里写 `//` 注释会炸**：命令被压成单行发送，`//` 会吞掉后面的全部代码，报 `EvaluatorException: missing } in compound statement (console.js#1)`。只用 `/* */`。
9. **等 `undefined` 可能假超时**：脚本末尾有 `print` 时控制台最后打的是数字。用自定义哨兵字符串。
10. **别信源码数值**：`Mindustry-Source` 是 v159.3，`conveyor` 在源码是 0.046/6.5，jar 是 0.035/5。源码只给公式和行号。
11. **`docs/游戏速查/方块配方.md` 的耗电单位错 60 倍**（per-tick 当 /s），且只有 115 个方块。
12. **`separator/disassembler` 是随机单出，不是多产物**：把它们当「同时产 4 种矿」会让线性规划解出不可能的工厂。
13. **发电机输出是「满效率」值**：thermal 依赖温度、solar 依赖光照、impact-reactor 自身还耗电 1500/s，直接当常数会低估需求。
14. **钻头速率依赖矿脉硬度**：同一台 laser-drill 挖 copper 和挖 thorium 是不同速率；且只有 `item.hardness ≤ tier` 才能挖。只填 `drillTime` 不足以算产量。
15. **python 交互式 here-doc 在 pwsh 里不可用**（`python - <<'PY'` 报「缺少文件规范」）：临时脚本用 `Out-File -Encoding utf8` 落盘再跑，或直接 `python -c`。
16. **写回/生成 `gamedata.json` 时务必 `ensure_ascii=False` + UTF-8**，否则中文/特殊名（`枯竭晶簇` 类）会被转义，下游 diff 不可读。
