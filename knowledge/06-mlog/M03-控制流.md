# M03 控制流

## 一句话

mlog 没有 if/while，只有 **jump**（条件跳转）和 **可写的 @counter**；循环 = 往回 jump，分支 = 往前 jump，`end` 只是「jump 到 0」。

## 规则 / 公式

### 1. jump 的 8 个条件（ConditionOp 枚举）

源码：`Mindustry-Source/core/src/mindustry/logic/ConditionOp.java`（`:6-13` 共声明 **8 个值**）。文本导出用**枚举名**作 token（`jump 24 strictEqual unFlag flag`），UI 上显示的是符号（`==` / `not` / `===`），两者不是一回事。 [src: Logic-Docs-v1.1.0.md:1661]

| # | 文本 token | UI 符号 | 语义 | 数值口径 | 源码 |
|---|---|---|---|---|---|
| 1 | equal | == | 相等 | `Math.abs(a-b) < 0.000001` | ConditionOp.java:6 |
| 2 | notEqual | not | 不等 | `Math.abs(a-b) >= 0.000001` | ConditionOp.java:7 |
| 3 | lessThan | < | 小于 | 精确 `<` | ConditionOp.java:8 |
| 4 | lessThanEq | <= | 小于等于 | 精确 `<=` | ConditionOp.java:9 |
| 5 | greaterThan | > | 大于 | 精确 `>` | ConditionOp.java:10 |
| 6 | greaterThanEq | >= | 大于等于 | 精确 `>=` | ConditionOp.java:11 |
| 7 | strictEqual | === | 严格相等（类型位 + 精确值） | **不是恒 false**，见 1b | ConditionOp.java:12 / :32-33 |
| 8 | always | always | 无条件成立 | 两个操作数完全不读 | ConditionOp.java:13 |

计数口径：**枚举 8 个**；若只数「比较运算符」则是 **7 个**（8 个减去 `always`）——资料里说的「7 个条件 op」就是这个口径。`jump <dest> always` 后面可以完全不写操作数（LStatements.java:1033/1041 只对非 always 渲染两个输入框）。

### 1b. equal 的浮点容差 与 strictEqual 的真相

jump 实际怎么比由 `ConditionOp.test(LVar, LVar)`（ConditionOp.java:31-40）决定，**不是**由枚举构造时传的 lambda 单独决定：

```java
if(this == ConditionOp.strictEqual){                                  // :32
    return va.isobj == vb.isobj && ((va.isobj && Structs.eq(va.objval, vb.objval))
                                  || (!va.isobj && va.numval == vb.numval));  // :33
}
if(objFunction != null && va.isobj && vb.isobj) return objFunction.get(va.obj(), vb.obj()); // :35-37
return function.get(va.num(), vb.num());                              // :39
```

- `equal` / `notEqual`：都不满足「两端都是对象」时走 :39 的数值口径，容差 **1e-6** [src: ConditionOp.java:6-7]⇒ `0.1+0.2` 与 `0.3` **判等成立**（差 5.55e-17）。两端都是对象时走 :35-37 的 `Structs.eq`（引用相等）。
- `strictEqual`：命中 :32-33 的特判 ⇒ 语义 = **类型位一致**（都对象或都数字）+ 数字**精确 `==`**（无 1e-6 容差）+ 对象**引用相等**。
- 对象 vs 数字的比较会**退化**：只有两方 isobj 都为 true 才走对象函数，否则 `num()` 把「非 null 对象」当 1、「null 对象」当 0（LVar.java:56-58）⇒ `jump ... equal @unit 0` 在未绑定时成立，判「有没有单位」必须用 `strictEqual @unit null`。

```mlog
op add x 0.1 0.2
jump eq equal x 0.3        # 成立（1e-6 容差）
jump ok strictEqual x 0.3  # 不成立（精确 ==，x = 0.30000000000000004）
ok:
```

**反例（重要）**：「`strictEqual`（`===`）恒为 false」是流传极广的说法 —— 依据是 ConditionOp.java:12 的 lambda 写成 `(a, b) -> false`。但该 lambda 只是 `function` 字段，`test()` 在 :32 就把它短路了，而 `jump`（LExecutor.java:1200 `op.test(value, compare)`）和 `op select`（LExecutor.java:893）都走 `test()` ⇒ **恒 false 的说法不成立**。只有绕过 test() 直接调 `ConditionOp.function` 时才会恒 false。 [实测: docs/断言表.md]

### 1c. 条件写错的三种典型

| 写法 | 实际后果 | 正确写法 |
|---|---|---|
| `jump 5 not a b` | `not` 是 **UI 符号**，文本解析按枚举名 ⇒ 认不出，条件可能落到默认 `notEqual` 或解析失败 | `jump 5 notEqual a b` |
| `jump 5 == a b` | 同上，`==` 只在 UI 显示 | `jump 5 equal a b` |
| `jump 5 always 0 0` | 合法但不必要；操作数被忽略 | `jump 5 always` |

浮点比较永远优先用 `lessThan`/`greaterThan` 加容差，不要用 `equal` 判「算出来的数相等」；要判「同一个对象」用 `strictEqual`。

### 2. 三种「停」的区别

| 指令 | 对 @counter | 对处理器 | 后果 |
|---|---|---|---|
| `end` | 归 0（等价 `jump 0 always`） | 继续跑 | 下一 tick 从第 1 条重来（L1-01/L1-03 已实测） |
| `stop` | 先 counter-- 再 yield，置 `stop=true` | **停住** | 程序不再推进，需外部重启处理器（LExecutor.java:1236-1245） |
| `wait` n | 保持不动（counter--，yield） | 暂停 n tick | 时间到后从同一条继续（LExecutor.java:1206-1234） |

### 3. 循环写法

`for` 的等价物（计数器版）：

```mlog
set i 0
loop:
op add i i 1
jump loop lessThan i 10
```

要点：

- **循环体不需要 wait 也能跑**，但会吃满每 tick 预算（M08）；想限速就 `wait 1`（≈1 s，见下节精度）。
- `wait 0` 特殊：立即 yield 且 **不消耗预算**（`break` 在 `accumulator--` 之前），等价「主动让出本 tick 剩余执行」但不用时间。实测语义见 L1-30。
- 计数器建议用 `op add` 而非 `set` 自增，避免浮点累加误差累积。

### 4. 改写 @counter 的后果

| 写入值 | 结果 | 依据 |
|---|---|---|
| 0..N-1 | 正常跳转 | runOnce 前置检查 |
| >= N（程序长度） | **归 0**，不崩 | `counter.numval >= instructions.length → 0`（LExecutor.java:111-121） |
| < 0 | **归 0** | 同上（L1-04 已实测） |
| 小数 | 被强转 int 截断 | `(int)(counter.numval++)` |

`@counter` 跨 tick 保持；`jump`/`end`/`stop` 都是直接写它。

### 5. wait 的精度

- 参数单位是**秒**（不是 tick），内部累加 `curTime += Time.delta/60f`（LExecutor.java:1206-1232）；60 tick/s 下 1 tick = 1/60 s ≈ 16.7 ms，故 `wait 1` ≈ 60 tick ≈ 1 s，`wait 0.05` ≈ 3 tick。 [src: LExecutor.java:1206-1232]
- `wait 0`：值 <= 0 分支，`yield=true; curTime=0`，**不 counter--** ⇒ 下 tick 重试同一条。
- 因此「精确到毫秒的节拍器」做不到；要更细只能用多处理器错相位。断言表 L1-29 已确认粒度 1 tick。 [实测: docs/断言表.md]

## 实测与反例

- ✅【E】`end` 后语句永不执行，`@counter` 归 0（L1-01/L1-02）。
- ✅【E】`jump -1 always` 从 0 重跑，不是空操作（L1-04）。
- ✅【E】`wait 0` 只让出不消耗预算（L1-30）；攒满突发池需 5 tick ≈ 0.0833 s（L1-31）。 [实测: docs/断言表.md]
- 反例（不成立边界）：**「jump 条件对浮点做精确相等」不成立**。`equal` 走 `num()`，而 num 对 NaN 归 0、对 null 归 0 ⇒ 两个「不同来源的 0」判定相等。要区分对象/数字用 `strictEqual`。

## 常见误解

1. 「有 while 语句」——没有，只有 jump。
2. 「end 是停程序」——end 是回到开头；停程序用 stop。
3. 「wait 能精确到帧」——精度 1 tick（≈16.7 ms），且受服务器 tick 率影响。 [src: knowledge/VERSION.md:1]
4. 「越界 jump 会崩」——不会，越界归 0，静默重跑。
