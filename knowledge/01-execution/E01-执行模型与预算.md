# E01 Execution model and budget

## In one sentence

Logic does not "run the program once per tick"; it is **a pool of points**. Each tick charges the pool with `edelta()×ipt` points, one point buys one instruction, and under a stall the pool is clipped to `5×ipt` — which explains "why a stall loses logic" and "why a burst can run faster".

## Rules / formulas

### 1. Main loop (LogicBlock.updateTile)

```java
// LogicBlock.java:564-579
if(accumulator > maxInstructionScale * ipt) accumulator = maxInstructionScale * ipt;
while(accumulator >= 1f){
    executor.runOnce();
    if(executor.yield){ yield = false; break; }
    accumulator--;
}
accumulator += edelta() * ipt;
```

Four counter-intuitive points, all of them from these 8 lines:

| Point | Mechanism | Consequence |
|---|---|---|
| Accumulation happens **after** the loop | The source comment states outright that it cannot move earlier; `accumulator` is an uninitialised field (0) | A new processor executes **0 instructions on its first tick** (it only loads); each later tick spends the previous tick's leftover; WaitI's curTime moves in step |
| The `yield` branch breaks **before** `accumulator--` | The round that yields does not pay | `wait` / `stop` cost no budget |
| The clamp happens **before** the loop | `min(pool, 5×ipt)` | Points earned during a stall are dropped outright, never saved up into a large burst |
| The loop is `while(>=1)`, not `for(i<ipt)` | It spends by point count | Instructions actually executed per tick = points left in the pool |

### 2. runOnce and @counter

```java
// LExecutor.java:111-121
if(counter.numval >= instructions.length || counter.numval < 0) counter.numval = 0;
instructions[(int)(counter.numval++)].run(this);
```

- `@counter` is **read first, incremented second**, so it always points at "the next instruction to execute".
- Out of range or negative ⇒ reset to zero (no crash, no halt).
- A rewritten `@counter` takes effect on the **next instruction**; the current instruction always finishes.

## Measurements and counter-examples

- ✅【E】`@ipt` can only be rewritten by `setrate`; `set @ipt 5` is silently dropped (@ipt is a putConst, LAssembler.java:27); measured: @ipt is unchanged after the set (assertion table, L1 series).
- ✅【E】micro needs 5 tick ≈ 0.0833 s to go from an empty pool to a full 10 points (L1-31). [measured: assertion table (docs/断言表.md)]
- Counter-example (a boundary that does not hold): **"a tick always runs ipt instructions" is false**. With less than 1 point in the pool it runs none; above 5×ipt it still runs only 5×ipt.
- 【U】When a multiplayer server's tick rate is not 60, the real throughput of `edelta()×ipt` needs one dedicated-server measurement (the client's 60 tick/s is a conversion convention, not a global guarantee). [src: knowledge/VERSION.md:1]

## Common misconceptions

1. "ipt=25 means 25 instructions per tick" — true in the long run; a single tick can run fewer because the pool is empty.
2. "wait costs budget" — the round it yields does not pay.
3. "@counter increments before the instruction runs" — it is read first, incremented second.
4. "after a stall logic catches up by running double" — the clamp comes first, so it cannot catch up.
