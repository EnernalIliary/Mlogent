# M05 Drawing and text

## In one sentence

`draw` packs its arguments into the display buffer as **signed 10-bit** values (each slot covers −511..511); `print` only appends characters to a **400-character** text buffer; and both land on the block only through `drawflush` / `printflush`.

## Rules / formulas

### 1. The 16 draw types (the GraphicsType enum)

| Type | Use | Parameters used |
|---|---|---|
| clear | clear the screen (the parameters are r,g,b) | x,y,p1 |
| color | set the color | x,y,p1,p2 |
| col | same as above (virtual type) | none |
| stroke | line width | p1 |
| line | draw a line | x,y,p1,p2 |
| rect | filled rectangle | x,y,p1,p2 |
| lineRect | outlined rectangle | x,y,p1,p2 |
| poly | filled polygon | x,y,p1,p2,p3 |
| linePoly | outlined polygon | x,y,p1,p2,p3 |
| triangle | triangle | x,y,p1,p2,p3 |
| image | texture | x,y,p1,p2,p3 |
| print | draw the text buffer (expanded per character internally) | x,y,alignment=p1 |
| translate | translate | x,y |
| scale | scale | p1 |
| rotate | rotate | p1 |
| reset | reset the transform | none |

The enum holds 16 values; the machine-readable version is `06-mlog/enums.json#enums.GraphicsType` (source LogicDisplay.java:290-312).

### 2. 10-bit packing: every command has only ±511 of resolution

Every field of `DisplayCmdStruct` (LogicDisplay.java:314-322) is marked `@StructField(10)`, packSign on write, unpackSign on read:

```java
static int unpackSign(int value){
    return (value & 0b0111111111) * ((value & (0b1000000000)) != 0 ? -1 : 1);
}
```

⇒ **1 sign bit + 9 magnitude bits**: the legal range is `-511..511`, and anything beyond is truncated/wrapped, because this is not floating point. Screen-local coordinates are usually only tens to hundreds, which is enough; but **drawing world coordinates (tens of thousands) necessarily overflows** — that is the root cause of "draw lands all over the screen".

### 3. The text buffer (print / printchar / format → printflush)

| Instruction | Effect | Cap |
|---|---|---|
| `print <value>` | appends to textBuffer | 400 characters |
| `printchar <codepoint>` | appends one character | 400 |
| `format <string>` | replaces `{0}..{9}` with the numeric placeholders in the buffer | still truncated to 400 after replacement |
| `printflush <message block>` | pushes the buffer to the message block and clears it | the message block itself, 400 |

Key source facts:

- `LExecutor.maxTextBuffer = 400` (LExecutor.java:46).
- Before appending it checks `if(exec.textBuffer.length() >= maxTextBuffer) return;` (:1057, :1100): **once the buffer is full, later prints are simply dropped**, with no error.
- If `format` overflows after substitution, `setLength(maxTextBuffer)` truncates (:1155-1156).
- The message block has its own 400 cap and **rejects the whole string** when it is longer (MessageBlock.java:29/42).
- The buffer is cleared at every consumer, such as `printflush` and `draw print` (:993, :1178, :1907, :1943).
- **`printchar <content>` prints an icon, not a character**: `PrintCharI` appends `(char)cont.emojiChar()` for an `UnlockableContent` (LExecutor.java:1101-1104); only a number takes the codepoint branch, and a non-content object is **silently ignored**. So `printchar copper` draws the copper icon and `printchar @landing-pad` draws the landing pad icon.
- **Icons are only guaranteed on message blocks**: the UI font ships Iconc glyphs (Fonts.java:78-90), while `draw print` on a logic display uses logic.ttf, whose character set is ASCII only (Fonts.java:92-98) ⇒ an information panel can get icons only through `printchar`.
- **`format <value>` fills exactly one placeholder per call**: it scans the buffer for the **lowest-numbered** `{0}..{9}` and replaces it (LExecutor.java:1123-1139); the placeholder must already have been written by `print`; a content-object value goes through `PrintI.toString` (:1143) ⇒ **you get the name, not the icon**.
- So "icon + count" costs 3 instructions at minimum: `printchar it` / `print "  x{0}\n"` / `format cnt`; the text-only version is `print "  {0} x{1}\n"` + `format it` + `format cnt`. ⚠ `format` needs build ≥ 147 (the checker reports a version gate).

### 4. Coordinate systems

| Quantity | Unit | Conversion |
|---|---|---|
| tile coordinates | 1 tile | `tilesize = 8` world units per pixel |
| processor range | tile | range = 8 × tile count (micro 80, logic 176, hyper 336) |
| draw coordinates | the display block's local coordinates (0..display width/height) | read them with `@displayWidth`/`@displayHeight` |
| world instruction coordinates | **tile** | `numfWorld()` converts to world units internally via `World.unconv` (LVar.java:70-72) |

So: passing tile coordinates to `draw` draws off-screen, and passing pixels/world units to a world instruction is scaled up 8×.

### 5. Color

- `draw color r g b a`: the components are 0..1 floats.
- `packcolor result r g b a` / `unpackcolor`: compress a color into a double bit pattern (DrawI unpacks with `Double.doubleToRawLongBits`, LExecutor.java:933-942).
- Once a color enters the display buffer it is subject to the same 10-bit packing ⇒ component precision is about 8-10 bit.

## Measured facts and counter-examples

- Counter-example (a boundary that does not hold): **draw coordinates are not floats, so you cannot draw at an arbitrary position**. Every field ends up as an unpackSign 10-bit signed integer, distorted beyond ±511.
- Counter-example: **an overlong print does not wrap**. Once the buffer is full the later characters are dropped, with no warning.
- Counter-example: **the buffer does not survive printflush**. Flushing clears it with setLength(0); you have to rebuild it.
- 【U】On a headless server DrawI returns immediately, so a logic display shows nothing: this is a mechanism inference for "the display is invisible on the server" and needs one server experiment with a display attached.

## Common misconceptions

1. "draw can draw world coordinates." — it cannot; they distort beyond ±511. Subtract the screen origin from world coordinates first.
2. "print outputs straight to the screen." — print only writes the internal buffer; you need printflush or draw print.
3. "format pads the width." — it only substitutes; it does not zero-pad or align.
4. "The text cap is 1000." — it is 400 (400 for the logic buffer and 400 for the message block).
