## 2. 逐项实测细节

### 2.1 蓝图层：`tools/msch.py` + 833 张语料

**解析（能力已闭环）**
- 全量 833 张 `.msch`：**831 张解析成功（99.76%）**，2 张失败（`unparsed`）。
- 分类（按工厂方块占比 ≥0.75 判工厂型）：**工厂型 574、混合 180、逻辑型 77**。
- 方块的 config 语义分布（全部 tile）：`null 43772 / content 15253 / point 14136 / array 3266 / bytearray 1477 / string 1465 / bool 452 / int 274 / float 4`。
  按方块看：`sorter`→content（选物品）、`bridge-conveyor`/`bridge-conduit`/`phase-conveyor`→point（对端坐标）、`power-node`/`beam-link`→array（连接点列表）、`micro-processor`→bytearray（逻辑代码）、`message`→string、`switch`→bool、`item-source`/`liquid-source`→content。
  **这就是 L0 `Block.configurable` 字段的实测来源**：config 语义完全可由方块类型分派，不需要猜。

**写入（有明确缺口，但可控）**
- "解析→写回→再解析"完全一致：**230/831（27.68%）**。
- 失败原因**只有一条**：`cannot serialize config of type list` —— 601 张蓝图里有 `array` 型 config（电力节点/光束节点的连接点列表），现有写入器不支持序列化数组。
- **⚠️ 原稿此处有一句错误断言，已修正**：原写"Mindustry 放置蓝图时会自己重建电力连接，所以生成蓝图时可以不写 `array` config"。核对源码 `Schematics.java:508-521` 的 `place()` 只做 `tile.setBlock()` + `tile.build.configureAny(st.config)`，**不调用 `Building.placed()`**；autolink 在 `PowerNodeBuild.placed()`（`PowerNode.java:399-410`）且仅在 `links.size==0` 时触发。**结论：该断言未验证，默认按"必须写 array config"实现**（MBO 已有这个能力），并由 `sim-spike` 补 30 分钟真机实验定论（见 `docs/12` §补测）。Validator 增加一条"电力连通块数 == 期望数"。
- **自补写入器（本调研已写通，在 `spikes/bp/scan_corpus.py` 的 `build_schematic_ext`）**：完整解码时保留 TypeIO tag 号（`TaggedList`/`TaggedDouble`），写入时按 tag 还原 —— **831/831（100%）语义往返**，**830/831（99.88%）写回的未压缩 body 与原始文件逐字节相同**。唯一差异是语料里唯一的 version=0 文件（方块字典含未用项，语义等价）。
  → 结论修正：**array config 的写入不是"待研究"，而是"已验证可做、代码已有"**，MBO 只需把它从 spike 搬进 `mbo/blueprint/codec.py` 并补单测。
- **对 MBO 的影响**：既然"自动重建"未验证，生成蓝图时**一律显式写 array config**（我们的 writer 已支持）；"语料往返回归"必须支持数组，否则测试集漏掉 72% 的图。
- 结论：**解析直接复用 `tools/msch.py`（只读 import）；写入在 MBO 侧自建一层**（不把 writer 塞进 `tools/`，避免破坏门禁中的镜像副本一致性）。

**语料规模与形态（决定 MBO 能用它做什么）**
- 总 tile 80099；宽 1–325（中位落 9–16），高 1–174；单张 tile 数中位 **40**，最大 4795。
- 含逻辑块（处理器）的蓝图 355 张（42.7%）—— 说明语料大半是"工厂 + 逻辑控制"混合的成品，纯工厂模块要靠筛。
- 工厂型蓝图的**方块覆盖率中位 95.6%**、每格工厂 tile 中位 0.39 —— 即真实工厂蓝图极其紧凑，说明"人工蓝图的空间利用率"是 B 组要挑战的硬指标。
- 工厂型涉及方块 104 种；产物分布（**工厂型口径，见 §0 口径表**）：`silicon 114、pyratite 110、coal 94、spore-pod 63、graphite 60、plastanium 59、phase-fabric 37、metaglass 36、blast-compound 34、surge-alloy 19、sand 14、oxide 4、carbide 1`（13 种）。全语料口径各多 1–2 张（如 surge 21）。
  → **E2 实验（合金）在语料里有 19 张工厂型样本**（+2 张混合型=21），其中**零逻辑 3 张**可直接作 A 组基线；样本量偏小是 E2 的风险（见 §4）。
- 与 v160.7 的方块名一致性：仅 8 张蓝图（0.96%）含当前版本不存在的方块，缺失名字只有 `alloy-smelter`（38 次）与 `thermal-pump`（1 次）——都是**旧版本改名**（alloy-smelter → surge-smelter）。这说明语料基本与当前版本兼容，只需一张改名映射表。
- **游戏硬上限（已实测源码确认）**：`Schematics.limitSchematicSize = true`，蓝图 `width>128 || height>128` 或 `tiles>128*128` 会被**游戏直接拒收**（`Schematics.java:52,557,598`）。语料里有 2 张违反（如 138×76/4795 tile）——**只能离线分析，不能进游戏验证**。MBO 的 Validator 必须把这条作为第一道硬剪枝。

### 2.2 游戏数据层：从"半张表"到"完整快照"

- 旧 `data/game/blocks.json`：447 方块，但 **`craftTime` 全为 -1**，只有 115 个方块有 `consumers/outputs` —— 不足以做生产计算（这是最大的数据缺口）。
- `out/_dump_game.py` 的思路正确（起 Server + Rhino 遍历 `Vars.content`），但字段太少。
- 新 dump（`spikes/data/gamedata.json`，本机实测生成）已补齐 MBO 需要的绝大部分：
  - **33 个配方方块**（craftTime 全 >0；其中 29 个有 IO、**27 个输入输出完整**），带 `cyclesPerSecond / inputs / outputItems / outputLiquids / outputItemsPerSecond`；
  - **107 个耗电方块**（`powerConsumption` 非空，102 是旧 dump 口径）、**15 个发电方块**（`powerProduction` 非空，含沙盒 `power-source`，真发电机 14）；
  - 物品 22 个（`hardness / cost / flammability / explosiveness / radioactivity / charge`）、液体 11 个（`heatCapacity / viscosity / temperature`）；
  - 电力节点：`laserRange 6 / maxNodes 10`（小节点）、`15/15`（大节点）；水泵 `pumpAmount 0.11`；桥 `bridgeWidth`；反应堆 `transportTime` 等。
- **仍然缺**（详见 11 号文档 §4，已收窄）：
  - `StackConveyor`/`plastanium-conveyor` 的 items/s（没有 `displayedSpeed` 字段，要按堆叠推）；
  - 钻头**逐矿种**的成品速率（`drillTime` 有了，但要按 `(drillTime + 50×item.hardness)/mult` 逐矿算，还要液体加成）；
  - `sorter`/`unloader`/`mass-driver` 的吞吐语义、反应堆产热。
  - 已补齐的：传送带 **12 种（9 种有 items/s）**、钻头 **10 种（8 种有 tier）**、完整配方 **27 个**。
- **单位陷阱（务必写进 L0 schema 注释）**：`power.usage` / `powerProduction` 是**每 tick** 值，字段 `usagePerSecond`/`productionPerSecond` 才是 ×60 后的 UI 值；`craftTime` 是帧，`cyclesPerSecond = 60/craftTime`。`Conveyor.speed` 是 tiles/tick，而 `Duct.speed` 才是 items/s——**两者不能混用**。
- **源码数值不可信的实证**：`Mindustry-Source`（v159.3）里 conveyor 数值是 0.046/6.5，而 v160.7 jar 里是 **0.035/5**。同一字段差 ~30%，直接抄源码会错——这条可以作为"数值只信运行时 dump"的铁证。

## 4. 复用风险（写在这里，防止后面才发现）

1. **版本漂移**：语料、源码（v159.3）、运行时（v160.7）三者版本不同。处置：语料只用于测试/参考，生成与验证一律以 v160.7 运行时为准，并在结果里记录 gamedata 快照 id。
2. **写入保真不等于"语义正确"**：往返通过只说明字节级稳定；`config` 语义、电力连接是否真的自动重建（源码层面看**不会**，`Schematics.place()` 不调 `Building.placed()`；待 `docs/12` §补测定论）、逻辑块代码是否被游戏接受，都要靠真机确认。
3. **E2 的 A 组基线可能太少**：surge-alloy 工厂型样本 19 张，其中**零逻辑仅 3 张**（`1653826623786.msch` 14×4、`1680154199512.msch` 13×11、`_____________.msch` 20×42）。若 A 组要求"无逻辑可对比"，样本只有 3 张；对策：A1 手搭作为主基线（A2 改造只作参照），并在 E2 协议里写明"A 组样本量小"是已知限制。
4. **"钛合金"→`surge-alloy` 的映射需要项目书作者确认**：原版 22 个物品里没有钛合金，MBO.md 第七节的实验名若另有含义（如指"钛相关产线"），E2 的机队与指标都要重算。
5. **口径漂移**：本文 §0 的口径表是唯一来源；后续任何文档写数字前必须回查，否则又会出现 19/20/21 这类分歧。
3. **语料来源与许可**：语料来自第三方 schematic 包，**不能直接把别人的蓝图当 MBO 的交付产物**；只做测试样本、统计参照、模板挖掘，必要时按自己模型重画。
4. **"工厂型"分类是启发式**：按方块类别占比判定，574 张里可能混入少量"仓库/防御 + 传送带"的样本，模块模板挖掘时要人工抽检 top 样本。
5. **不要过度依赖 `data/game/` 旧数据**：它已经证明了"字段不全"的代价（craftTime 全 -1 导致所有生产计算不可能），新 dump 才是指定数据源。
