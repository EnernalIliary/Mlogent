## 0. 三条不可妥协的前提

1. **规则来自游戏，不来自语言模型。** 所有数值（配方、craftTime、耗电、钻头速度、传送带速度）都从 v160.7 真实执行器（服务端 jar）导出成版本化快照；LLM 只做"提方案/写代码/解释"，不做数值来源。
2. **离线模型必须能被真机证伪。** 离线算出的"产量 2.4/s"必须能被真引擎跑出来的数字推翻，并且这个差异会被记录、回流修正模型。
3. **搜索空间先被压缩，再被搜索。** 先用数学把"不可能"和"被支配"剪掉，剩下的才交给启发式/学习。算力决定能探索多少，经验决定值得探索什么。

**依赖只能向下，事件只能向上（结果回流）。** 具体约束：

- `L0/L1/L2` 是纯函数库：给定输入必得同一输出，无随机、无 I/O 副作用（除显式读快照），可单测。
- `L3` 是唯一允许随机的地方，但必须**带 seed 可复现**。
- `L4` 是唯一允许起外部进程（JVM）的地方。
- `L5` 只写"经验数据"，不改规则；经验是**软剪枝的输入**，不是硬约束的来源。
- `L6` 负责把人的判断变成结构化数据（约束/评分/否决理由），而不是聊天记录。

## 2. L0 GameData：版本化游戏事实快照

### 2.1 快照而不是"数据库"

游戏数据是**可替换的快照**，不是一个持续维护的手工数据库：

```
gamedata/
  v160.7/
    meta.json            # 版本、导出时间、来源(jar sha256)、导出脚本 sha256
    items.json           # id, name, hardness, cost, explosiveness, flammability, radioactivity, charge
    liquids.json         # id, name, heatCapacity, viscosity, temperature, flammability
    blocks.json          # 见 2.2
    logistics.json       # 传送带/管道/电力节点/路由器等参数（见 2.3）
    recipes.json         # 规范化后的配方表（见 2.4）
```

- 每个快照自带 `source: {jar: "sha256:...", script: "sha256:..."}`，**任何一次搜索/验证的结果都记录快照 id**，否则不可复现。
- 模组 = 另一个快照目录（`gamedata/<mod>@<ver>/`），结构与原版完全一致。这满足"MBO 文档要求的数据结构应支持未来添加模组"。

### 2.2 Block 记录（MBO 需要的字段）

```python
@dataclass(frozen=True)
class Block:
    id: int
    name: str
    size: int                     # 边长（1..9）
    category: str                 # production / distribution / power / liquid / defense ...
    health: float
    requirements: list[ItemAmount] # 建造材料（不是运行消耗）
    # 生产
    crafter: CrafterSpec | None    # craftTime(frames), inputs[ItemAmount], outputs[ItemAmount],
                                   # liquidInputs, liquidOutputs, boost 等
    drill: DrillSpec | None        # tier, drillTime, hardnessMultiplier, liquidBoost, 可挖物品判定
    # 电力
    power: PowerSpec | None        # consumption(units/s), production(units/s), capacity, range
    # 物流
    conveyor: ConveyorSpec | None  # speed(tiles/tick 或 items/s), capacity, bridge span
    conduit: ConduitSpec | None    # liquid 速度/容量/压力
    # 交互
    rotate: bool                   # 是否可旋转（决定布局自由度）
    configurable: str | None       # 主 config 的 TypeIO tag 语义：content(item/liquid/unit/block) | point | point[] | byte[](code) | string | bool | int | None
    solid: bool                    # 是否挡路（影响可达性/攻击面）
    link_range: int | None         # 电力节点连接范围
```

**关键**：`configurable` 决定 L1 解析出的 `config` 怎么解释（筛选器选物品、桥的端点、处理器的代码）。这是从 `.msch` 到语义的唯一桥梁，必须按方块类型分派，不能靠猜。

### 2.3 物流参数（MBO 文档里"物流参数"的具体化）

| 参数 | 用途 | 建模影响 |
|---|---|---|
| 传送带 items/s、容量 | 边容量 | 物流网络最大流/吞吐瓶颈 |
| 传送桥跨度 | 允许跨接 | 布局约束（`bridge-conveyor`: range=4、bridgeWidth=6.5；以 jar 反射值为准，源码 v159.3 不可抄）|
| 管道 liquid/s、容量 | 液体边容量 | 液体子网络 |
| 电力节点连接范围、电池容量 | 电力连通性 | 覆盖图 + 缓冲 |
| 路由器/分配器/装卸器吞吐 | 节点分流 | 分流器建模（保守：按均分/按需分配两档） |
| 钻头 tier / drillTime / 矿脉硬度 | 原料供给 | 原料边界条件（"地图上有什么矿"是外部输入） |

### 2.4 配方规范化（L0 → L2 的接口）

```python
@dataclass(frozen=True)
class Recipe:
    block: str
    craft_time_frames: int       # 原值（游戏里就是帧，整数；surge-smelter=75）
    inputs: dict[str, float]     # 物品/液体 -> 每批数量
    outputs: dict[str, float]    # 每批数量（原版最多 1 种物品 + 0..2 种液体）
    power_per_tick: float        # 每 tick 耗电（gamedata 原值），对外用 usage_per_second = ×60
    @property
    def cycles_per_second(self) -> float:
        return 60.0 / self.craft_time_frames      # 批/秒
```

> **量纲铁律（曾出过 60× 错）**：L0 快照存 **帧**（整数，来自 jar 反射的 `craftTime`），L2 及以上只暴露 `cycles_per_second`；任何人不得再出现"秒 = craftTime/60"或"batch_rate = 1/craft_time"这种帧/秒混用的写法。单测断言：`silicon-smelter.craft_time_frames==40 → cps==1.5`、`surge-smelter 75 → 0.8`。
>
> 生产计算只依赖 `inputs/outputs/cycles_per_second/power` 四样东西。**副产物与液体产出必须保留**（`results` 随机单出 + 多液体产出），否则物料平衡会错。

## 3. L1 Blueprint：内部数据结构

### 3.1 两层模型：Tiles + Structure

```python
@dataclass(frozen=True)
class ConfigValue:
    tag: int          # TypeIO tag 号原样保留：0 null / 5 content / 7 point / 8 point[] / 14 byte[] / 4 string / 10 bool / 1 int / 3 float / 11 double
    value: object     # 按 tag 解释；content 必须带 contentType(item/liquid/unit/block)，否则 content 与 point 无法区分

@dataclass
class Tile:
    block: str            # 方块名（引用 GameData）
    x: int; y: int         # 锚点 = footprint 中心格（= Schematic.Stile.x/y = setBlock 传入格；见 3.3）
    rotation: int          # 0..3
    config: ConfigValue | None   # **带 tag 的结构化 config**，不是枚举
    logic: LogicPayload|None

@dataclass
class Blueprint:
    width: int; height: int
    tags: dict[str, str]          # name/description/labels
    tiles: list[Tile]
    # 派生结构（惰性计算，可缓存）
    def occupancy(self) -> Grid: ...          # 每格被哪个 Tile 占据
    def partitions(self) -> Partitions: ...   # 生产模块 / 物流 / 电力 / 防御 分区（供剪枝）
    def links(self) -> list[Link]: ...        # 处理器链接、电力节点覆盖
    def stats(self) -> BlueprintStats: ...    # 面积/建筑数(blocks)/占格数(tiles)/包围盒/端口
```

**为什么不用 `list[dict]`**：搜索层需要按"分区/端口/模块"频繁切分与比较，扁平字典难以做**规范形哈希**（对称性消除）与**增量评估**（局部修改只重算受影响区域）。

**为什么 config 必须带 tag**：语料实测 config 的 tag 分布是 content 15253 / point 14136 / point[] 3266 / byte[] 1477 / string 1465 / bool 452 / int 274 / float 2 / double 2（见 10 号文档 §3.6）。一旦把 content 与 point 都折成"点/名"，写回时就再也分不开——这是 601 张蓝图写失败的根因之一。**tag 号必须原样保留。**

### 3.2 与现有代码的关系

- **解析（读）**：直接 `import` `tools/msch.py` 的 `parse_file()`，转成 `Blueprint`（只读，不改 tools/；注意门禁有镜像副本一致性要求）。它已对 831/833 张真实蓝图验证过，TypeIO 读取可用。
- **写回（写）**：**必须用 MBO 自建的 `mbo/blueprint/codec.py::write_ext()`**，不能走 `msch.build_schematic()`——后者只支持 230/831（27.68%），遇到列表型 config（point[]/array）直接抛 `cannot serialize config of type list`（坑在 `tools/msch.py:492 _write_object` 缺数组分支、`:318 _pack_point` 用带符号 int32 溢出）。
- MBO 自建 writer 的实测指标（bp-scout）：**831/831 语义往返、830/831 逐字节一致**（唯一差异是 version=0 且字典含未用项的一张，语义等价）。这是唯一可用的写回路径。
- 若将来支持模组方块：L0 的 `Block.configurable` 多一类 tag 即可，L1 不受影响。

### 3.3 坐标与旋转约定（**已用真机实测钉死**）

- **锚点 = 中心格（不是左下角！）**：`.msch` 里的 `Stile.x/y` 是方块 footprint 的**中心格**；`Tile.setBlock(x,y)` 传的也是中心格，实际 origin = `(x - (size-1)//2, y - (size-1)//2)`。实测：3×3 `vault` 传 `(33,20)` → 实占 `32..34 / 19..21`（向左下偏 1 格）；2×2 因 `(2-1)//2 = 0` 恰好看起来像"左下原点"，早期实测因此误判（`docs/12` §补C 已修正）。
  **后果**：生成器放任何 3×3 及以上方块（core/vault/大型炮台）必须按中心格算偏移，否则会覆盖邻块（实测把旁边的 2×2 压成 `build=null`）。
- 放置后必须 `Vars.indexer.addIndex(tile)`，否则方块不进索引（容器"看不见"物品）。
- 旋转：`rotation ∈ {0,1,2,3}` 顺时针 90°，渲染/放置/碰撞三处共用同一函数。
- 这些约定写进 `bp/conventions.md`，L1 单测断言 `test_anchor_roundtrip`。

#### 生成侧七条硬约束（R1–R7，全部有真机实测出处，见 `docs/13`）

| 编号 | 约束 | 违反后的症状 | 出处 |
|---|---|---|---|
| R1 | 坐标存**中心格**，origin = `(c-(size-1)//2)` | 3×3+ 方块错位、覆盖邻块 | `docs/13` §2.2 |
| R2 | `Schematics.place(px,py)` 的 (px,py) 是**蓝图中心**：`ox = px - w//2, oy = py - h//2` | 验证器算错落点 | `Schematics.java:508-521` |
| R3 | `power-node` / `power-source` 的连线必须**显式写 array config**（`Point2[]` tag=8，相对偏移） | 电力孤岛，eff=0，不产货（不报错） | `docs/13` §2.4 变体 C |
| R4 | `consumer` 必须与某个 node **正交相邻** | 隔 3 格（node range 覆盖也不管用）→ 不进网，eff=0 | `docs/13` §2.4 变体 B |
| R5 | `power-source` ↔ node 同样要显式 config | 无电 | `docs/13` §2.4 变体 A |
| R6 | 读数必须扫 `Vars.world.tile(x,y).build`，**禁用 `Groups.build`** | 建筑数/库存严重偏小（21 tile → 5 build） | `docs/13` §2.6 |
| R7 | 生成器必须自校验 occupancy（重叠即拒绝） | `place()` 静默覆盖，后者吃掉前者，蓝图能转但不产货 | `docs/13` §2.7 |

**写回层结论**：`build_schematic_ext`（保留 TypeIO tag 号）解压 body 与语料**逐字节一致 3/3**，从零构造图 `write→reparse` 一致 3/3；原版 `msch.build_schematic` 只有 27.68% 往返——写回一律走自建 writer。

## 4. L2 求解层：三个子问题，三种工具

### 4.1 生产求解（确定性，LP/MILP）

**变量**：每个方块类型 b 的数量 `n_b ∈ ℤ≥0`；每种物品 i 的净流量 `f_i ∈ ℝ`；总电力 `P`。
**约束**（线性）：

```
对每个物品 i:  Σ_b n_b · rate_b(i) − Σ_b n_b · rate_b_consumed(i) = f_i − supply_i
对电力:        Σ n_gen · prod − Σ n_use · use = P_net ≥ 0
对目标产物 t:  f_t ≥ target_rate
```

其中 `rate_b(i) = outputs[i] * cycles_per_second_b`（**批/秒，不是每帧**）。这是**整数线性规划**（建筑数整数），规模很小（几十~几百个方块的候选组合），OR-Tools CP-SAT 或 SCIP/HiGHS 都能秒解。

**分层策略**（重要）：
1. 先做**配方 DAG 的线性传递**：`target_rate` → 每层需求 → 每种中间品需求（连续 LP，忽略整数性）。这一步是纯代数，numpy 足够，无需求解器。
2. 再对"每层建筑数向上取整"（`ceil(需求/单机产能)`），得到可行但可能过量的初始方案。
3. 最后用 MILP 精修：允许过量的"共享中间品"（例如一份煤同时供硅炉和石墨压机），同时优化建筑数/电力/面积权重（多目标 → epsilon 约束或加权和，按 Pareto 存档）。

**为什么先 LP 后 MILP**：Mindustry 的生产是近似线性的（时间离散但长期平均线性），LP 误差 ~1 台建筑，这正是剪枝要用的上界/下界：LP 下界是**硬剪枝**依据（"这个组合不可能达到目标产量"），MILP 才是最终解。

**必须建模的非线性点**（否则产量会系统性偏高）：
- 建筑 `efficiency`：缺料时停机；多输入方块的"多种物品都要有" -> 以 `min` 语义建模（LP 里用每输入约束 + 全链路瓶颈传递）。
- 钻头受矿脉硬度/tier 限制：产量 = f(矿种, 钻头等级, 矿脉密度)，是**地图输入**，不是固定常数。
- 传送带容量有限：局部拥堵会使上游停机（这属于 L2 物流 + L4 真机校验的范畴，不要试图在 LP 里精确建模）。

### 4.2 空间求解（组合，CP-SAT / 精确覆盖）

**问题形式**：给定一组建筑（含尺寸/旋转）与可用矩形区域（蓝图宽高上限），求一个**不重叠**的放置，使目标函数（面积、物流距离、端口对齐）最优。

三层求解（由粗到细，逐层收窄）：

| 层 | 内容 | 方法 | 输出 |
|---|---|---|---|
| S1 | **模块选择与组合**：选哪些生产模块、各几个 | 生产 LP 的解 → 模块组合 | 模块列表 + 目标产量 |
| S2 | **模块间排布**：模块（矩形，含输入/输出端口）在画布上铺开 | 带端口的 2D 装箱（shelf/guillotine + CP-SAT 精修）；对称性消除 | 模块坐标 + 朝向 |
| S3 | **模块内建筑排列**：模块内部建筑摆放 | CP-SAT：每格 assign 1 个建筑或空；尺寸/旋转/邻接/端口位置约束 | 建筑坐标 |

**MVP 的务实选择**：S2 用"模板 + shelf packing"足够（人类蓝图 90% 是矩形模块拼贴），S3 先做**手工模块模板库 + 参数化变体**（例如 N 台冶炼炉 + 传送带环），CP-SAT 只用于"模块内 N 台的紧凑排列"这一子问题。**不要一开始就对整张蓝图做全局 CP-SAT**——变量数会爆炸，且没有收益。

> **MVP 阶段不装 OR-Tools 也能开工**：S2 先做 shelf packing + 手工模板，S3 先做模板变体。**升级到 CP-SAT 的判据**（写进决策记录，避免"永远推迟"）：E1/E2 的布局生成在 30 分钟预算内失败（放不下/重叠修不好）超过 3 次，或某类模块的人工模板覆盖不到 → 才引入 CP-SAT。同理物流层先做"贪心 A* + 手工分线"，**升级到 MCMF 的判据**是布线失败率 >15% 或 E2 出现"有解但布不通"。

**对称性消除**：蓝图整体旋转/镜像等价；模块内部也存在周期性等价（如 4 台炉子排成一行的排列）。规范化哈希 = 把 tile 集合按 (block, 归一化坐标) 排序后哈希，取 4 个旋转 × 2 镜像里最小的那个。存进 `set[hash]` 去重。

### 4.3 物流求解（图论，最小费用流 / 定向布线）

**建模**：把"建筑端口"作为节点，可铺传送带/管道的格子作为候选边，问题 = 在网格图上找一组**方向化的边**（每格 1 条传送带，有朝向），使得：

- 每个生产方块的输入端口被满足（流量 ≥ 需求）；
- 每个输出端口有去处（流量 ≤ 容量）；
- 边容量 = 传送带 items/s × 该边可承载的并行度；
- 目标：总长度最小 / 转弯数最小 / 拥堵最低。

**方法**：
1. 先解**多商品流 LP/最小费用流**（NetworkX + 自写 MCMF，或 OR-Tools），得到"哪些格子上有多少流量"。
2. 再解**格子定向**：在流量图上给每格选一个朝向，使相邻格子首尾相接（这是"管道连接"约束，可 CP-SAT 解，规模小）。
3. 电力网络单独解：节点覆盖（几何）+ 连通分量（并查集）+ 发电/耗电平衡（LP），电池作为缓冲不参与稳态平衡但影响启动。
4. 液体网络同物流，速度/容量参数不同。

**注意**：传送带是"格子上有物品流动"的连续系统，不是离散边——MBO 的离线模型用"边容量 + 最短路径"近似，**精确行为交给 L4 真机校验**。

### 4.4 多目标与 Pareto

**目标向量**（严格对齐 MBO.md 第四节的 8 项，名称不改、顺序不改；MVP 先实现前 5 项）：

```python
Metrics = {
  "yield_per_area": float,      # 1 单位面积产量
  "area": int,                  # 2 占地 = footprint(w×h)
  "blocks": int,                # 3 建筑数（实例数，不是占格数！）
  "logistics_length": int,      # 4 物流距离（传送带+导管 tile 数）
  "throughput": float,          # 5 物流吞吐量（Σ稳态输入量/秒）
  "power_draw": float,          # 6 电力（稳态净耗电）
  "extensibility": float,       # 7 扩展性（预留空列×可接端口，公式进 `mbo metrics`）
  "complexity": float,          # 8 复杂度（方块种类熵 + 转弯数）
}
```

> **三个量必须区分**：`blocks`（建筑实例数）/ `tiles`（占格数）/ `footprint`（包围盒面积）。人类习惯说"17 格"，通常是 footprint。任何报告都必须写明用的是哪个，否则 A/B/C 不可比。

- **绝不把所有指标加权成一个分数**（MBO 原则 7）。存档用 epsilon-支配的 NSGA-II 或"网格存档 + 每格保留代表"。
- 输出是 **Pareto 前沿** + 每个解的可解释理由（哪一项指标优秀）。
- 人的偏好以**约束**（"物流距离 ≤ 40"）或**排序**（"这两张我更喜欢 A"）注入，而不是改权重。

## 5. L3 搜索优化：分层 + 双剪枝 + anytime

### 5.1 搜索分层（与 MBO 文档一致）

```
Level 0  生产方案      : 选配方路线 / 模块组合（LP+MILP，枚举可行组合）
Level 1  模块排布      : 模块矩形在画布上的位置/朝向（启发式 + 局部搜索）
Level 2  模块内布局    : 建筑在模块内的坐标/旋转（CP-SAT / 模板 + 变体）
Level 3  连接          : 传送带/管道/电力的具体路径（流 + 定向）
Level 4  完整验证      : 离线仿真 → 真机抽样验证
```

上层决定下层的问题实例，下层失败则回溯上层（约束回传：例如"模块 X 在 20×20 内放不下 6 台炉子"→ 上层换模块组合）。这是 **CP/搜索里的"约束传播"**，也是"分层搜索"的真正含义。

### 5.2 硬剪枝 / 软剪枝

**硬剪枝（可证明非法或不可能）**——必须严格，不能误杀：

| 判据 | 依据 | 证明方式 |
|---|---|---|
| 建筑重叠 | 占用格集合相交 | 精确 |
| 超出画布 | 坐标+尺寸 | 精确 |
| 物料不守恒 | 某种物品净需求 > 所有可能供给 | LP 可行性 |
| 产量上界不足 | LP 最优值 < 目标 | LP 对偶/界 |
| 违反游戏规则 | 方块不可旋转/不可放置/连接超范围 | L0 数据 |
| 被严格支配 | 所有指标不差且至少一项更好 | Pareto |

**软剪枝（降低优先级，不永久排除）**——可误判，必须保留复活机制：

| 判据 | 处理 |
|---|---|
| 物流线过长 | 优先级 ×0.5，进"待探索"队列 |
| 空间利用率低 | 优先级 ×0.7 |
| 模块不可扩展 | 标记但保留 |
| 经验判断低价值 | 记分，**保留 top-K 配额**（例如每次迭代保底 10% 预算给低分方案，防局部最优） |

**实现要求**：软剪枝的分数必须**可追溯**（哪条规则、哪个经验模型给的），并能被人的否决/偏好覆盖。

### 5.3 记忆化

- **模块指纹**：`(模块内方块多重集, 尺寸, 端口位置)` → 规范化哈希 → 缓存"该模块的产能/耗电/端口能力/最小包围盒"。相同模块只算一次。
- **子问题缓存**：`(需求向量, 画布尺寸, 约束集)` → 已知可行解/不可行证明。不可行证明也要缓存（省掉重复 LP）。
- **结果存档**：每次搜索的 seed、gamedata 快照、代码 git rev、候选集、Pareto 前沿，全部落盘为 `runs/<id>/`，满足"可追溯、可复现、可验证"。

### 5.4 Anytime 与预算

- 预算 = 墙钟时间 or LP 调用次数 or 真机验证次数。**真机验证是昂贵资源**，只在候选进入 Pareto 前沿或"离线预测不确定"时调用。
- 搜索随时可停，随时可输出当前 Pareto 前沿（anytime）。

## 6. L4 验证层：双轨制

### 6.1 离线验证（快、便宜、可能不准）

- **静态合法性**：碰撞、越界、连接范围、config 合法性（用 L0 `configurable` 校验）。
- **生产/物料/电力**：复用 L2 的 LP/公式，输出"理论产量、物料平衡、电力平衡"。
- **离散事件仿真（DES）**：按 tick 推进传送带/建筑（item 位置、堵塞、efficiency），比 LP 精确、比真机便宜。先实现"传送带 = 固定速度 + 容量 + 上游停机"的最小模型。

### 6.2 真机验证（慢、权威）

- 用 v160.7 官方服务端 jar + Rhino JS 把蓝图放进真实世界跑 N tick，读核心库存/方块状态/效率（可行性见 12 号文档）。
- **抽样式使用**：不是每个候选都跑真机，而是"Pareto 前沿 + 随机抽样 + 离线不确定的候选"。
- 结果落盘为 `RunResult`：实际产量、实际耗电、堵塞点、与离线预测的偏差。

### 6.3 误差回流（MBO 文档的"修正离线模型误差"）

```
真机结果 → 误差向量（产量偏差/耗电偏差/停机原因）
        → 修正表（按方块类型/模块类型：belt 堵塞系数、drill 实际供给、电力损耗）
        → 更新 L2 的系数（版本化，作为 gamedata 旁路的 "calibration" 快照）
        → 下次离线预测更准
```

**关键设计**：修正系数是**独立于规则数据的校准层**（`calibration/<gamedata_id>.json`），不污染"游戏规则"本身，可回滚。

## 7. L5 学习层：四个阶段，先规则后模型

| 阶段 | 内容 | 数据来源 | 交付 |
|---|---|---|---|
| 1 规则库 | 人的经验写成可审计规则（"冶炼模块留 1 格维护通道"） | 人工 + 语料统计 | `rules/*.json` + 校验器 |
| 2 检索复用 | 语料蓝图 → 模块指纹库；新任务查相似模块 | 833 张 .msch 语料 | 指纹索引 + 最近邻 |
| 3 价值模型 | 预测候选的"值得深挖程度"/最终指标 | 搜索日志（候选+评估） | 排序模型（GBDT/小 MLP） |
| 4 主动学习 | 挑"模型最不确定"的候选让人审 | 模型不确定性 + 人反馈 | 审阅队列 |

**反模式警告**：阶段 1/2 就能带来大部分收益；不要跳过规则库直接上 RL。MBO 文档明确"第一阶段不需要训练大型语言模型"，这个判断是对的。

**人反馈的数据结构**（L6 → L5 的接口）：

```python
@dataclass
class HumanFeedback:
    candidate_id: str
    verdict: Literal["accept", "reject", "modify"]
    reason_code: str          # 预定义枚举：太挤/物流乱/扩展性差/电力不稳/其他
    free_text: str = ""       # 只作解释，不进入规则
    edited_blueprint: str|None  # 人的修改版（最有价值：diff → 偏好样本）
```

规则只能从**结构化字段 + diff** 里学，不从 free_text 里"猜规则"——这防止把人的随口一句变成硬约束。

## 8. 工程约定

1. **语言**：Python 3.11（工作区现有工具全是 Python，直接复用）。
2. **依赖**：`numpy`（已有）、`OR-Tools`（已验证可 `pip download` 到 cp311 wheel）、`networkx`（可选，图论）。**不引入重量级框架**；PyTorch 只在阶段 5 需要时再加。
3. **目录**（新建，与现有 mlog 工具链并存，不侵入）：

```
MBO/
  mbo/                     # 包
    gamedata/              # L0 加载 + 快照校验
    blueprint/             # L1 IR + msch 适配
    solve/                 # L2 生产/空间/物流
    optimize/              # L3 搜索、剪枝、Pareto、存档
    validate/              # L4 离线仿真 + 真机 runner
    learn/                 # L5 规则/检索/模型
    cli/                   # 命令行入口
  tests/                   # 单测 + 黄金用例（语料蓝图）
  runs/                    # 搜索/验证存档（gitignore）
  docs/                    # 本文档所在
```

4. **可复现**：每个结果记录 `gamedata_id + jar_sha256 + git_rev + seed + 参数`。搜索必须能在另一台机器上重放。
5. **测试**：黄金用例优先用**真实语料蓝图**（解析→重写→解析一致；LP 产量与真机一致率），而不是手工构造的小例子。
6. **禁止**：在规则/数值层面调用 LLM；把软剪枝写成永久排除；把多目标塌缩成单分。
