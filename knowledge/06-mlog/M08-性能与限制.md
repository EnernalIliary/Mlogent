# M08 Performance and limits

## In one sentence

Logic has exactly one performance resource: **the per-tick instruction budget**. Every "slower / frame drop / logic lag" symptom ultimately reduces to one of three things: the budget, the tick rate, or the wait granularity.

## Rules / formulas

### 1. The three levels of throughput

| Level | Formula | micro example | hyper example |
|---|---|---|---|
| steady-state throughput | `ipt × 60` instructions/s | 2×60 = 120 | 25×60 = 1500 |
| single-tick burst cap | `5 × ipt` instructions | 10 | 125 |
| program size cap | 1000 instructions | same | same |

Sources: `maxInstructionScale=5` (LogicBlock.java:45), `maxInstructionsPerTick=40` (:48), `maxInstructions=1000` (LExecutor.java:41).

### 2. What a stutter really does

```text
accumulator = min(accumulator, 5*ipt)   // 卡顿后先把池子削到上限
while(accumulator >= 1) { 执行; if(yield) break; accumulator--; }
accumulator += edelta() * ipt
```

| Symptom | Mechanism | Consequence |
|---|---|---|
| one frame stalls for 100 ms | `edelta()` grows ⇒ one add of 6×ipt points, but it is clamped to 5×ipt | part of the budget is lost |
| fast running right after a stall | the pool is filled to 5×ipt | short-term throughput > ipt |
| long-run average | always ipt×60 | a stall does not change long-run throughput |

Measured: a micro (ipt=2) going from empty to a full 5×2=10 points takes **5 tick ≈ 0.0833 s** (assertion table L1-31, measured). [measured: assertion table (docs/断言表.md)]

### 3. wait and latency

| You want | What you write | Error / source |
|---|---|---|
| wait 1 frame | `wait 0` (yields this tick) | 0 tick, but **no budget consumed** |
| wait 1 tick | `wait 0.0166` (any 0<v≤1/60 is equivalent) | exactly 1 tick |
| wait 1 s | `wait 1` | 60 tick (the parameter is in seconds, L1-29 measured) |
| an exact metronome | impossible | granularity 1 tick |

`wait` accumulates with `curTime += Time.delta/60f` (LExecutor.java:1206-1234), so on a 60 tick/s server 1 tick ≈ 16.7 ms. [src: LExecutor.java:1206-1234]

### 5. Multiple processors

- Each processor runs independently with its own budget; there is **no global quota** (aside from switches such as `disableWorldProcessors`).
- The execution order of several processors within one tick is **【U】unverified** (assertion table L3-05 pending); relying on it for synchronisation produces random bugs, so use `sync` or a flag/memory handshake instead.

## Measured facts and counter-examples

- Counter-example (a boundary that does not hold): **"adding processors scales the same logic linearly" does not hold**. Logic is a serial budget model; splitting one processor into two only helps if you are willing to rewrite the logic as parallel work.
- Counter-example: **"wait lowers CPU cost" points the right way but the mechanism is different** — a wait yields without consuming budget, but it still occupies one instruction slot.
- 【U】The exact value of the display buffer cap `maxGraphicsBuffer` was not verified in this round; it needs a read of the LogicDisplay/DisplayCmd constants.

## Common misconceptions

1. "Logic dropping frames means the game is lagging." — mostly the impression made by the clamped budget plus the burst after a stall.
2. "More processors are faster." — each processor has its own budget, but the server's total CPU is still finite.
3. "wait 0 equals spinning." — it yields this tick and consumes no budget.
