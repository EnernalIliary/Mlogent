## 0. 结论表

| 层 | 结论 | 判定依据（实测数字） |
|---|---|---|
| ① 编码 / 写回 | ✅ **可信** | 3 张语料解压后 body **逐字节一致 3/3**；从零构造 3 张图 write→reparse 全一致 3/3 |
| ② 坐标语义 | ✅ 可信，但**语义是"中心格"** | 3×3 vault 写入 (2,2) → 落 world 29..31 / 36..38，`build.tileX, tileY = 30,37`（中心）；2×2 container 写入 (8,2) → 落 36..37 / 37..38，`tileX=36`（= 左下角，因 (2-1)//2 = 0） |
| ③ 旋转 | ✅ **可信** | rot 0/1/2/3 四条传送带进引擎后 rotation 仍为 0/1/2/3 |
| ④ 电力接线 | ⚠️ **有硬约束** | 节点↔节点/电源必须显式写 array config；**consumer 必须紧贴 node**，否则 eff=0、sat=0、不产货 |
| ⑤ 产量测量 | ✅ 可测，但**必须换口径** | 2 台硅炉：窗口 487.6→1940.7 tick（24.22 s）产 72 硅 = **2.973 /s**，理论 3.0 /s，**相对误差 −0.9 %** |

**E1 前置条件判定：成立。** 从零生成的蓝图能被游戏接受、能跑、产量可测、误差 <1%（远优于 Gate 要求的 ≤5%）。

## 2. 逐条证据

### 2.1 编码层：我们的 writer 与游戏一致

```
T1a corpus body identical: [True, True, True]
   metaglass-2.msch  body 435 B  ver 1→1  file 300 B
   graphite-1.msch   body 256 B  ver 1→1  file 201 B
   cryofluid-2.msch  body 361 B  ver 1→1  file 271 B
T1b from-scratch reparse ok: [True, True, True]
```

注意区分两个层次：**文件字节**不经 zlib 压缩级别保证（原图与你写的图压缩级别不同，文件字节会不同），**解压后的 body 必须逐字节一致**。`build_schematic_ext` 满足这一条；原版 `msch.build_schematic` 不满足（27.68 % 往返，见 `docs/10` §2）。

### 2.2 坐标层：存的是"中心格"

`_dbg_3x3.py` 把 vault(3×3) 写到 (2,2)、container(2×2) 写到 (8,2)，画布 24×10 放在 (40,40)：

```
place 锚点: ox = 40 - 24/2 = 28, oy = 40 - 10/2 = 35
vault     落 29..31 × 36..38   build.tileX,tileY = 30,37   ← 中心格
container 落 36..37 × 37..38   build.tileX,tileY = 36,37   ← (2-1)//2 = 0，中心即左下
router    落 40,37             build.tileX,tileY = 40,37
```

由此得到两条必须写死的规则：

- **R1（坐标）**：`.msch` 里每个 tile 的 `(x,y)` 是**该方块的中心格**；占格原点 `origin = (cx - (size-1)//2, cy - (size-1)//2)`。对 2×2/4×4 这类偶数尺寸，"中心格"退化为左下角，所以早期"锚点=左下角"的观察在 2×2 上恰好成立，一上 3×3 就错。
- **R2（落点）**：`Schematics.place(sch, px, py, team, true)` 的 `(px,py)` 是**蓝图中心**：`ox = px - sch.width/2, oy = py - sch.height/2`（`Schematics.java:508-521`）。验证器算世界坐标时用这个式子，不要假设 (px,py) 是左下角。

> 早期文档（`docs/01` §3.3、`docs/10`、`docs/12` 初版）写的"锚点=左下角"是 2×2 实验的误判，本节为更正后的口径。

### 2.3 旋转层：原样落地

```
conveyor@30,39 rot=0   conveyor@34,39 rot=1   conveyor@38,39 rot=2   conveyor@42,39 rot=3
```

`Stile.rotation` 0..3 写入 → 引擎读出的 `b.rotation` 完全一致。**注意**：conveyor 的 `front()` 在本版本返回 `null`（与 `Building.front()` 实现有关），所以"朝向"不能靠 `front()` 验，只能验 `rotation` 数字本身 + 布局语义。

### 2.4 电力层：三条变体，只有一条能跑

同一世界里并排放三组（`_dbg_power.py`，跑 900 tick）：

| 变体 | 接线 | 结果 |
|---|---|---|
| **A** 节点紧贴硅炉 + 显式 config | node(18,19) links=1 ↔ source(18,21) links=1 | ✅ smelter `eff=1, sat=1`，容器 22 硅 / 904 tick = **1.46 /s**（理论 1.5，−2.7 %） |
| **B** 节点离硅炉 3 格 + 显式 config | node(38,20) links=1、source(38,22) links=1 | ❌ smelter `eff=0, sat=0`，**0 硅**；硅炉 `links=0`（没进网） |
| **C** 节点紧贴硅炉 + 全空 config | 两个方块 `links=0` | ❌ smelter `eff=0`，**0 硅**；节点各成孤岛 |

结论（三条，都要写进生成器）：

- **R3**：`power-node` 的连线必须**显式写 array config**（相对偏移的 `Point2[]`，tag=8）。空 config 不会自动连——`Schematics.place()` 只做 `setBlock` + `configureAny`，**不调 `Building.placed()`**，而自动连线恰好在 `placed()` 里（`PowerNode.getNodeLinks`）。
- **R4**：`consumer`（硅炉这类耗电方块）**必须与某个 node 正交相邻**。相邻时 `Building.add() → power.graph.checkAdd()` 会把它并进相邻节点的图；隔开 3 格（即使 node 的 `laserRange=6` 覆盖到）也**不进网**，因为 `placed()` 没被调用。
- **R5**：`power-source` 与 node 之间同样要显式 config（变体 A/B 的 source 都写了 `[(0,-2)]` 才 links=1）。

> 对"游戏内正常游玩"而言 `placed()` 会被调用，所以玩家手接不一定需要紧贴；但**蓝图粘贴走的正是 `Schematics.place()`**，所以生成器必须按 R3/R4/R5 保守布线。E1 的判定也用这个口径。

### 2.5 产量层：可测，且误差 <1 %

`trust_run.msch`（两台硅炉 + 两个容器）跑 1940 tick：

```
窗口 487.6 → 1940.7 tick（24.22 s），容器硅 Δ72 → 2.973 /s
理论 2 × 1.5 = 3.0 /s，相对误差 −0.9 %
两台炉 eff 均为 1.0，库存 coal=10 / sand=10（喂饱）
```

对照早期 `_dbg_power` 单炉：1.46 /s vs 1.5 /s（−2.7 %，含启动段未剔除）。两个数字都落在 E1 Gate 的 ±5 % 内。

### 2.6 读数层：`Groups.build` 不可信

同一次运行里：

```
世界实际方块：21 个 tile（vault 9 + container 4 + router 1 + core 1 + …）
Groups.build：5 个
```

源码里也有同样的自承：`MapProcessorsDialog.java:146`——"scan the entire world for processors (`Groups.build` can be empty, indexer is probably inaccurate)"。

- **R6**：验证器的一切计数（建筑数、库存、eff、电力）**必须扫 `Vars.world.tile(x,y).build`**，不能遍历 `Groups.build`。
- 影响面：`docs/12` §3 的 `built=..` 与 `items=` 聚合口径作废（那些数字偏小），E1 的产量读法改为"扫 container tile 的 `items` 差分"，与 §2.5 一致。
- 另一条坑保留：`srv.js()` 每次只可靠返回**一行**，多行 `print` 会丢行；读数压成单行 tab 分隔。

### 2.7 静默失效：重叠会被后者覆盖，但不报错

第一版 `trust_run.msch` 把 container(4,2) 摆在源 (5,2)/(5,3) 上（我的布局错误）。结果：

```
silicon-smelter@36,37  运行正常 eff=1 → 容器 17 硅
silicon-smelter@40,37  i[] eff=0     ← 它的两个 item-source 被 container 顶掉了，饿死
```

`Schematics.place()` 逐 tile `setBlock`，**不做占用检查、不报错、不提示**，后写的直接盖掉先写的。

- **R7**：生成器输出前必须跑一遍 occupancy 校验（模板占地 vs 已占格，重叠即拒绝），验证器也要独立复算一遍。这是 E1 静态 Gate 里"无重叠"那一条的真实动机。

## 4. 还没验证的（诚实清单）

1. **3×3 以上奇数尺寸在生成器布局里未实际生成过**——本报告的 vault 只是摆放实验，E1 的 24×24 画布里暂不需要 3×3 方块；等用到（如 core-shard/impact-reactor）再补一条真跑。
2. ~~传送带吞吐未测~~ **已补（`docs/14`）**：稳态 **4.9 items/s**，带长只影响延迟（≈0.47 s/tile）、不影响吞吐，单格容量 3，方向 rot 0=东/1=南/2=西/3=北；E1 走传送带版本真机 3.05/s（+1.7%）。仍缺：交叉带/junction/router 分流吞吐。
3. **逻辑块（processor）与产线联动未测**——合金厂那条线（用户已确认"需要配合逻辑运行"）走的是逻辑模板槽位，还没做端到端。
4. **`front()` 恒 null**，只能验 rotation 数字，不能验"朝向行为"（比如 router 朝哪边分流）。
