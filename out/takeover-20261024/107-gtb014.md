# 107 · GTB 0.1.4：把「每秒全图扫描」拆成事件驱动 + 滚动兜底

> 用户 m10511：「什么东西需要全图扫描啊，不能只在方块更新时扫描或者看看有没有原版API可供调用吗。」
> 前情：0.1.3 已把真正的元凶（`seqGet` 先调 `EntityGroup.get(int)` 抛异常）修掉，
> 每秒 370 ms 降到 3.3 ms。本条问的是「为什么还需要那 3.3 ms 的全图遍历」。

## §1 取证：哪些能事件驱动，哪些不能

| 需求 | 有原版事件吗 | 依据 |
|---|---|---|
| 发现「新放了哪些方块」 | **有** `BlockBuildEndEvent`（放置完成） | 触发点 `Mindustry-Source/core/src/mindustry/world/Build.java:116`、`ConstructBlock.java:67/120`、`CoreBlock.java:222` |
| 发现「拆掉了哪些方块」 | **有** `BlockDestroyEvent` | `BuildingComp.java:2250`（销毁前，tile.build 非 null） |
| 方块还在不在 | `Building.isValid()` | `BuildingComp.java:2036` |
| 钍堆热量上升 / 钍被烧完 / 冷冻液变化 | **没有**（`NuclearReactor.update()` 内部数值，无事件） | 内部 `heat` 字段，无 Events.fire |
| 发电机被塞爆混 / 爆混被取走 | **没有**（物品模块变化不发事件） | `ItemModule` 无事件；`ConfigEvent` 只属于玩家点配置 |
| 逻辑块代码被改 | **只有玩家配置那条路**（`ConfigEvent` ← `InputHandler.java:729`） | 网络同步改代码不保证走这里 |
| 世界被 world processor `setblock` / 模组直接改 | **没有事件** | ⇒ 必须留兜底 |

结论：**「检查」这三类状态只能轮询**（热量、爆混、代码都是随时间变的量），
但**「有哪些方块」不该每秒全图找** —— 这才是可以事件化的部分。

## §2 改法：三层

1. **世界载入播种**（一次性）：`WorldLoadEvent` → `seedWatch()` 全图一遍（8311 方块约 3 ms），
   填三张登记表 `GTB_WATCH.react / .gen / .logic`。
2. **事件增量维护**：
   - `onBuildEnd`（BlockBuildEndEvent）→ `watchAdd(b, bk)`；
   - `onConfig`（ConfigEvent）→ `watchAdd` 补登记（逻辑块改代码、发电机被塞爆混）；
   - 新增 `onBuildDestroy`（BlockDestroyEvent）→ `watchDrop(key)`，把监视表、`GTB_REACTORS`、
     `GTB_GENS`、`GTB_VIRUS`、`GTB.builders` 一起抹掉。
3. **滚动兜底 `sweepWorld()`**：每 tick 只登记 `GTB_SWEEP.per = 64` 个方块，
   8311 方块约 30 秒滚完一遍，单 tick <0.05 ms；兜住 world processor setblock、
   模组直接改世界、事件漏发。**它只做「登记」，不做检查。**

每秒 `watchStep(now)` 只遍历三张登记表（100~200 个方块），热量 / 爆混 / 逻辑代码在那里读。
`stepReactor` / `stepGen` 不再需要 `live` 表（登记表本身就是「还活着」的集合），
登记表里方块消失由 `Building.isValid()` + `watchDrop` 收尾。

## §2.1 代码表（GriefToBan/scripts/main.js）

| 位置 | 改动 |
|---|---|
| `GTB_WATCH / GTB_SWEEP / GTB_PERF` | 新增登记表、扫掠游标（per=64/rounds）、`sweep/sweepWorst/watch` 计数 |
| `watchKind / watchAdd / watchDrop / watchCount / watchLive` | 新增 |
| `seedWatch()` | 新增，世界载入一次性播种 |
| `sweepWorld()` | 新增，每 tick 64 个，只登记 |
| `watchStep(now)` | 新增，每秒遍历三张表，替代 `scanWorld()`（后者删除） |
| `stepReactor(b,key)` / `stepGen(b,name,key)` | 去掉 `live` 参数 |
| `stepLogic` | 先判 `isVirusCode`，代码改干净就清 `GTB_VIRUS` 标记（同一块再被注入仍会报） |
| `onBuildEnd` | `watchAdd` + 建造者表只给被处置的三类方块记 |
| `onConfig` | `watchAdd` 补登记 |
| `onBuildDestroy` | 新增，绑定 `ET.BlockDestroyEvent` |
| `tick()` | `inEditor()` 之后 `sweepWorld()`；1 秒块里 `watchStep()` |
| 自检 / 探针 | `gtb.scan` 与心跳行加 `watch= / sweep=`；selftest 增加登记表断言 |

## §5 真机验

- 重启游戏后进大地图，`gtb-debug.log` 心跳行应有 `watch=100~200`、`sweep=` 个位数毫秒，
  `ms=`（每秒那一轮）≈0（不再是 3 ms 级）。
- 地图编辑器：加载不再有每秒一次的停顿；日志 `editor=1`。
- 功能仍在：钍堆升温停用/钍取空或通冷冻恢复、爆混机只停用、自复制逻辑被停用。

## §6 未做 / 待观察

- `sweepWorld` 的 64/tick 预算没有做成可配置（暂不需要；若有人造 10 万方块地图，
  可把 `GTB_SWEEP.per` 提到 256）。
- 若后续发现「模组方块在 world load 之后才被别的模组塞进来」，滚动兜底最迟 30 秒收敛。
