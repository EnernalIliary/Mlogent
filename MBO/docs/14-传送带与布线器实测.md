## 1. 传送带吞吐（`spikes/gen/belt_probe.py`）

### 1.1 装置

同一世界铺 8 组 rig，每组 `item-source(coal)` → 若干条 `conveyor` 串联 → `2×2 container` 计数；真 60Hz 跑 **1200 tick（20 s）**，每秒单行采样（`SAMPLE\t<tick>\t<k=v …>`）。

### 1.2 实测表

| rig | 带长（格） | 稳态 items/s | 说明 |
|---|---|---|---|
| 直连 source→container | 0 | **14.7** | 无传送带，source 直 dump |
| belt 单条 | 1 | **4.93** | 单格吞吐上限 |
| belt 串联 | 3 | **4.64** | 含启动延迟 |
| belt 串联 | 8 | **4.62** | |
| belt 串联 | 16 | **4.55** | 带长只增延迟，不降稳态吞吐 |
| 带占用 | — | 每格 **3** | `belt0占用max=3.0`（= `gamedata.conveyor.itemCapacity=3`） |

### 1.3 结论与用法

- 生成器取常量 **`BELT_RATE = 4.9 items/s`**（保守值，比实测单条 4.93 略低）。
- **带长不影响稳态吞吐**，只影响延迟：所以布局阶段可以用"长度"当成本项（延迟/物流距离），不必担心串长掉产能。
- 与 `gamedata` 对照：`conveyor.raw.speed=0.035`（tiles/tick）、`displayedSpeed=5`（UI 值）。实测 4.9 与 displayedSpeed 5 吻合（−2%），说明 **UI 的 items/s 可信，raw.speed 是 tiles/tick 不能当 items/s 用** —— 这正是 11 号报告里"源码 v159.3 conveyor 0.046 与 jar 0.035 差 30%"的延伸：一切以 jar 实测为准。
- 边界：本实验只测了"单向直带"。**交叉带、junction、router 分流、sorter 过滤未测**（见 §6）。

## 2. 方向与延迟

### 2.1 方向语义（实测钉死）

```python
DIRV = {0: (1, 0), 1: (0, -1), 2: (-1, 0), 3: (0, 1)}   # 0=东 1=南 2=西 3=北
```

四向都单独跑过，都有货（4.93 items/s）。注意 **1 是南 = `-y`**（Mindustry 世界坐标 y 向下），写生成器时最容易在这里翻车。

### 2.2 延迟

| 带长 | 首货到达 |
|---|---|
| 3 格 | 1.5 s |
| 8 格 | 3.8 s |
| 16 格 | 7.6 s |

线性 ≈ **0.47 s/tile**（≈28 tick/tile）。用于 `metrics.json` 里的 `startup_latency_s` 与"预热窗口该丢多少 tick"。

## 3. 电力布线器（`gen_e1.py::route_power`）

13 号已证明"空 config 不会自动接线"，所以生成器必须自己布线。规则（与 doc01 §3.3 的 R3–R5 一致）：

1. **consumer 邻位**：每个电 consumer（本图是 silicon-smelter）找正交相邻的空位放 `power-node`；找不到就报错（R4：consumer 必须与 node 正交相邻）。
2. **连成一片**：node 之间用并查集合并，就近连线；两 node 曼哈顿距离 > `NODE_RANGE=5`（保守，laserRange 是 6）时插中继 node。
3. **电源**：选一个距 `anchor` 近、且能与某个 node 连上的空位放 `power-source`（沙盒电源，按 D3 决策允许）。
4. **写 config**：每个 node/source 写 **对称的 Point2[] 相对偏移**（`tag=8`，`dx = 对端.x - 本端.x`）。必须对称、必须显式——这是 13 号实验 A 的结论。
5. **返回 components 数**，`static_check` 断言 `== 1`。

E1 实际输出：

```
node@(5,13) 贴 silicon-smelter@(5,14)
node@(5,11) 贴 silicon-smelter@(5,9)
source@(2,12)
links: node(5,13) <-> node(5,11) <-> source(2,12);  components = 1
```

耗时：可忽略（毫秒级）。这一步不需要 CP-SAT，贪心就够——真需要优化时再换成" Steiner 树 / 最小节点覆盖"，判据写进 doc01 §L2。

## 4. E1 最小生成（`gen_e1.py`）

### 4.1 布局

24×24 画布，两条对称支线（每条 = 煤源 + 沙源 + 2 格带 + 1 台炉 + 1 个容器）：

| 要素 | 坐标（蓝图内） | 说明 |
|---|---|---|
| item-source `coal` | (2,15) / (2,10) | 沙盒供料，按 D3 允许 |
| item-source `sand` | (2,14) / (2,9) | |
| conveyor ×2（rot0 东） | (3,15)(4,15) / (3,14)(4,14) | 进炉 |
| silicon-smelter（2×2，中心格） | (5,14) / (5,9) | 占 5..6 × 14..15 / 9..10 |
| container（2×2） | (6,16) / (6,11) | 接产物 |
| power-node | (5,13) / (5,11) | 布线器生成 |
| power-source | (2,12) | 布线器生成 |

统计：**19 tiles / 31 占用格 / 175 字节 / 粘贴码 236 字符**。

### 4.2 静态校验（`static_check`）

全部通过：无重叠、无越界、每条带子前端有接收方块、每台炉都有相邻 node、电力连通块 = 1、每个 node/source 都有 links config。

### 4.3 预测（`predict`，直接读 gamedata 配方）

| 项 | 值 |
|---|---|
| 产量 | 3.00 硅/s（2 台 × 1.5/s） |
| 输入需求 | coal 3.0/s、sand 6.0/s |
| 耗电需求 | 60/s（2 × 30），电源=沙盒无限 |
| 占用格 | 31 |

### 4.4 真机结果（1800 tick）

```
窗口 305..1800 tick：3.05 硅/s（预测 3.00，误差 +1.7%）
s5_14 eff=1.00 prog=0.17 库存=19
s5_9  eff=1.00 prog=0.17 库存=19
墙钟 45.8s
PLACED indexed=36 buildings=15
```

- 两台炉 **efficiency 恒为 1.00**（不缺料、不缺电、不堵塞）。
- 实际 3.05 略高于 3.00 是窗口边界取整（丢前 300 tick 后取样首尾各差半个 batch），不是产能超发。
- 与 13 号 `trust_run`（2.973/s，−0.9%）同量级，**说明"从零生成 + 真机验证"这条路本身可信，误差在 ±2% 内**。
- 端到端（生成 + 写完 + 起引擎 + 1800 tick）**≈46 s**，符合 doc03 的"≤5 分钟"。

### 4.5 判定

doc03 的 E1 Gate：`mbo gen silicon:3/s` → 5 件产物齐全、静态合法、真机 ≥2.85/s 且误差 ≤5%。本轮（原型版）**静态 + 真机两项已达标**；还差"5 件产物目录化"（现在只写了 msch/b64/metrics，`report.md`/`trace.json` 未生成）。

## 5. 本轮踩的坑（都会再踩，记下来）

1. **`BP_PREP_JS` 是 `%` 模板**：必须 `srv.js(ep.BP_PREP_JS % {"n": 128})`，直接传模板 → `EvaluatorException: syntax error (console.js#1)`。
2. **`srv.js()` 返回的是 list**：要 `next(ln for ln in lines if ln.startswith("SAMPLE"))`；它每次只可靠返回一行。
3. **`Vars.time` 不存在**：用 `Vars.state.tick / 60.0`。
4. **2×2 方块的 origin 等于中心格**（`(size-1)//2 = 0`），只有 3×3 才偏 1 格。本轮第一版按"中心 −1"去读 container，读到了隔壁方块 → 产量读出 **0.00/s 的假失败**；修正后立刻 3.05/s。**这个坑会让"验证器"错误地判死正确蓝图**，写进 doc03 的读数口径。
5. **`power-source` 的 `productionPerSecond = 999999.96`** 会污染"净功率"计算（第一版显示 −999940/s）。`predict()` 现在把电源拆成 `power_need` / `power_supply` / `sandbox_power` 三项分别报。

## 6. 仍未验证（诚实清单）

|---|---|---|
| 交叉带 / junction / router 分流吞吐 | **未测** | 多产品/多机器汇流时 `BELT_RATE` 会打折，E2 前必测 |

| 逻辑块联动（E2 合金厂） | **未测** | MBO.md 的 E2 明确要逻辑，13 号只验了"能读写逻辑块" |

| 液体管线 / 桥 | 未测 | E2 若用 cryofluid 才需要 |
| 传送带满载时的 backpressure | 未测（本图容器容量足够） | "堵死判定"依赖它 |
