# N 运行期可变 — 方案 v1（挖矿多控 v3 基线）

> 目标（m06648）：N 不再写死在 init，而是运行期按核心库存动态算。
> 本文只给方案与影响面，**不改代码**。基线产物 `Logic/多控挖矿-v3.mlog`（30 槽 / stride 18 / @pulsar / 签名 daf5df426e9a）。

---

## 1. 结论先行

**这不是重构，是搬家。** 派发层本来就把 N 当变量用：

| 位置 | 语句（v3 行号） | 角色 |
|---|---|---|
| 热派发 | `:32-33` `op mul tmp.hp N -18` / `op sub tmp.hp tmp.hp 3` | 进槽表第 N 槽 |
| 表尾 | `:577` `op add @counter @counter tmp.hp` | 每圈 1 条跳回 |
| 体检派发 | `:591` `op mul tmp.p N -2` | 从 chk_N 起扫到 chk_1 |
| 补员预算 | `:16-17` `op mul cfg.cap N 2` / `op add cfg.cap cfg.cap 4` | 一次补员的绑定次数 |
| 夹取 | `:30-31` `op min N N 30` / `op max N N 1` | 越界保护 |

其中 chk 派发是**内联**的（每圈现算），天然跟着 N 走；只有 `tmp.hp` 和 `cfg.cap` 是 init 算死的一次性缓存。
所以「N 可变」= **把 N 的赋值点从 init 挪到补员段，并在同一段里重算 tmp.hp / cfg.cap**，热循环一条不用动。

补员链本身已经是被 N 约束的：chk 从 chk_N 进入、逐级下落到 chk_1，fillK 的尾巴跳 `chk(K-1)` ⇒ 槽位 > N 永远不会被填。
**实测佐证**：N=4、8 只 pulsar 跑 400 tick，只有 u4..u1 被占（u5..u30 全 null），说明 N 是硬边界，不需要额外守卫。

## 2. 三个候选架构

### A. 窗口式（推荐）

槽表固定 30 个（u30..u1），N 只决定「窗口 = uN..u1」。

- 改 N 的成本：**4 条**（重算 tmp.hp 2 条 + cfg.cap 2 条），放在补员段里一次性执行。
- 表结构不动、跳转地址不动（相对派发本来就不写死地址）。
- 缩容：槽外的单位不再收到 ucontrol，**10 s 后 controlTimer 超时自动掉控**（LogicAI.java:59-63），回归游戏 AI 自己挖矿/倒核心 —— 零成本释放。
- 扩容：新槽 u_{Nold+1}..u_N 是空槽，补员从 chkN 往下扫，天然先补它们；一次补不完就下一个 2 s 周期继续（预算 cfg.cap 也是新的）。

### B. 压缩式（表长 = 实际占用）

复用 `--live` 那一套：L = 存活槽数，4 条/槽降序收缩 + `op mul tmp.p L -4` 入口。

- 改 N 要**移动单位**（swap-with-last 或整段上移），成本 `O(|ΔN|)` 条，且要保证不把正在搬货的单位挪丢。
- 收益：热循环只走真正有单位的槽。只有「N 长期远小于 30」时才划算。

### C. 分档直派

预生成 2~3 段独立槽表（如 8 槽段 / 16 槽段 / 30 槽段），每段自带派发；切换 N 只需 1 条跳转换入口。

- 成本最低、行为最稳（每段都是满血直派发），但**语句翻倍**：一段 30 槽已经 543 条，再加 16 槽段 +288 条 ⇒ 逼近 1000 条硬上限（LExecutor.java:41）。
- 只适合「档位很少且槽位数不大」的场景。

| | 改 N 成本 | 热循环条数 | 语句占用 | 适合 |
|---|---|---|---|---|
| **A 窗口式** | 4 条 | 18N+4 | 固定 955 | N 在 1..30 全域变化 |
| B 压缩式 | ~4×|ΔN| | 18L+4 | 固定 + 收缩段 | N 长期远小于槽位 |
| C 分档直派 | 1 条 | 各段独立 | ×档位数 | 只要 2~3 个固定档 |

**建议 A。** 理由：挖矿的热路径没有「逐单元状态」需要搬（状态全在单位自己身上），所以不需要压缩；而 A 的改动只有 4 条语句 + 一个公式。

## 3. A 方案的改动清单

### 3.1 必改（3 处）

| # | 改什么 | 为什么 | 成本 |
|---|---|---|---|
| 1 | N 的赋值从 init 挪到补员段（`rf1` 之后、chk 之前） | 补员段是唯一「所有单位状态已知 + 可以做重活」的地方 | 搬家 |
| 2 | 同一段重算 `tmp.hp`（`op mul tmp.hp N -18` / `op sub tmp.hp tmp.hp 3`） | 不重算 ⇒ 下一圈入口落到槽中间（v27 踩过：tmp.p 被 chk 段覆盖，入口歪到 604） | 2 条 |
| 3 | 同一段重算 `cfg.cap`（`2N+4`） | 预算是 N 的函数；不同步 ⇒ 扩容后补不满、缩容后白烧绑定 | 2 条 |

### 3.2 修一个既有隐患（建议一起做）

`loc` 段用的是 `ubind u1`（`:956`）。u1 是补员链最末一槽，**单位数 < N 时 u1 恒空** ⇒ loc 整段跳过 ⇒ `ox/oy` 永远是 null ⇒ 全队不挖矿。
动态 N 会主动往「N < 实际单位数」的方向走（见 §5），这个坑会变成必现。

改法（与 N 解耦，2 条）：`ubind uty` + `sensor tmp.c @unit @controller` + `jump hot notEqual tmp.c @this` —— 只借「一个已经归我们管的单位」来跑 `ulocate ore`，不在乎它是第几槽。

### 3.3 不用改（确认过的）

- chk 派发（内联 N）、fill 链（chk 进入 ⇒ 天然有界）、槽位跳转地址（相对派发）。
- 热循环 18 条/槽：一条不动。

## 4. N 从哪来（核心库存 → N）

### 4.1 先定方向（这个必须你拍板）

- **供给侧**：库存**低** ⇒ 多派人（N↑），库存高 ⇒ 减人。用于「保证产线不断料」。
- **需求侧**：库存**高** ⇒ 多派人（N↑），库存低 ⇒ 减人。用于「快速堆量」。

挖矿逻辑通常是供给侧（缺什么补什么），但两条路线**架构改动完全一样**，只差公式里的符号，可以先把骨架做好、公式后调。

### 4.2 三个公式（成本递增）

| 档 | 写法 | 条数 | 特点 |
|---|---|---|---|
| 线性 | `sensor tmp.stk core @totalItems` → `op div N tmp.stk cfg.unit` → `op floor N N` → 夹取 | 4~5 | 连续，但抖动敏感 |
| 阶梯 | 3~4 条 `jump` 分档（如 <500→4 / <2000→8 / <8000→16 / else 30） | 8~10 | 稳，语义清楚，最好调 |
| 双闸 | 先算需求档，再 `op min N N tmp.avail`（实际可用单位数） | +3 | 防止 N 大于单位数空转 |

**双闸为什么必要**：N=20 但只有 8 只单位 ⇒ 热循环白跑 12×18 = 216 条/圈，纯粹浪费 ipt。`tmp.avail` 可以在补员段免费统计（fill 链本来就在数绑定次数 tmp.t，加一条 `op max tmp.avail tmp.t 0` 之类即可，或直接用「上一轮成功占用的最高槽号」）。

### 4.3 迟滞（必须有）

库存每 2 s 变一次，N 跟着跳 ⇒ 单位被反复认领/释放，白烧 10 s 掉控窗口。

- 死区：`|N_new − N| ≥ 2` 才改（1 条的差值忽略）。
- 回差：升档阈值 > 降档阈值（如升到 16 要 >8000，降到 8 要 <6000），2 条。
- 冷却：N 最多每 4~6 个补员周期改一次（`op add cfg.nchg @time 10000` 门控），3 条。

## 5. 数量表：N 与一圈时长（这个决定「动态 N 有没有意义」）

micro 2 ipt，挖矿 stride 18 ⇒ 一圈 = (18N+4)/120 秒：

| N | 4 | 8 | 9 | 12 | 16 | 20 | 30 |
|---|---|---|---|---|---|---|---|
| 一圈 | 0.63 s | 1.23 s | 1.38 s | 1.83 s | 2.43 s | 3.03 s | **4.53 s** |

两条硬约束：

1. **掉控超时 600 tick = 10 s**（LogicAI.java:59-63）⇒ 一圈必须 < 10 s ⇒ N ≤ 66，被 1000 条上限先卡在 30。**挖矿在 1..30 全域都安全。**
2. 搬运（haul）版 stride 19、一圈 (19N+3)/120 ⇒ N > 9.1 就超过 `transferDelay` 90 tick (1.5 s) ⇒ **动态 N 只对挖矿有意义；haul 版应把 N 钳在 ≤9。**

这是本次方案最重要的架构结论：**挖矿的瓶颈不是 1.5 s 转移节流（每单位几秒才倒一次货），所以 N 真的能铺到 30；而搬运版铺到 30 只是排队。**

## 6. 风险清单

| # | 风险 | 处理 |
|---|---|---|
| R1 | N 变化后 tmp.hp / cfg.cap 没同步 | 规定「N 只在补员段改，且紧接 2 条重算」，不许在别处写 N |
| R2 | 缩容后旧单位仍在挖 | 10 s 超时自愈，不主动 unbind（显式释放要级联扫描，30 槽 ×2 条，不值） |
| R3 | 扩容后新槽补不满 | 预算 cfg.cap=2N+4 可能不够一次铺满，允许跨 2 个补员周期 |
| R4 | N 抖动 | 死区 + 回差 + 冷却（§4.3） |
| R5 | N 变大 ⇒ 单只单位被摸的间隔变长 | 挖矿可忍（自治采矿 + 10 s 掉控线）；面板上把「一圈 s」打出来 |
| R6 | N 算成 0 或负数 | `op max N N 1` 必须保留（现在 `:31` 就有） |
| R7 | 库存读的是核心还是容器 | `ulocate building core` 拿到的 `st` 才是核心；`ubind u1` 修完后 loc 才可靠（§3.2） |

## 7. 落地步骤（每步可独立验证）

1. **搬 N**：init 的 `set N 8` 保留为初值；补员段读库存 → 算 N → 夹取 → 重算 tmp.hp / cfg.cap。
   验证：`--probe` 看 N=1/8/30 各只跑对应槽数（沿用 v27 的探针手法）。
2. **修 loc 段**（`ubind u1` → `ubind uty`）。
   验证：3 只单位 / N=8 时 `ulocate ore` 仍在执行、ox/oy 非 null。
3. **加迟滞**。
   验证：库存稳定时 N 不跳（跑 3000 tick 数 N 的变更次数）。
4. **接公式**（供给侧或需求侧）。
   验证：把核心库存人为改大/改小，看 N 与槽位占用来回跟随。
