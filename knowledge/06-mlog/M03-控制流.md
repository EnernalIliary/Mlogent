# M03 Control flow

## In one sentence

mlog has no if/while, only **jump** (a conditional branch) and **a writable @counter**; a loop is a jump backwards, a branch is a jump forwards, and `end` is just "jump to 0".

## Rules / formulas

### 1. The 8 jump conditions (the ConditionOp enum)

Source: `Mindustry-Source/core/src/mindustry/logic/ConditionOp.java` (`:6-13` declares **8 values**). The text export uses the **enum name** as the token (`jump 24 strictEqual unFlag flag`), while the UI shows the symbol (`==` / `not` / `===`); the two are not the same thing. [src: Logic-Docs-v1.1.0.md:1661]

| # | Text token | UI symbol | Semantics | Numeric rule | Source |
|---|---|---|---|---|---|
| 1 | equal | == | equal | `Math.abs(a-b) < 0.000001` | ConditionOp.java:6 |
| 2 | notEqual | not | not equal | `Math.abs(a-b) >= 0.000001` | ConditionOp.java:7 |
| 3 | lessThan | < | less than | exact `<` | ConditionOp.java:8 |
| 4 | lessThanEq | <= | less than or equal | exact `<=` | ConditionOp.java:9 |
| 5 | greaterThan | > | greater than | exact `>` | ConditionOp.java:10 |
| 6 | greaterThanEq | >= | greater than or equal | exact `>=` | ConditionOp.java:11 |
| 7 | strictEqual | === | strict equal (type bit + exact value) | **not always false**, see 1b | ConditionOp.java:12 / :32-33 |
| 8 | always | always | unconditionally true | neither operand is read at all | ConditionOp.java:13 |

Counting: **8 in the enum**; counting only "comparison operators" gives **7** (8 minus `always`) — that is the "7 condition ops" figure quoted in the docs. `jump <dest> always` may omit the operands entirely (LStatements.java:1033/1041 renders the two input boxes only for non-always).

### 1b. equal's float tolerance and the truth about strictEqual

How a jump actually compares is decided by `ConditionOp.test(LVar, LVar)` (ConditionOp.java:31-40), **not** by the lambda passed when the enum constant is constructed:

```java
if(this == ConditionOp.strictEqual){                                  // :32
    return va.isobj == vb.isobj && ((va.isobj && Structs.eq(va.objval, vb.objval))
                                  || (!va.isobj && va.numval == vb.numval));  // :33
}
if(objFunction != null && va.isobj && vb.isobj) return objFunction.get(va.obj(), vb.obj()); // :35-37
return function.get(va.num(), vb.num());                              // :39
```

- `equal` / `notEqual`: unless "both sides are objects", they take the numeric path at :39 with a tolerance of **1e-6** [src: ConditionOp.java:6-7]⇒ `0.1+0.2` and `0.3` **compare equal** (difference 5.55e-17). When both sides are objects they take `Structs.eq` at :35-37 (reference equality).
- `strictEqual`: hits the special case at :32-33 ⇒ semantics = **the type bits agree** (both objects or both numbers) + numbers compared with an exact `==` (no 1e-6 tolerance) + objects compared by **reference**.
- An object vs number comparison **degrades**: the object function runs only when both isobj are true; otherwise `num()` treats a "non-null object" as 1 and a "null object" as 0 (LVar.java:56-58) ⇒ `jump ... equal @unit 0` holds while nothing is bound, so "is a unit bound" must be written `strictEqual @unit null`.

```mlog
op add x 0.1 0.2
jump eq equal x 0.3        # 成立（1e-6 容差）
jump ok strictEqual x 0.3  # 不成立（精确 ==，x = 0.30000000000000004）
ok:
```

**Counter-example (important)**: "`strictEqual` (`===`) is always false" is a very widespread claim — grounded in ConditionOp.java:12 writing the lambda as `(a, b) -> false`. But that lambda is only the `function` field, which `test()` short-circuits at :32, and both `jump` (LExecutor.java:1200 `op.test(value, compare)`) and `op select` (LExecutor.java:893) go through `test()` ⇒ **the always-false claim does not hold**. It is always false only when you bypass test() and call `ConditionOp.function` directly. [measured: assertion table (docs/断言表.md)]

### 1c. Three typical ways to write a condition wrong

| What you write | What actually happens | What you should write |
|---|---|---|
| `jump 5 not a b` | `not` is a **UI symbol**; the text parser reads enum names ⇒ it is unrecognised, so the condition may fall back to the default `notEqual` or fail to parse | `jump 5 notEqual a b` |
| `jump 5 == a b` | same as above; `==` exists only in the UI | `jump 5 equal a b` |
| `jump 5 always 0 0` | legal but unnecessary; the operands are ignored | `jump 5 always` |

For float comparisons always prefer `lessThan`/`greaterThan` with a tolerance; never use `equal` to test "two computed numbers are the same". To test "the same object", use `strictEqual`.

### 2. The three kinds of "stop"

| Instruction | Effect on @counter | Effect on the processor | Consequence |
|---|---|---|---|
| `end` | reset to 0 (same as `jump 0 always`) | keeps running | the next tick starts over from statement 1 (L1-01/L1-03 measured) |
| `stop` | counter-- first, then yield, sets `stop=true` | **stops** | the program no longer advances; the processor needs an external restart (LExecutor.java:1236-1245) |
| `wait` n | stays put (counter--, yield) | pauses for n ticks | resumes at the same statement when the time is up (LExecutor.java:1206-1234) |

### 3. Writing a loop

The `for` equivalent (counter version):

```mlog
set i 0
loop:
op add i i 1
jump loop lessThan i 10
```

Key points:

- **The loop body runs with no wait**, but it eats the whole per-tick budget (M08); to throttle it, use `wait 1` (≈1 s, see the precision section below).
- `wait 0` is special: it yields immediately and **consumes no budget** (`break` comes before `accumulator--`), equivalent to "give up the rest of this tick" without spending time. Measured semantics in L1-30.
- For the counter prefer `op add` over self-incrementing with `set`, so float error does not accumulate.

### 4. Consequences of rewriting @counter

| Value written | Result | Basis |
|---|---|---|
| 0..N-1 | normal jump | the pre-check in runOnce |
| >= N (program length) | **reset to 0**, no crash | `counter.numval >= instructions.length → 0` (LExecutor.java:111-121) |
| < 0 | **reset to 0** | same as above (L1-04 measured) |
| fractional | truncated by the int cast | `(int)(counter.numval++)` |

`@counter` persists across ticks; `jump`/`end`/`stop` all write it directly.

### 5. wait precision

- The parameter is in **seconds** (not ticks); internally it accumulates `curTime += Time.delta/60f` (LExecutor.java:1206-1232). At 60 tick/s, 1 tick = 1/60 s ≈ 16.7 ms, so `wait 1` ≈ 60 tick ≈ 1 s and `wait 0.05` ≈ 3 tick. [src: LExecutor.java:1206-1232]
- `wait 0`: the value <= 0 branch, `yield=true; curTime=0`, and **no counter--** ⇒ the next tick retries the same statement.
- So a "metronome accurate to the millisecond" is impossible; anything finer needs several processors out of phase. Assertion table L1-29 confirms the granularity is 1 tick. [measured: assertion table (docs/断言表.md)]

## Measured facts and counter-examples

- ✅【E】statements after `end` never run and `@counter` resets to 0 (L1-01/L1-02).
- ✅【E】`jump -1 always` restarts from 0; it is not a no-op (L1-04).
- ✅【E】`wait 0` only yields and consumes no budget (L1-30); filling the burst pool takes 5 tick ≈ 0.0833 s (L1-31). [measured: assertion table (docs/断言表.md)]
- Counter-example (a boundary that does not hold): **"jump conditions compare floats exactly" does not hold**. `equal` goes through `num()`, which maps NaN to 0 and null to 0 ⇒ two "zeros of different origin" compare equal. To separate objects from numbers, use `strictEqual`.

## Common misconceptions

1. "There is a while statement." — there is not; only jump.
2. "end stops the program." — end returns to the top; use stop to stop.
3. "wait is accurate to the frame." — the granularity is 1 tick (≈16.7 ms), and it depends on the server tick rate. [src: knowledge/VERSION.md:1]
4. "An out-of-range jump crashes." — it does not; it wraps to 0 and restarts silently.
