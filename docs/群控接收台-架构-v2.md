## 0. 先定位 v1 为什么不控制台子

v1 在模拟器里能配置 sorter 当假台（9 台分配出 lead×1 / titanium×4 / silicon×4），但真机不动。按可能性排序，四个候选，每个都有明确的证伪方法：

| # | 候选原因 | 为什么可疑 | 一行证伪 |
|---|---|---|---|
| A | **链接顺序/数量假设错了** | v1 假设 `link0=message1`、`link1..15=台`，且写死 `set npad 15`。真机 `getlink i` 按**连接顺序**走，跟位置无关；少于 15 条链接时尾部全是 null，整段被跳过 → 静默什么都不做 | `print @links` 看实际链接数 |
| B | **台子里没水** | 资格过滤 `@efficiency < 1` 直接跳过。着陆台的 `@efficiency` 是「水 ≥ 100」的布尔（`LandingPad.java:96-98`：`liquids.get(water) >= consumeLiquidAmount ? 1 : 0`，amount=100f），没水就是 0 → 全部台子被过滤，一条 config 都不发 | 贴 `sensor e pad1 @efficiency` + `sensor w pad1 @water` |
| C | **台子是满的** | `@totalItems > 0` 也跳过。刚落完地的台在 dump 前会短暂显示 100 件 | 贴 `sensor t pad1 @totalItems` |
| D | **物品不在本星球/未解锁** | `LandingPad.java:74` 的 config 里 `!item.isOnPlanet(...) || !item.unlockedNow()` 直接 return，**静默拒绝**，台子配置保持原样 | 人工点一次台子看能不能选那个物品 |

诊断包（贴进任意处理器，5 行）：

```
print @links
printflush message1
sensor t1 pad1 @type
sensor e1 pad1 @efficiency
sensor w1 pad1 @water
sensor i1 pad1 @totalItems
```
读出来就知道是 A / B / C 哪一种。

## 1. 目标与硬约束

**目标**：N 台着陆台、M 种物品，进口能力不足时把「接收选项」调度到尽量不让台子断供。

**约束（不可绕过，来自源码）**
1. 读不到冷却进度（`cooldown` 无 LAccess）、读不到进口率（`getImportRate` 无 LAccess）⇒ **不可能做预测式调度**，只能做反馈式。
2. 引擎已经按物品做了全局串行队列：`waiting.get(config)` + `importCooldownTimers`，每个物品每帧只放行一台，落完地把该物品 timer 归零并 first↔head 交换 priority（`LandingPad.java:156,183-200`）⇒ **同物品多台在引擎侧已经公平轮转**，逻辑唯一能拧的旋钮是「每种物品分几台」。
3. 台子装满后**静默丢单**，不补发 ⇒ 台子空转的代价是整个 landing 周期。
4. 物品喂不进台（`acceptsItems=false`），只能靠 config 换物品。

**由此得到唯一的调度变量**：`k_i` = 分给物品 i 的台数，`Σk_i = N`，理想 `k_i ∝ 需求/供给`。

## 2. 架构：五层

对 v1 最大的改动是**把「链接布局」和「物品表」都从编译期常量变成运行期事实**，逻辑不再假设任何东西。

```
┌─ L0 发现（每圈重数，不写死）───────────────────────┐
│ p = 0                                            │
│ loop: getlink b p                                │
│       b null → 跳过                              │
│       sensor ty b @type ≠ @landing-pad → 跳过     │
│       sensor eff b @efficiency < 1 → 跳过（没水） │
│       sensor tot b @totalItems > 0 → 跳过（在飞） │
│       npad += 1                                  │
│ 产出：npad = **本圈真正可用的台数**（不是链接数） │
└───────────────────────────────────────────────────┘
┌─ L1 快照 ─────────────────────────────────────────┐
│ 借一只单位 ulocate 核心（或直接吃 link 里的核）    │
│ 只读 1 次：mx = max over items(@库存)             │
└───────────────────────────────────────────────────┘
┌─ L2 打分 ─────────────────────────────────────────┐
│ 对每个物品（编译期展开，不 lookup）：              │
│   amt = sensor core @item                        │
│   s_i = (w_i * (mx - amt))^e   → 存 sc_<item>    │
│   sum += s_i                                     │
│ 产出：sum、每物品分数（各存一个变量）              │
└───────────────────────────────────────────────────┘
┌─ L3 分配（物品外循环 + 链接游标内循环）───────────┐
│ vol = sum / npad          （npad 只进分母，不当预算）│
│ 物品顺序推进；每个物品块：                        │
│   pf += s_i                                      │
│   while pf >= vol:                               │
│       取下一个可用台（游标 p 在链接上单调前进，   │
│       跨物品共享，扫到 @links 为止）              │
│       下发该物品；pf -= vol                       │
│ 余量 pf 自动 carry 给下一个物品                    │
└───────────────────────────────────────────────────┘
┌─ L4 下发 ─────────────────────────────────────────┐
│ 对每个被分配的台：                                │
│   getlink b p / 类型校验 / 水≥100 / 空仓 →          │
│   control config b <item>                         │
│   control enabled b true                          │
└───────────────────────────────────────────────────┘
```

**为什么台游标不是「预算」而是一条扫到头的链接游标**：L0 数出来的 `npad` 只用来算 `vol`；
真正发多少个台由「`pf` 攒够几份 `vol`」决定，游标 `p` 单调前进到 `@links` 就收工。
这样就不会出现「L0 数了 12 台、L4 却扫了 15 条链接」的计数与遍历对不上的问题——
v1 用 `set npad 15` 时正是靠硬编码把两者强行对齐的。

## 3. 三个关键设计决定

### D1 物品表：编译期展开，不用 `lookup`

v1 用 `lookup item it i` + `@itemCount` 动态遍历。两条路：

| | lookup 动态 | 静态展开（推荐） |
|---|---|---|
| 语句 | 少（3 条/物品 → 循环复用） | 多（展开 20 次） |
| 依赖 | `@itemCount` + 内容注册表 id 顺序 | 无（生成器持有清单） |
| 加 mod 物品 | 自动生效 | 要重新生成 |
| 真机风险 | `lookup` 在非世界处理器上虽不禁用（`LStatements.java:875` 无 `privileged()`），但 id 顺序与版本绑定 | 无 |

推荐**静态展开**，理由：`@itemCount` 只有在「物品集合会变」时才有价值，而这是个固定游戏版本的逻辑；静态展开同时省掉 `read w @this <name>` 的一层间接（权重直接是字面量），并且能把 `sc_<item>` 存成独立变量，L3 不用重算分数。

### D2 链接发现：getlink 扫描，按类型+资格过滤，不按顺序

```
set p 0
set npad 0
sc0: jump sc1 greaterThanEq p @links     ← @links 是运行时真值
     getlink b p
     jump sc2 strictEqual b null
     sensor ty b @type
     jump sc2 notEqual ty @landing-pad
     sensor eff b @efficiency
     jump sc2 lessThan eff 1
     sensor tot b @totalItems
     jump sc2 greaterThan tot 0
     op add npad npad 1
sc2: op add p p 1
     jump sc0 always
sc1: jump done lessThanEq npad 0         ← 一台可用都没有，直接收工（防 vol=sum/0）
```
11 条 + 5 条/链接。message1 在哪个下标、台子怎么排、有没有别的链接，全都不影响。

**关键语义**：`npad` 统计的是**可用台**（有水 + 空仓），不是链接总数。于是
`vol = sum / npad` 摊的是「这一圈真正能接货的容量」——没水的台不占份额，份额
自动落到能落的台上；等它补上水，下一圈自然回到分母里。这比「按总台数摊、
再跳过没水的台」更公平：后者会把没水台的份额直接丢掉。

代价是 `npad` 每圈会变，`k_i` 随之浮动 ±1。因为 `control config` 是幂等的、
且没水的台本来就落不了地，浮动无害。

### D3 资格判定：三态 + 两条闸门

```
sensor eff b @efficiency     ← 水 ≥ 100（LandingPad.java:96-98 精确等于「够一次着陆」）
jump skip lessThan eff 1
sensor tot b @totalItems
jump skip greaterThan tot 0
```
- `@efficiency` 是**精确**的水量闸门（不是近似）：`consumeLiquidAmount=100f`，台子液容 200（`liquidPad=2`）。
- `@totalItems > 0` 只跳过「正在卸货/在飞」的台。
- 被 disable 的台：`enabled=false` ⇒ efficiency=0 ⇒ 永远被过滤 ⇒ 自锁；所以下发时必须 `control enabled b true`（v1 已有）。

## 4. 时序与节流

| 事件 | 动作 |
|---|---|
| 上电 | 立刻跑一圈 |
| 每 `period`（默认 10 s） | 跑一圈 |
| 台子落地（`@totalItems` 由 >0 变 0） | 不管，靠周期覆盖（引擎侧已经有 5 s 冷却 + 每物品队列） |

**为什么不做事件驱动**：读不到 landing 事件（`produced()` 不可观测），只能轮询 `@totalItems` 跳变，那本身就是一圈扫描，不如直接周期。

## 7. 待你拍板的四件事

1. **处理器**：micro / logic / hyper？（决定要不要为语句数做取舍）
2. **物品表**：Serpulo 全 20 种，还是你只关心其中几种？（少一半能省 ~120 条）
3. **周期**：10 s 默认，还是要更短（6 s）/更长（20 s）？
4. **要不要 Tier2**（自适应供给）：按每种物品的**实测落地间隔** T̂ 修正 `s_i ← s_i / T̂_i`，让调度自动偏向进口慢的物品。代价 +4×N 条 + 每台一个时间戳变量，且 T̂ 需要几十秒才收敛。
5. **npad 重数时机**：每圈重数（+5 条/链接，≈91 条/圈，台子被拆/加水都能立刻跟上）vs 只在 init 数一次（省 ~75 条/圈，但台子被拆后会虚高，需要手动重跑）。默认按你说的「初始化时获取」＝init 一次；要更稳就改每圈。

## 8. Tier2 草案（可选）

- 每台存一个「上次见到 totalItems 由 0 变 >0 的 tick」（`set t<i> @time`）。
- 每圈扫台时，若某台 `tot > 0` 且上次记录为 0，则 `dt = @time - t<i>`，按物品累加 `sumT_<item> += dt`、`cnt_<item> += 1`。
- `T̂_i = sumT_i / cnt_i`，`s_i ← s_i * 1000 / T̂_i`（对 20 秒量级做定点）。
- 只在 `cnt_i >= 3` 时启用修正，否则退回纯需求。
- 风险：把台子从慢物品抢走会让它更慢，形成正反馈 ⇒ 需要死区（比值 1.25 内不动）。

## 9. v2 实现与实测（已交付）

生成器 `tools/mlogc_landing2.py`；产物 `Logic/群控接收台-v2-micro8.mlog`（135 语句，签名 0a38bfb34be0）与 `Logic/群控接收台-v2-logic30.mlog`（同代码，仅周期与 print 头不同，签名 644afce98dad）。两份 check 均 0 error 0 warn、全语句可达。

**核心定位改三级**（v1/v2 草案里只有 ulocate 一级，会导致「处理器没有任何单位时永不定位核心」）：

| 级 | 条件 | 成本 |
|---|---|---|
| 0 | 已缓存的核心仍有效（`sensor cap core @itemCapacity` ≥ 4000） | 3 条/圈 |
| 1 | 借一只单位 `ulocate building core`（从上次成功的类型下标 `uiok` 起扫，命中即停） | 9 条/圈（稳态） |
| 2 | 退路：扫链接找 `@itemCapacity ≥ 4000` 的建筑（核心一定被链接，否则读不到库存） | 5 条/链接，只在 0/1 都失败时跑 |

**实测（mlogsim v160.7，9 个 sorter 假台 + 核心 400 铜/硅/铅/钛）**

- npad：链接 10 条（message1 + 9 台）→ `npad=9`，message 被 `@type` 过滤掉。
- 分派结果：graphite 1 台、thorium 6 台、plastanium 1 台、第 9 台空置 —— 累计切片在浮点余量 <1 份 vol 时不再开台，属预期。
- 结算变量：`mx=400`、`sum=119855220`、`vol=1.33e7`、`pf` 收敛到 `vol`。
- **每圈真实工作量**（itrace 分段减去让路自旋）：9 台 708 条、30 台 1076 条。
  - micro（2 ipt）：708 → 354 tick = **5.9 s**；周期设 10 s，占空比 59%。
  - logic（8 ipt）：1076 → 134 tick = **2.24 s**；周期设 4 s，占空比 56%。
- 资格闸门实测：真 `@landing-pad` 未供水 → `@efficiency=0` → `npad=0` → 本圈直接放弃（连核心都不定位），不会把台子配错。**（此行为已在 v2.2 改为默认不判水，见 §11）**

**已知取舍**：tail 物品在「份数取整」处被丢掉（`vol` 是平均值，得分不足一份 vol 的物品永远轮不到）。要更公平需加一轮「保底一台」小循环（+3×M 条），当前按你「先保证调度」的要求未做。

## 10. v2.1：卡在 gate 的三处修正

用户反馈「一直卡在 39/40 行的 gate」。gate 本身是设计中的让路（每 10 s 才干活），但**如果永远出不去**，只可能是两件事：`npad == 0`（没有可用台）或 `core == null`（既绑不到单位、核心又没链接）。两条都会在几十条指令内直接冲回 gate，于是看上去「死在 gate 上」。

三处改动：

1. **让路改用 `wait`**。原实现是 `jump work greaterThanEq @time gate` / `jump main always` 自旋，靠 `@time` 判时间；现在 `main: wait wt`（LExecutor.java:1219-1232，`curTime += Time.delta/60f` 即**秒**，并且 `exec.yield = true` 让出本 tick），等待期间 **0 ipt**，也不再依赖 `@time`。`set wt 0` 让首圈立即执行。
2. **失败快重试**：`npad == 0` / `core == null` / `vol <= 0` 三条早退路径把 `wt` 压到 2 s（加水、补链接后 2 s 内就跟上），正常圈仍是 10 s / 4 s。
3. **空核心兜底** `op max mx mx 1`：原公式 `d = w*(mx-amt)`，核心空时 `mx = 0` ⇒ 全部缺口 0 ⇒ `sum = 0` ⇒ 永不配置。加上这条后空核心退化为「按权重分台」。

另外每圈 `printflush` 汇报 `npad / core / sum / vol`（`--verbose`），并把 `Logic/群控接收台-诊断.mlog` 作为独立探针：打印链接表（`@type` / `@efficiency` / `@totalItems` / `@itemCapacity`）、能否 `ubind` 到单位、能否 `ulocate` 到核心。

## 11. v2.2：着陆台「未受控制」的真因与修正

**用户实机诊断输出**（`Logic/群控接收台-诊断.mlog`）：

```
links=9
L0 message      eff=0 items=0 cap=0
L1..L8 landing-pad eff=0 items=0 cap=100
unit=flare      core=core-acropolis x=352.5
```

⇒ 8 台全部 `@efficiency=0` ⇒ `npad=0` ⇒ 一台都没被配置。**唯一的直接原因就是资格闸门把台全过滤掉了。**

`@efficiency` 的语义（`LandingPad.java:86-107`）：

```java
init(){ consume(new ConsumeLiquid(consumeLiquid, consumeLiquidAmount){
    public float efficiency(Building build){
        return build.liquids.get(consumeLiquid) >= amount ? 1f : 0f;
    } }).update(false); super.init(); }
```

即 eff=1 **当且仅当**该台储水 ≥ 100。没接水管的台恒为 0 —— 而一张刚建好的台子通常就是没水的。

两处改动（`tools/mlogc_landing2.py`）：

1. **资格闸门默认只判空仓**（L0 与 pass3 复检两处同步）：`sensor tot b @totalItems` / `jump c2|p3a greaterThan tot 0` —— 满仓的台本来就会静默丢单（`LandingPad.java:332-334`），跳过它是对的；没水的台则照样下发 config，等水通了立刻就能接货。
   `--need-water` 可恢复旧行为（追加 `sensor eff b @efficiency` / `jump … lessThan eff 1`），仅在「宁可空着也不配」时才需要。
2. **核心有效性判据放宽**：`jump p1x greaterThanEq cap 4000` → `jump p1x notEqual cap null`。用户的核心是 mod 的 `core-acropolis`，容量未知；原先 `≥4000` 会把 mod 核心判成「无效」，于是每圈都退到借单位 ulocate（白烧 9 条）。链接扫描的 `--core-cap` 默认值仍是 4000（那一步只是用来把核心从容器里挑出来）。

**验证**（mlogsim v160.7，1×1 sorter 假台 ×9，1200 tick）：`npad=9`、`mx=400`、`sum=101546343`、`vol=13317246`，下发 graphite ×1 / thorium ×6 / plastanium ×1 ⇒ 整条流水线完好。

**模拟器工艺坑（不是逻辑 bug）**：用 `--probe-pads` 造出真实 3×3 着陆台后，程序里**所有** `read w @this <名字>` 一律返回 null，但 `sensor tt @this @type` 仍返回 `micro-processor`、`getlink` 也正常；同一位置换 1×1 sorter / container / router、3×3 silicon-arc-furnace / overdrive-dome 都正常，唯独 landing-pad 触发。

- 链路：`ReadI.run`（LExecutor.java:624-632）先判 `read.readable(exec)`，不可读就 `output.setobj(null)`；`LogicBuild.readable`（LogicBlock.java:601-604）= `isValid() && (exec.privileged || (this.team == exec.team && !this.block.privileged))`；`BuildingComp.isValid()`（BuildingComp.java:2036-2038）= `tile.build == self() && !dead()`。
- 即：模拟器把 3×3 台子摆到压住处理器格的位置，处理器与 `tile.build` 脱钩（对象还在、仍被 `updateTile` 驱动），于是 @this 读写全部静默返回 null。
- 根因有两个，都已修（`Tile.setBlock` 的居中偏移 + `LandingPad.accessible()` 闸门），现在 `mlogsim.py --pads N` 能端到端跑真台，见 **§16**。

**实机验证点**：消息块上打印的 `npad` 应从 0 变成 8。

**两条测量教训**：

- mlogsim 跑满一圈要 ≥1200 tick。先前 400 tick 看到的 `sum=0` / config 全 null 是假象（pass2 还没跑完）。
- 往 .labels.mlog 里手工插语句再 `aigenerated post` 转数字时，插入的 jump 会被重编号成「跳到下一行」而失效（`jump 100 notEqual w null` 紧邻第 100 行）。做探针必须改生成器，不要文本拼接。

## 12. v3：精简版与信息板（原理）

**结构**（147 条语句，check 0/0）：

```
权重表(12 行) → init → wait 周期
  ├─ 信息板：draw clear / 标题 / 图标循环 / drawflush display1
  ├─ 库存没变？ sensor tmp.tot core @totalItems ; 等于 last 就回 wait
  └─ 变了才重算：数台 npad → 找核心 → pass1 求 mx → pass2 求 sum
                 → pass3 累计切片下发 → 缓存 last
```

### 12.1 为什么这么算

1. **打分量的是「缺口」，不是「存量」**。`d_i = (w_i · (mx − amt_i))^e`，`mx` 是该核心里单品最大库存。核心越缺某物品，`mx − amt` 越大，分到的台越多；`w_i` 是你给的手动权重（钛 5、硅 5、钍 2、铜铅 0.5…），权重为 0（不写）的物品根本不参与。`e=@e` 把差距拉开，避免「每种都分一点」导致谁都喂不饱。
2. **累计切片 = 一次算完的最大余数法**。`sum = Σd`，`vol = sum/npad` 是「一台该承担多少分」。按物品 id 顺序累加 `pf += d_i`，每跨过一份 `vol` 就多发一台。等价于 `k_i ≈ npad·d_i/sum`，但不需要排序、不需要除法取整，浮点余量自动 carry 到下一个物品。
3. **同物品多台的轮转不归逻辑管**。引擎里 `LandingPad.updateTimers` 对每个物品维护一条串行队列（`waiting`），每帧只服务 priority 最小的一台，落地后 `first↔head` 交换（`LandingPad.java:183-200`）⇒ 同物品的 k 台天然轮流接货。**逻辑唯一要决定的就是 k_i**，这就是整个算法的落点。
4. **满仓的台照样计入 npad**。`LandingPad.java:332-334` 的排队条件里有 `items.total()==0`，满仓的台本来就不会抢着陆槽位，所以提前给它下发 config 是零副作用的；把它排除在外，反而会让这台永远改不了物品（v2.2 的教训）。
5. **库存不变就整圈跳过**。分配结果只由「核心库存 + 链接里的台子」决定，跟台子当前状态无关；所以 `sensor tmp.tot core @totalItems` 与上圈相同就 `jump main`。稳态一圈只有十几条指令，真正重算只在物品进出核心后发生一次。

### 12.2 信息板怎么画

- 画在链接名为 `display1` 的逻辑显示屏上（`drawflush display1`；没链接就静默丢弃，不会报错）。
- 尺寸自适应：`sensor tmp.ds display1 @displayWidth`，读不到就按 64。8 列网格，格子 = `ds/8`。
- 每个图标是那台台子当前的 `@config`（`sensor cf b @config`），用 `draw image` 直接画物品贴图 ⇒ 一眼看出「哪台在等什么货」。
- 标题用 `print` 写进 textBuffer，再由 `draw print` 渲染（`LExecutor.java:943-993`：`draw print` 消费的就是 `print` 攒的缓冲区，画完自动清空）。字体是 ASCII only（`Fonts.java:97`），所以板上文字只能用英文/数字。
- 颜色：底色 `0.02 0.03 0.05`，标题琥珀 `255 200 90`。

### 12.3 代价

| 场景 | 指令数 | micro(2 ipt) | logic(8 ipt) |
|---|---|---|---|
| 稳态（库存没变） | ~15 + UI | UI 部分约 `12×链接数` 条 | 同左 |
| 一次完整重算（20 物品 / 9 台） | ~520 | 4.3 s | 1.1 s |

⇒ 周期给 10 s（micro）/ 4 s（logic）都很宽裕；想更快只缩短周期，重算频率由库存变化自然决定。

## 13. v3.1：信息板改成 message 文本板

**改了什么**：UI 从 `draw` + `drawflush display1` 改成 `print` + `printflush message1`。语句数 147 → **130**。

板面长这样（重算时才刷新）：

```
[#ffd166]RECEIVER[]  pads=9  core=core-shard
  titanium x6
  thorium x1
  silicon x1
```

- 第一行：台数 + 当前核心名（`print core` 打印建筑时走 `PrintI.toString` → `build.block.name`，LExecutor.java:1080）。
- 以后每行一个**分到了台子**的物品，格式 `名字 x 台数`；没分到的不打印（`cnt==0` 直接跳过）。
- 只在真正重算的那一圈写盘；库存没变的那几圈连 `printflush` 都不执行，板子保持不动。
- 文本上限 400 字符（`MessageBlock.java:29 maxTextLength=400`，与 `LExecutor.java:46 maxTextBuffer` 一致），一行物品约 18 字符 ⇒ 12 个物品 + 表头远未触顶。
- `printflush` 会清空 textBuffer（`LExecutor.java:1178`），所以不会跨圈叠加；失败早退路径（`r1`）也会 flush 一次，避免残句堆积。
- 颜色用游戏文本标记 `[#ffd166]…[]`，板子渲染时支持；逻辑字体只影响 `draw print`，message 板用的是 UI 字体。
- **message 板只能写字，画不了物品图标**。想要图标版就加 `--hud`，那条路径仍是 `draw image` 到 `display1`（两套可并存）。
- 板子链接名默认 `message1`，要换用 `--board-target`。

## 14. v3.3：信息板用 printchar 画图标 + format 压条数

**`printchar <内容>` 就是图标打印机**：`PrintCharI` 对 `UnlockableContent` 追加 `(char)cont.emojiChar()`（LExecutor.java:1101-1104），传数字才走码点分支，传别的对象静默忽略。所以 `printchar copper` 画铜锭、`printchar @landing-pad` 画着陆台。

**`format <值>` 一次只填一个占位**：它扫描缓冲区里**编号最小**的 `{0}..{9}` 并替换（LExecutor.java:1123-1139）——占位必须先被 `print` 写进缓冲。值是内容对象时走 `PrintI.toString`（:1143），**出名字不出图标**，所以图标不能靠 format，只能 printchar。

两者拼起来，一行只要 3 条：

```
printchar it            # 物品图标
print "  x{0}\n"        # 文本 + 占位
format cnt              # 填数量
```

表头同样 3 条（`printchar <pad>` + 带 `{0}` 的标题 + `format npad`）。整块板子从 7 + 5k 条降到 **3 + 3k** 条；程序总条数 142 → **126**。

板面效果：

```
[着陆台图标]  RECEIVER  pads=9
  [钛图标]  x6
  [钍图标]  x1
  [硅图标]  x1
```

⚠ `format` 需要 build ≥ 147（检查器会报 version gate），v160.7 没问题。

## 15. v4：把我那一半补回去 —— 供给占空比反馈

v3 只搬了「缺口打分 + 累计切片」，我先前承诺的另一半 `k_i ∝ 1/T_i`（按供给分配台数）当时被砍了。原因是它的输入不可读：着陆台只暴露 `totalItems / efficiency / config`，`cooldown` 与 `importCooldownTimers` 都不在 LAccess 表里（LandingPad.java:86-107、:160-181）。

**能测的替代量是占空比**：台子落地瞬间 `items.set(arriving, itemCapacity)`（:311），随后 1 件/帧 dump 出去（BuildingComp.java:1059-1067）。所以采样到 `@totalItems > 0` 的概率 ≈ 落地频率 × 排空时长。健康台约 100 件 / 1.67 s 排空、20 s 一个周期 ⇒ 占空比 ~8%；供不上的台恒为 0。

实现（tools/mlogc_landing4.py，`--supply`）：

```
pass2/3 打分：d = (w·Δ)^e · (u + c)        # u = 上周期占空比，c = 0.02 兜底
pass3 尾部： smp = Σ(pad.@totalItems) / (100·k)   # 本轮实测
            u  = u + lr·(smp − u)               # EMA，lr = 0.25
            write u @this <物品名>              # 20 个名字在末尾 draw 里声明
```

- 供不上的物品 `u→0`，份额被压到 `c/(u+c)` ≈ 1/5，把台子让给真的在到货的物品；`c` 保证它不会彻底归零（否则永远没有台子去探测它的供给恢复）。
- 物品名当 `@this` 槽位需要先声明：末尾放 4 条 `draw triangle`（不可达，零运行时成本，checker 报 5 条 unreachable 警告属预期）。
- 成本：代码 +26 条（128 → 154），但**每圈执行**多约 300 条（20 物品 × pass2 5 条 + pass3 10 条）⇒ micro 版周期要放到 10 s 以上，logic 版 4 s 无压力。
- ⚠ 均匀因子会让浮点边界漂一台：模拟器里所有台都不着陆，`u` 恒 0、全体乘 0.02，分配从「钛 6 / 钍 1 / 硅 1」变成「钛 7 / 硅 1」。真机上 `u` 各不相同，不会出现这种整体平移。
- ~~模拟器**验不了**真实供给反馈（假台不着陆，`smp` 恒 0 ⇒ 退化成 v3 的纯需求分配）~~ → **已可验证**：`mlogsim.py --pads N` 能放真着陆台并真实落地，见 §16。

## 16. 模拟器支持真着陆台（`--pads N`）

v1–v5 的分配结果此前只能在 sorter 假台上验：假台不落地、`@totalItems` 恒 0，供给反馈 `u` 退化成常量。现在 `tools/mlogsim.py --pads N` 会放 `N` 台真 4×4 `landing-pad`，接成 link 0..N-1（名字 `pad1..padN`），落地、耗水、`control config` 全部走引擎。

```
python tools/mlogsim.py Logic/落子-v5.2-micro8.mlog --ticks 1800 --pads 9 --pad-drain 2 --units flare:1 --core-items copper:400,silicon:200,lead:300,titanium:150 --world 96 --base 30,30
```

每台输出一行状态：

```
PAD pad3 (18,26) cfg=titanium arriving=titanium cd=1.00 items=0 water=3000 eff=1 landings=5
```

`--json` 里是 `rec["pads"]`（`name/x/y/config/arriving/cooldown/items/water/efficiency/landings`）。默认每 tick 把水箱补满；`--no-pad-refill` 才能看到「两次落地后水空、eff=0 永久停摆」的真实供给约束；`--pad-drain N` 每 tick 抽 N 件货，台子不空仓就永不再落。

### 16.1 两个不修就调不通的坑（`--pads` 已自动处理）

1. **多格建筑是按中心对齐放置的**：`Tile.setBlock` 里 `int offset = -(block.size - 1) / 2;`（Tile.java:255-288），4×4 台摆 origin 会覆盖处理器格 ⇒ 处理器 `BuildingComp.isValid()`（`tile.build == self() && !dead()`）变假 ⇒ 程序里所有 `read x @this <名字>` 恒 null。而 `sensor @this @type` 仍返回 `micro-processor`（@this 是 `exec.build` 的对象引用，不查 tile），很容易误判成「变量没声明」。模拟器现在按居中矩形做重叠检测。
2. **`LandingPad.config()` 在沙盒里被 `accessible()` 静默拒绝**：`config(Item.class, ...)` 第一句就是 `if(!build.accessible() || ...) return;`（LandingPad.java:73-77），而 `accessible()` 要求 editor / `allowEditWorldProcessors` / campaign / infiniteResources 之一（:160-163）。非战役世界全为假 ⇒ `control config` 不报错、cfg 永远 null。`--pads` 会打开 `rules.allowEditWorldProcessors`（唯一不改变消耗语义的分支）。

### 16.2 v160.7 的真实节奏（取代 v159.3 的 20 s 模型）

- 实测反射：`size=4`、`itemCapacity=100`、`liquidCapacity=3000`、`consumeLiquidAmount=1500`、`cooldownTime=150`、`arrivalDuration=150` ⇒ 单台周期 **5 s**。
- **每次落地喝 1500 水**，满箱 3000 只够两次。再落的条件必须同时满足：水 ≥ 1500、库存 = 0。
- `LandingPadBuild` 在 v160.7 **没有** `importCooldownTimers` / `waiting` / `importRate` 字段（`getDeclaredField("waiting")` 抛 NoSuchFieldException），只有 `config/priority/cooldown/arriving/arrivingTimer/liquidRemoved`。⇒ v159.3 文档里「进口率决定 20 s 冷却、每物品全局串行 + first↔head 轮转」在 v160.7 看不到对应实现，实测表现就是「空仓 + 有水 ⇒ 每 5 s 落一次」。
- 对算法的含义：到货频率由**你有没有把货拉走**决定（`--pad-drain`），不是引擎限额。所以供给反馈 `u` 量的是下游消化能力，正是 `k_i ∝ 1/T_i` 想要的量。

### 16.3 实测（9 台真台 + 落子 v5.2-micro8，1800 tick = 30 s）

| 指标 | 值 |
|---|---|
| npad | 9 |
| core | `Building#210[91,91]:core-shard` |
| mx / sum / cu | 400 / 3107.115 / 3107.115（末尾累计 = sum ⇒ 配额和恰为 9，无空台） |
| 分配 | metaglass×1 / graphite×2 / titanium×3 / thorium×3 |
| 每台 landings | 5（30 s 内，即 5 s 一台的满负荷） |

与旧 sorter 假台（titanium×7 + thorium×2）的差异全部来自 `u>0` 现在真的在变 ⇒ **供给反馈第一次可测**，不再退化。

### 16.4 链接范围是硬约束

| 处理器 | range | 能连到 4×4 台的距离 |
|---|---|---|
| micro-processor | `8*10 = 80wu`（LogicBlock.java:49） | 80+16 = 96wu = **12 格** |
| logic-processor | `8*22 = 176wu`（Blocks.java:6857） | 192wu = 24 格 |
| hyper-processor | `8*42 = 336wu`（Blocks.java:6868） | 352wu = 44 格 |

`validLink` = `other.within(this, range + other.block.size*tilesize/2f)`（LogicBlock.java:736），4×4 台比 1×1 建筑多吃 2 格余量。micro 的 12 格半径内可用面积约 450 格，9 台 4×4（144 格）放得下，30 台（480 格）放不下 ⇒ 「logic 控 30 台」要求台子铺开（24 格半径约 1800 格，可行）或用世界处理器。
