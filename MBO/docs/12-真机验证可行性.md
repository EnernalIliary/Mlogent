## 0. 一句话结论

**部分可行 —— 但已经是"足够开工"的部分可行。**
用一段 python 驱动官方服务端 + Rhino，可以把**一整张真实 .msch 蓝图**导入真实世界、让服务端自己的 60 Hz 循环真推进、并**权威读回**"建筑数、每个生产方块的 efficiency/progress、电力图发电量/需求量/满足率、方块与核心的物品与液体库存、方块位置"。
~~没有打通的一环只有一个：产物总量的端到端闭合计数~~ → **已在 §补测 打通**（产物汇入 container/vault/core 后按 `build.items` 差分：稳态 0.684/s vs 理论 0.667/s，**+2.6%**；`progress` 回绕计数与之一致）。同一次补测还推翻了两处早期结论：**多格锚点是中心格**（§1.5 已修正）、**电力不会自动连线**（§补测 A）。

所以 MBO 的验证层可以按 **"真机闭环（状态口径 + 总量口径）"** 设计；但生成器必须显式写电力 config、按中心格算偏移，否则真机侧会得到孤岛电力网/被覆盖的邻块。

## 1. 实测证据（全部为本机实测，非估算）

### 1.1 启动与成本

| 项 | 实测值 | 备注 |
|---|---|---|
| java → `Server loaded.` | **1.77 / 1.95 / 2.05 / 2.07 / 2.16 / 2.29 s**（6 次） | 冷/热差不多，JVM 启动很便宜 |
| `Vars.world.loadGenerator(128,128,...)` → 世界可用 | **0.43 / 0.44 / 0.52 s** | 含铺地板 |
| 整张 .msch 导入（`Schematics.readBase64` + `place`） | < 0.1 s | 与蓝图大小无关（23 tiles 也瞬间） |
| 真实推进 tick 速率 | **60.1 ~ 60.3 tick/s**（121 tick/2.00 s；610/10.12 s；1807.4/30.07 s；609.3/10.12 s） | 服务端自己的循环，不用手写 tick 循环 |
| 1800 tick（30 游戏秒）一次完整实验 | **~33 s**（2.0 s 启动 + 0.5 s 造世界 + 30.1 s 推进） | 见 §5 成本 |
| JVM 常驻内存（1800 tick 跑动中） | **working set ≈ 150 MB，private ≈ 218 MB**（12 次采样中稳定段） | 并发上限很宽 |

**结论：单次实验 ~33 s，主要成本是"真实时间"本身，不是启动。**

### 1.2 世界会真推进（这条是整个方案的地基）

```
SNAP  t0_0  125.31  ...  items=coal=3
SNAP  tN_0  734.61  ...  items=coal=60
```
- 不需要玩家、不需要 `--host`、不需要 .msav：`Vars.state.set(Packages.mindustry.core.GameState.State.playing)` 之后 tick 自增，服务端循环会真实更新方块。
- `Vars.state.tick` 是 double，可直接用来算真实经过的 tick 数。
- **不要照抄 `tools/mlogsim.py` 的 `worldTick()`**：它把 `w.power.status` 强制成 1（电力是打桩的），那会毁掉"真实电力"这个验证项。

### 1.3 电力图是真跑的

手搭最小 rig（`power-source`(5,5) + `battery`(6,5) + `illuminator`(7,5)），2 s：
```
BAT_START  stored=0/4000
BAT+2s     stored=4000 sat=1  prod=16537.9 need=0.0496 bal=16666.6
PS=0  BAT=1  IL=1  IL.eff=1
```
- 电池会真充电（`getBatteryStored()` 涨到 4000；注意 **`getBatteryCapacity()` 在这个 jar 上返回 0**，读数只用 stored）。
- 耗电方块 `efficiency=1` 说明拿到了电。
- 整张 `metaglass-2.msch`（3 台耗电 kiln）1800 tick 后：`graph 4: prod=22335.1 need=4.02 sat=1` —— **电力供需数字是引擎算的，不是我们填的**。
- 这意味着 `powerConsumption()/powerProduction()` 这类离线估算可以在真机上被校验：`Graphics.power` 的 `sat`（满足率）就是"这个布局电力够不够"的权威答案。

### 1.4 生产方块的状态是真跑的

单建筑最小 rig（`graphite-press` + 预置 20 煤），2 s（121 tick）：
```
coal 20 → 18   graphite 0 → 1   progress=0.3444   efficiency=1
```
整张 `metaglass-2.msch` 1800 tick 末态：`effLow=0/5`（5 台 kiln 全都不缺料）、`effAvg=1`、`progSum=2.0`。
→ **"缺料/堵死"是可自动判定的**：`efficiency==0` 且 `progress` 不涨 = 停摆；`effLow`（efficiency<0.05 的方块数）就是堵塞/缺料计分板。

### 1.5 多格方块锚点（⚠️ 本节早期结论已被 §补测 C 推翻：锚点是**中心格**）

`W.tile(3,3).setBlock(Vars.content.block("graphite-press"), T)`（2x2）之后：
- 占据 (3,3)(3,4)(4,3)(4,4)；
- `build.tileX(), tileY()` = **3,3**；`build.x, build.y` = 28,28 px；
- 4 个格子 `tile.build != null`。

**早期结论（仅对 2×2 成立）**：传给 `setBlock` 的格子看起来就是左下角。**更正**：`(2-1)//2 = 0` 使 2×2 的中心格恰好等于左下角；3×3 实测传入格是**中心格**，实际 origin = `(x-(size-1)//2, y-(size-1)//2)`（§补测 C 与 `docs/13` §2.2）。

### 1.6 `Tile.setBlock` 之后必须 `Vars.indexer.addIndex(tile)`

`Tile.setBlock` 不更新 BlockIndexer（`Tile.java:208` 注释）。不补 index 的方块：不在 `Groups.build` 里、不参与电力图/物流。本 spike 里 `PLACED indexed=<n>` 就是在补 index。

### 1.7 整张 .msch 可以直接进引擎（关键突破）

`Packages.mindustry.game.Schematics` 在 Rhino 里完全可用：

| API | 签名 | 用途 |

| `Schematics.readBase64(String)` | static → Schematic | 直接把 .msch 文件内容（base64）读成 Schematic |

| `Schematic` 字段 | `width, height, tiles:Seq, tags, labels, mod` | 离线侧和引擎侧同一个对象模型 |
| `Schematic` 方法 | `hasCore() powerConsumption() powerProduction() findCore() name() requirements() save()` | 离线估算与引擎实测可直接对齐 |

**实测导入结果**（全部真导入、真跑）：

## 2. 三个必须知道的坑（都是实测踩出来的）

### 坑 1（致命）：服务端启动后 ~12 s 会用它自己的地图把我们的世界换掉

原始日志：
```
[11-04-2026 20:02:29] [I] Game over! Team crux is victorious with 0 players online on map Unknown.
```
之后 `Vars.state.tick` 会**回退**（实测 757.29 → 17.81），世界变成默认图（`core-foundation@99,99` + 200 copper），我们放的蓝图全没了 —— 而实验"看起来"还在正常跑，只是数字全是别人的。

- 实测命中：**3 次里有 3 次都在 12.1~12.3 s 命中**（第一次蓝图进新 JVM），第 2 张蓝图就没事（已经过了那个时刻）。
- 加重条件无关：`Vars.state.rules.canGameOver=false`、`waves=false` 都拦不住。
- **解法（已验证有效）**：`Server loaded.` 之后先 `--warmup 13`（默认值），等服务器把自己的地图加载完，再 `loadGenerator` 造我们的世界。加了 warmup 之后 `graphite-1` 跑满 609.3 tick 无 wipe。
- **兜底（已实现）**：每 0.3 s 读 `Vars.state.tick`，一旦**回退**就判 `world_wiped=True`，不拿这份数据当结果（`RESULT` 里 `ticks 0.0` + `WIPE` 行），重试一次。

### 坑 2：不能在"正在跑"的世界上放方块

边跑边 `setBlock`（尤其把 `item-void` 换成 `container`）会和物流更新竞争，实测直接把服务端搞崩/触发世界重载。**正解**：放置 + 插桩全在 `Vars.state.set(State.paused)` 下做，做完再 `set(playing)`。已实现（`BP_PREP_JS` 开头就 pause）。

### 坑 3：进程清理必须自己兜，`srv.js("exit")` 不保证干净

- 实测出现过：python 已打完 `JAVA_PROCS_AFTER 0` 之后仍有 java 子进程停留（约 1 min 才退），shutdown 阶段 `pipe` 不排空时会卡。
- 已实现三层清理：Windows **job object（KILL_ON_JOB_CLOSE）** → 发 `exit` → `proc.kill()` + `taskkill /F /T`。
- **每次实验后务必 `Get-Process java` 复核**；批量跑时照 `tools/mlogsim.py` 的 `sweep_orphans` 思路（WMI 查 `CommandLine` 含 `_server160.jar` 且父进程已死的 java.exe 再 `taskkill`）定期扫。

## 4. 产物总量计数（本节为**第一轮**的记录，已由 §补测 B 打通；保留以说明当时的误判路径）

当时的失败现象：

1. 把蓝图里的 `item-void` 换成 `container`（`--instrument`，`SINKS 1 item-void->container`，已补 indexer），跑 1800 tick，**container 始终为空**；
2. 同时 `metaglass` **从未**出现在任何 items 聚合里（`items=copper=100,lead=69,sand=69` 只有输入），而 kiln 的 `efficiency=1`、`progress` 在推进；
3. `graphite-1` 600 tick：`coal 3→60` 累积，但 `graphite` 没出现（单建筑 rig 里同样条件却能出 1 个石墨）。

**当时的推断（现已被 §补测 B 证伪）：输入侧（缺料/堵塞/电力）可信，输出侧绝对计数不可信。** 实际根因是 sink 选错了——`item-void` 会把物品销毁、而 `--instrument` 换成的 container 没被采样到正确路径；换成"产物直连 container 并按 `build.items` 差分"后立刻读到数。**含义：不要把"读不出数"当成"游戏不给数"，先确认产物落点。** 当时的候选原因（按可能性排序）：
- 导入蓝图的传送带"下一个目标"缓存指向了旧建筑，产物被丢进虚空；
- 产物落在没被我聚合到的方块类型（如 `unloader`/`container` 的 `items` 访问路径不同）；
- `progress` 读的是动画进度而非配方进度（需要逐方块 dump 才能确认）。

**下一步（已执行并成功）**：逐方块确认产物落点 → 用"产物直连 container（2×2、itemCap 300）+ 每 tick 记录 `container.items` 差分"实现绝对产量口径，见 §补测 B（`--mode yield`）。

## 5. 给 MBO Validator 层的接口建议

### 5.1 Python API 形状

```python
# MBO/validator/engine.py
RunResult = {
    "ok": bool,            # 世界没被服务端换掉、没崩
    "ticks": float, "wall_s": float,
    "buildings": int,                       # 引擎里真实建筑数（对齐离线 len(tiles)）
    "production": {item: per_s},            # ← 总量口径未闭环，先标 experimental
    "consumption": {item: per_s},
    "eff": {"avg": float, "low": int, "total": int},   # 可靠性/堵塞计分板
    "power": [{"graph": i, "prod": f, "cons": f, "sat": f, "stored": f}],
    "liquids": {liquid: amount},
    "per_building": [{"name","x","y","eff","progress","items","liquids"}],
    "offline_vs_engine": {...},             # 与离线估算的差异（powerCons/powerProd/产量）
    "wiped": bool, "log_tail": [str],
}
run_blueprint(msch_path, ticks=1800, seeds=None, sink="container", timeout=180) -> RunResult
```

建议：
- **一个 JVM 跑多张蓝图**（`--msch a b c`）：启动 2 s 摊薄，实测 JVM 内连跑第 2 张蓝图正常（**第 1 张吃掉 warmup 13 s，第 2 张起不再付**）。
- **`RunResult.offline_vs_engine` 是 MBO 的核心价值**：离线模型（`data/game/blocks.json`）算的产能/耗电 vs 引擎实测，差异要能回归到离线规则表。
- `seeds` 目前无意义：`loadGenerator` 是平地板，没有地形随机性；要做地形相关验证得换成 `loadGenerator` + 自定义 `TileFloor` 或加载 .msav。

### 5.2 成本与并发

**统一口径（避免"2.5 s / 33 s / 46 s"三个数打架）**：每个 JVM 的**首张图必付一次 warmup ~13 s**（避开服务端地图替换），之后同 JVM 内每张图只付"放置 + tick"。

| 场景 | 实测/估算成本 |
|---|---|
| 单图端到端（新 JVM，1800 tick） | **~46 s** = 启动 2 s + warmup 13 s + 放置 0.5 s + 1800/60=30 s + 收尾 0.5 s |
| 同 JVM 内第 2 张起（1800 tick） | ~31 s（不再付 warmup） |
| 冒烟（新 JVM，60 tick） | **~15.5 s**（=13 s warmup + 1 s + 1 s + 余量），**不是 2.5 s** |
| 300 tick（新 JVM） | ~20 s |
| 批量预算公式 | `T ≈ 13 + 0.5 + ticks/60 + 3`（秒/图，单进程串行） |

- JVM 150 MB working set（实测），8 个并发 ≈ 1.2 GB —— 机器上完全可行。
- **并发方式（二选一，不要混写）**：
  - **A. 一图一 JVM**（隔离最稳，`Vars.state` 是全局单例，不能并行）：`ProcessPoolExecutor(max_workers=4~6)`，**每图都付 13 s warmup**。
  - **B. 一 JVM 串行多图**（省 warmup）：每进程跑 3–5 张图后重启（防状态残留），warmup 只付首张。
  - 真人验算时：批量 ≥4 张图 → 用 B；单张调试 → 用 A。
- 失败（`wiped`/`ok=False`）自动重试 1 次；重试要换新 JVM，不要在同一 JVM 里重放（世界已被换掉）。
- 成本敏感场景：冒烟必须 300 tick 起（60 tick 连预热都不够），只有候选集前 N 名才跑 1800 tick。

## 7. 坑与注意（工程清单）

1. **warmup 必须 ≥13 s**，否则 §2 坑 1 会把世界换掉，而且不报错。
2. **一切世界修改都在 paused 下做**；跑起来之后再改 = 崩。
3. **`setBlock` 后必须 `indexer.addIndex`**，否则方块是"幽灵"（不在 Groups.build、不接电力/物流）。
4. **`--ticks` vs `--steps`**：本 spike 只走真实 60 Hz（`--ticks`）。`mlogsim.py` 的 `--steps` 手动循环（`tick++; Time.update(); logicVars.update(); worldTick()`）**不能用于电力验证**，因为 `worldTick()` 里 `w.power.status=1` 是打桩；而且没有做过与真实循环的等价性对照。**所以 1800 tick 就锁死 30 s 真实时间**，别再想"快进 10 倍"除非另做等价性验证。
5. **core 库存读取**：`core.items` 是 `ItemModule`（`get(Item)`/`total()`）；放置 `core-shard` 后它自带 starter items（实测 200 copper），做净产出差分时要先记基线。
6. **`getBatteryCapacity()` 在 v160 服务端返回 0**，只有 `getBatteryStored()` 可信。
7. **日志解析**：`js` 的返回值只从含 `[none/base.js]:` 的行里取；多行脚本会被拼成一行发（控制台一行一条命令），所以脚本里别用换行分隔语句之外的东西。
8. **进程泄漏**：job object + `exit` + taskkill 三层；每次跑完 `Get-Process java` 复核，批量跑前 `sweep_orphans`。
9. **JVM 内存**：默认就够（150 MB）；如遇寄生 OOM 可给 `-Xmx512m`，但没必要。
10. **不要动 tools/**：本 spike 只 import `tools/msch.py` 的 `parse_file`；`out/` 下只写 `_probe/`。

## 8. 未验证项（下一轮）

- 产物总量闭环（§4，最高优先级）；
- 逻辑块（processor）在引擎内是否编译执行、能否读 `@counter`/变量；
- 快进 tick 的等价性（若要做，必须先在"电力 rig"上对照真实 60 Hz 的数字）；
- `loadGenerator` 后残留 ~17 个非 air 方块（bbox 出现 7,7）的来源；对实验无害但会让 `indexed` 计数偏大；
- .msav 场景加载路线（本轮未用，`out/scenes/*.msav` 可用 `Vars.world.loadMap` 试）。

### A-4 一句话结论

**placement 本身不产生任何自动连线**（`Schematics.place()` 只做 `tile.setBlock()` + `tile.build.configureAny(st.config)`，不调 `Building.placed()`；而 `PowerNodeBuild.placed()` 才是 autolink 的地方，且只在 `links.size==0` 时触发）。**只要生成器把 power-node 的 links 写进 array config，导入后连线就成立、`sat=1`。**
→ **生成蓝图必须写 power-node 的 array config（相对偏移的 links 数组）**；离线模型也要按"config 里有点才算连"来建网，否则离线算出的电力网会与引擎不一致（引擎是孤岛，离线以为连通）。

## 补 C. 对 12 号原文的修正

1. **原文 §0 / §4「产物绝对总量不可信、只有输入侧可信」→ 修正为：绝对产量可读，已验证到 +2.6%（稳态）。**
   原文失败的原因不是引擎读不出来，而是：那批语料蓝图把产出接进 `item-void`（**故意销毁**，测试台写法），加上当时在已跑起来的世界上做 `item-void → container` 改写（竞态）。改成"产物进容器 + 暂停期插桩"后即闭合。

2. **原文 §1.5「传入格 = 原点（左下），不需要 `x-(size-1)/2` 偏移」→ 修正为：传入格是"中心格"，`origin = (x - (size-1)//2, y - (size-1)//2)`。**
3. **读数口径**：`Groups.build` 不可信（实测 21 tile → 5 build），一切计数改扫 `Vars.world.tile`；详见 `docs/13-生成器可信度测试.md` §2.6。
4. **电力必须写成"节点紧贴 consumer + 节点间显式 config"**：consumer 离节点 3 格（即使 node range 覆盖）也不进网，`eff=0`（`docs/13` §2.4）。
   实测：3x3 `vault` 传 `(33,20)` 后实际占 **32..34 / 19..21**（TILEDUMP 原样：`32,19=vault 32,20=vault … 34,21=vault`），即向左下偏 1 格；2x2 因 `(2-1)//2 = 0` 恰好看起来像"原点"。
   **这是致命细节**：本轮按"原点"理解时，3x3 vault 直接覆盖掉旁边 2x2 press 的格子，那台 press 的 `build` 变成 `null`（`p2=null`，`groups` 7→4）。生成器放任何 3x3 方块（核心、vault、大型炮台）都必须按中心格算偏移。

3. **原文 §1.3 / §3 里"读 `graph.production / graph.consumption`"→ 修正为：该 jar 的 `PowerGraph` 上这些名字不是字段（实测 `prod=undefined`）。可读的是 `satisfaction`、`powerBalance`、`lastPowerProduced`、`lastPowerNeeded`、`lastPowerStored`、`lastScaledPowerIn/Out`、`lastCapacity`，以及 `graph.all.size`（图上节点数）。**

4. **新增工具坑（原文 §6/§7 未提）**：`srv.js()` **每次调用只可靠返回一行** `[none/base.js]:` 输出；多行 `print` 会丢行、且后续调用可能读到上一次的尾巴。本轮第一版正因一条 print 打 4 个方块 → 只拿回 1 行。**所有读数必须压成一行 tab 分隔输出**——这是写 MBO 引擎桥的第一条硬规矩。
