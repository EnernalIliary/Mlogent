# M07 Units and logic control

## In one sentence

`ubind` binds a unit to `@unit`, after which every `ucontrol` acts on `@unit`; only ubind can write `@unit` (`set @unit` is silently dropped), and it becomes null by itself when the unit dies.

## Rules / formulas

### 1. The @unit lifecycle

| Event | @unit state | Basis |
|---|---|---|
| initial | null | nothing bound |
| `ubind <unit type>` | points at an available unit of that type | LExecutor.java:193 `exec.unit.setconst(...)` |
| the target dies / is destroyed | **null** (the object slot is cleared) | the engine nulls it when the unit becomes invalid |
| `ubind <unit type>` with **no** unit of that type on the map | **null** (the old unit is not kept, and no error) | assertion table L2-133 |
| `ucontrol unbind` | null | an explicit unbind |
| `set @unit x` | **unchanged** | @unit is putConst (LAssembler.java:27), so SetI drops it |

⇒ To test "is a unit bound", use `jump ... equal @unit null`, not `equal @unit 0` (null and 0 are equal under num(), which misjudges).

### 2. Full parameter table for the 21 ucontrol subcommands (the LUnitControl enum)

Source: `Mindustry-Source/core/src/mindustry/logic/LUnitControl.java` (`:4-24` declares **21 entries**; the order is the declaration order, and the `params` array is the text parameter table). Text format: `ucontrol <subcommand> <p1> <p2> <p3> <p4> <p5>` — token 0 is `ucontrol`, token 1 is the subcommand, and **the parameters start at token 2** (p1..p5 in the source).

| # | Subcommand | Parameters (source declaration order) | Parameter types | Semantics | Common mistake |
|---|---|---|---|---|---|
| 1 | idle | — | — | the AI stands by without clearing the build/mine state | thinking it equals stop |
| 2 | stop | — | — | stops movement and clears `mineTile` / the build plan | thinking it unbinds @unit (use 21) |
| 3 | move | x y | tile numbers | move in a straight line to (x,y) | writing pixel coordinates (×8 internally) |
| 4 | approach | x y radius | tile numbers ×3 | walk until within radius of (x,y) | omitting radius (defaults to 0, degrading to move) |
| 5 | pathfind | x y | tile numbers | path around obstacles to (x,y) | using it as move ⇒ straight into a wall |
| 6 | autoPathfind | — | — | pathfind automatically to the enemy core | spinning on a map with no enemy core |
| 7 | boost | enable | boolean | toggle unit boost | — |
| 8 | target | x y shoot | tile numbers + boolean | aim at a coordinate; shoot decides whether to fire | omitting p3 ⇒ aim only, no fire |
| 9 | targetp | unit shoot | unit object + boolean | aim at a specific unit | writing coordinates into p1 (should be a unit) |
| 10 | itemDrop | to amount | building object + number | unload into a block | coordinates in p1; to=@air empties the held items |
| 11 | itemTake | from item amount | building object + item + number | take items from a block | a plain variable for item (should be a content constant such as `@copper`) |
| 12 | payDrop | — | — | unload the payload | a non-payload unit does nothing |
| 13 | payTake | takeUnits | boolean | true = take units, false = take buildings | thinking the parameter is a count |
| 14 | payEnter | — | — | enter a payload block | — |
| 15 | mine | x y | tile numbers | mine | on an ore-free tile ⇒ silently mines nothing |
| 16 | flag | value | number | writes `unit.flag` | confusing it with a block's flag |
| 17 | build | x y block rotation config | tile×2 + block + number + config | build; rotation is taken `mod 4` | omitting the config slot; limited by the logicUnitBuild rule |
| 18 | deconstruct | x y | tile numbers | deconstruct | limited by the logicUnitDeconstruct rule |
| 19 | getBlock | x y type building floor | **2 inputs + 3 outputs** | read blocks near the unit | writing the output variables into p1/p2 |
| 20 | within | x y radius result | **3 inputs + 1 output** | whether it is inside the circle, writes 1/0 | writing the output slot into p1..p3 |
| 21 | unbind | — | — | `unit.resetController()` to unbind | after unbinding @unit=null, so ubind again |

**Coordinate convention (the most common mistake)**: `LExecutor.java:352` does `x1 = World.unconv(p1.numf())`, `y1 = World.unconv(p2.numf())`, `d1 = World.unconv(p3.numf())`, and `World.unconv` is **tile → world (×8)** (`core/World.java:170-172`) ⇒ **x / y / radius are all written in tiles**; writing pixels is off by 8×. The same holds for `target`/`build`/`deconstruct`/`getBlock`/`within`.

**Preconditions**: a non-world processor requires `state.rules.logicUnitControl` (LExecutor.java:344); `build`/`deconstruct` additionally require `logicUnitBuild` (:445) / `logicUnitDeconstruct` (:470); a `privileged` world processor passes straight through.

Machine-readable version of the 21 entries: `06-mlog/enums.json#enums.LUnitControl`; the per-entry `params` arrays live in `06-mlog/instructions.json`.

### 3. Output-carrying subcommands (easy to get wrong)

- `ucontrol getBlock x y type building floor`: slots **4/5/6** are outputs (type/building/floor), not inputs.
- `ucontrol within x y radius result`: slot **5** is the output (a boolean result) and slot 4 must be left at 0.
- The source **unconditionally** converts p1,p2,p3 to numbers for every subcommand (LExecutor.java:352), so reading an "unused slot" is harmless, but an output variable written into p1..p3 gets overwritten.

### 4. ulocate: 4 LLocate values + four outputs

`ulocate <locate> <flag> <enemy> <ore> <outX> <outY> <outFound> <outBuild>` (8 params). The `LLocate` enum (`logic/LLocate.java`:3-7): **ore / building / spawn / damaged**.

| locate | Inputs used | What it finds | Source |
|---|---|---|---|
| ore | the 4th param ore (an item constant) | the nearest tile of that ore to @unit | LExecutor.java:247-251 |
| building | flag (BlockFlag) + the enemy boolean | the nearest block with that flag (enemy=true finds enemy ones) | LExecutor.java:252-256 |
| spawn | — | the nearest enemy spawn point | LExecutor.java:257-259 |
| damaged | — | the nearest friendly damaged building | LExecutor.java:260-264 |

Output semantics (easy to get wrong):

- `outX`/`outY` are written as **tile coordinates**: `World.conv(...)` (world→tile, ÷8, LExecutor.java:270-271).
- On a miss it **only writes outFound=0**; `outX`/`outY`/`outBuild` keep their old values (:273-276) ⇒ test existence through outFound alone.
- `outBuild` is written only when "the building is within range or belongs to your side", otherwise it is nulled (:278-284).
- Results are cached: while `ai.checkTargetTimer(this)` has not expired it replays the cache (:242, :285-290), so the output lags; do not treat it as a per-tick live value.
- It depends on `@unit`: with nothing bound or the unit invalid, the whole instruction does nothing (:237 tests `unitObj instanceof Unit && ai != null`), and a non-world processor also needs `logicUnitControl` (:232).

### 5. radar / uradar: 8 targets, 5 sorts, dead slots

`RadarTarget` (`logic/RadarTarget.java`:6-14) has **8 values**, each carrying a filter lambda:

| target | Filter condition (source) |
|---|---|
| any | always true |
| enemy | `team != other.team && other.team != Team.derelict` (**excludes neutral derelicts**) |
| ally | `team == other.team` |
| player | `other.isPlayer()` |
| attacker | `other.canShoot()` |
| flying | `other.isFlying()` |
| boss | `other.isBoss()` |
| ground | `other.isGrounded()` |

`RadarSort` (`logic/RadarSort.java`:6-11) has **5 values**, the sort keys:

| sort | Sort key (source) |
|---|---|
| distance | `-pos.dst2(other)` (negative **squared** distance, not dst) |
| health | `other.health()` |
| shield | `other.shield()` |
| armor | `other.armor()` |
| maxHealth | `other.maxHealth()` |

Text format and dead slots:

| Instruction | Parameters (positions of the 8 tokens) | Note |
|---|---|---|
| radar | `radar <t1> <t2> <t3> <sort> <from> <order> <output>` | from = the name of the building the processor links to |
| uradar | `uradar <t1> <t2> <t3> <sort> <0> <order> <output>` | **the 5th parameter is a dead slot**: `UnitRadarStatement` hardcodes `radar="0"` and `buildFrom()==false` (LStatements.java:1171-1186), and the source uses `@unit` directly, so whatever you write in that slot has no effect |

- The three targets are not ANDed: the source only checks whether the three slots mention enemy / ally to decide the scan scope (`enemies`/`allies`, LExecutor.java:765-766).
- `order` is a **boolean direction**, not a count: `sortDir = sortOrder.bool() ? 1 : -1` (:752); the distance key is negated ⇒ `order=true` picks the nearest.
- There is exactly one output object; a miss writes null (after :800).
- Results are cached for 30 tick (buildings `timer.get(30f)`, LExecutor.java:763; units use `ai.checkTargetTimer`) ⇒ repeating the call inside the cache window changes nothing, so it is no per-tick precise detection. [src: LExecutor.java:763]
- radar's `<from>` building must be Ranged and on the same team; for privileged blocks it must also be privileged (:755-756).

## Measured facts and counter-examples

- ✅【E】`op select` is silently replaced by a noop (L1-25), so "choose between two units with select" does not work in v160.7. [measured: assertion table (docs/断言表.md)]
- ✅【E】@velX/@velY do not exist (L2-24); read unit speed through @velocityX/@velocityY.
- Counter-example (a boundary that does not hold): **"one ubind holds forever" does not hold**. When the unit dies @unit becomes null and every later ucontrol turns into a no-op; the correct pattern is to test `@unit == null` each loop and ubind again.
- 【U】The precise conditions for losing control (another processor binding it away, a player taking the unit over) are unverified; they need an experiment with two processors fighting over one unit.

## Common misconceptions

1. "set @unit can switch units." — it is silently dropped; only ubind works.
2. "ucontrol reads only the slots it uses." — p1..p3 are evaluated unconditionally.
3. "getBlock's outputs are the last two slots." — they are slots 4/5/6, three outputs.
4. "A unit flag and a block flag are the same thing." — they are not; the block side is the BlockFlag enum, the unit side a numeric flag.
