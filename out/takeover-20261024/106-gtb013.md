# Grief to Ban 0.1.3：地图编辑器卡顿的真正原因（每秒 2.5 万次引擎异常）

> 用户 m10163：「启用这个插件之后地图编辑器进入加载时间很长，而且长时间未响应，排查一下原因。」
> 用户 m10300：「造成卡顿的是Grief to Ban」——随后确认就是本模组，下面是实测取证与修改。

## 1. 取证

### 1.1 症状与现场
- 编辑器打开慢、操作长时间不响应；当时游戏只加载 MindustryX / mlog-auxiliary / patch-editor / camera-unbind，**Grief to Ban 也在列表里**（用户随后确认）。
- 该地图 `Groups.build.size()` 约 **8311**（日志 beat 行 `builds=137` 是当时另一张图，编辑器那张是 8311）。
- 现场日志（数据目录 `gtb-debug.log`）里没有任何异常行 —— 因为异常被 `catch` 吞成 `null`，这就是它一直没被发现的原因。

### 1.2 根因
`GriefToBan/scripts/main.js` 的 `seqGet(seq, i)` 先调 `seq.get(i)`，而 v160 的
`mindustry.entities.EntityGroup` **没有 `get(int)`**：

```
Mindustry-Source/core/src/mindustry/entities/EntityGroup.java
  index(int) :231     size() :235     each(Cons) :149      // 没有 get(int)，也没有 public items 字段
```

于是**每一个方块**都要先抛一次 Rhino TypeError（`Cannot find function get in object
[Building#210[0,0]:micro-processor]`），再被 `catch` 吞掉、退回 `index(i)`。
旧代码每秒跑三遍全图扫描（`scanReactors` / `scanGenerators` / `scanVirusQuick`），
三遍都在同一个 tick 里 ⇒ **8311 × 3 ≈ 24933 次异常/秒**。

### 1.3 实测（真 v160.7 Rhino：`out/jre21` + `out/_server160.jar`，无头服务端）
每段 8000 次 × 3 轮取 min × 6 个独立 JVM 取中位（task-10，mod-dev；产物
[out/_seqcost_probe.py](out/_seqcost_probe.py)、[out/_seqcost.log](out/_seqcost.log)）：

| 段 | 8000 次 | 单次 |
|---|---|---|
| `try{G.get(i)}catch`（缺方法，真凶） | 110.7–126.5 ms | **13.8–15.8 µs（中位 14.87）** |
| `try{G.index(i)}catch`（i≥size 抛越界，**不是对照**） | 118.2–126.1 ms | 14.8–15.6 µs |
| `try{G.size()}catch`（普通 interop 对照） | 9.6–13.7 ms | 1.2–1.8 µs |
| `try{G.index(0)}catch`（真·无异常对照） | 2.9–3.2 ms | **0.36–0.46 µs** |

换算：`14.87 µs × 24933 次/s = 370.8 ms/s`（区间 344–394）＝ **37% 墙钟**；
摊到 60 fps 的一帧是 6.2 ms / 16.67 ms，等于每秒烧掉 22 帧的量。三遍连在同一 tick ⇒
真机表现就是**每秒一次约 370 ms 的主线程整段停顿**，与「长时间未响应」完全吻合。

机理（顺手量出来的）：成本不在 `catch` / 栈展开，在 **Rhino 构造引擎异常对象**——
`new Error('x')` 只要 0.24–0.44 µs、`throw 1` 1.9–2.5 µs，但任何「引擎抛出」的错误
12–16 µs；缺方法那条还要拼实参的 `toString()`（`Building.toString()`），所以比纯 JS
TypeError 还贵一点。**异常开销与元素个数无关**：size=1 的组照样每次 15 µs。

### 1.4 同一条路上的另外两笔开销
- `swrite()` 每次都 `Core.settings.autosave()`：整份 `settings.bin`（本机 287 KB）落盘，
  一次事件里改几处就在同一帧写几遍。
- `dbg()` 每行 open/write/close 一次文件；扫描一忙就是每秒几十次同步 IO。

## 2. 修改（全部在 `GriefToBan/scripts/main.js`）

| 项 | 以前 | 现在 |
|---|---|---|
| 取元素 | `seqGet` 先 `seq.get(i)`，每个元素抛一次异常 | `seqGet` **先 `index(i)`**（0.36 µs，无异常），`get` 只作最后的兜底；新增 `seqIter` |
| 扫描遍数 | `scanReactors` + `scanGenerators` + `scanVirusQuick`，各遍历一遍 `Groups.build` | 单个 `scanWorld(now)`，循环里直接 `arr.index(i)`，分派给 `stepReactor` / `stepGen` / `stepLogic` |
| 编辑器 | 编辑器里照样每秒扫三遍全图 | `inEditor()`（读 `Vars.state.rules.editor`）为真时 tick 直接返回，`onBuildEnd` / `onConfig` 也早退 |
| 计时 | 只有计数 | `GTB_PERF{scan,worst,builds}`；系统属性 `gtb.scan` 与心跳日志带 `ms= / worst= / editor=`；单轮 ≥40 ms 记 `scan slow` |
| 写设置 | 每处 `swrite` → `autosave()` | 同值不写、标脏，tick 里最多每 1.5 s 冲一次；世界加载后立刻冲一次 |
| 日志 | 每行同步 open/write/close | 内存缓冲，40 行或 500 ms 冲一次；诊断/查看/导出前强制冲 |
| 处置数量 | 一个 tick 里可能连发一堆封禁 | `GTB_PUNISH` 预算：一轮最多 6 个，其余下一秒继续 |

同一工作量的成本：**约 371 ms/s → 约 3.3 ms/s（≈110×）**。

### 2.1 随版带上的四条行为改动（用户 m10061 / m10076 / m10086）
- **钍堆恢复条件**：从「热量回到 0」改成 `reactorSafe()` = 钍取空 **或** 通了冷冻液；
  否则保持停用且不再重复提示（日志一行 `reactor held`）。旧逻辑会因为钍还在而
  停用→恢复→再升温无限循环，每次都广播。
- **爆混机**：不再 `items.set(blastCompound, 0)` 删玩家的材料，只 `setEnabled(false)`；
  `GTB_GENS` 记录同一台方块，只提示与处置一次，玩家再打开就静默再停；爆混被取走则清记录。
- **建造者拉黑**：`onBuildEnd` 现在对**所有方块**都记建造者（旧代码只给钍堆记），
  爆混机命中时拉黑建造者：在线走 `punish`，离线直接 `addBlacklist`；管理员建的只广播
  「只停用，不拉黑」。
- **管理员移出黑名单**：`tickAdmins` 里 `removeBlacklist` 之后补 `restoreTeam(p)`，
  广播与私聊写明「已移出黑名单，并恢复到原来的队伍」（以前只删名单、人还留在队伍 0）。
- **ESC 菜单入口**：`pd.cont.button("Grief to Ban", Icon.hammer, openGtbDialog)`，
  取不到 `Icon` 时退回纯文字按钮。
