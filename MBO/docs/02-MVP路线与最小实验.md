# MBO MVP 路线与最小实验设计（第一版）

> 上游：`01-总体架构与数据模型.md`。本文回答三件事：**先做什么、做到什么算成功、怎么证明它比人强或在哪些维度强**。
> 所有阶段估算按"一个人 + AI 辅助"的工作日计。

---

## 0. MVP 的边界（先说不能做什么）

**MVP 能做的**（验收以此为准）：

1. 从真机导出一份**可信的游戏数据快照**（v160.7），配方/工时/耗电/物流参数齐全，且能用真机抽查验证。
2. 解析任意 `.msch` 蓝图 → 内部 IR → 原样写回（往返保真），并能统计产量/耗电/物料平衡。
3. 给定目标产物与速率（如"硅 3/s"），**自动生成**一张可导入游戏的蓝图（矩形生产模块），理论产量达标。
4. 这张蓝图能**在真引擎里跑起来**，实测产量与离线预测的相对误差 ≤5%（E1 判据；E0 单建筑标定要求 ≤5%）。
5. 输出 A/B/C 对比实验的完整记录（指标表 + 蓝图文件 + 复现命令）。

**MVP 明确不做**（写清楚，防止范围膨胀）：

- 全自动"从零到全工厂"（含防御、采矿、地形、电力网全图规划）；
- 模组方块、多星球规则差异；
- 战斗/波次/地形碰撞的仿真；
- 训练大型模型做布局（阶段 5 之后）；
- 图形界面（先用 CLI + 静态渲染图）。

---

## 0.1 先行验证：生产层已经能跑（写方案时已做）

不是纸上谈兵——`MBO/proto/mini_calc.py` 已用真机 dump 的配方数据跑通"配方 DAG 传递 + 每层取整"：

| 目标 | 建筑清单 | 总耗电 | 边界输入 | 占格 |
|---|---|---|---|---|
| 硅 3/s | silicon-smelter ×2 | 60/s | 煤 3/s、沙 6/s | 8 |
| 石墨 1/s | graphite-press ×2 | 0/s | 煤 2.67/s | 8 |
| 玻璃 4/s | kiln ×2 | 72/s | 铅 4/s、沙 4/s | 8 |
| **合金 0.8/s** | **surge-smelter ×1 + silicon-smelter ×2** | **300/s** | **铜 2.4、铅 3.2、钛 1.6、煤 3、沙 6 (per s)** | **17** |

它同时暴露了两个**必须在正式实现里处理的建模问题**：
1. **取整过量**：`ceil` 会让上游产能富余（硅 3/s 需求 2.4 → 2 台产 3/s，富余 0.6/s）。富余是否要回收（喂给别的产品/存仓库）是 MILP 阶段的事，原型只报警告。
2. **非配方产出**：煤/沙/矿在原版主要来自**钻头**（无 craftTime），原型把它们当"边界输入"；也可选 `coal-centrifuge`（无输入、纯耗电产煤）——**MBO 必须显式区分这三类供给**：配方产出 / 采矿产出（地图相关）/ 外部输入。

除生产层外，另外两块也已有可运行原型（详见 `docs/10`、`docs/12`）：

| 层 | 先行验证件 | 实测结果 |
|---|---|---|
| 蓝图写出 | `spikes/bp/scan_corpus.py::build_schematic_ext` | 831/831 语义往返，830/831 body 逐字节一致 |
| 真机验证 | `spikes/sim/engine_probe.py` | 整张 .msch 入世界、60Hz 真推进、读回 efficiency/电力/液体；产物绝对计数未闭环 |

这三块合起来意味着：**MVP 的"生成→写回→真机验证"主链路在调研期就已被逐段证明可行**，剩下的是把它们工程化并接上布局求解。

## 1. 阶段路线（每阶段都有可验收的产出）

### 阶段 0：数据层成活（0.5–1 天）

**做什么**
- 扩展 `out/_dump_game.py` 的思路（用现有 mlogsim Server + Rhino JS），导出**完整字段**：`craftTime / outputItems / outputLiquids / itemCapacity / liquidCapacity / powerConsumption / powerProduction / range / rotate / solid / size / requirements`，钻头（tier/drillTime/hardnessDrillMultiplier/liquidBoost）、传送带（speed/displayedSpeed/capacity）、管道、电力节点。
- 落成 `gamedata/v160.7/*.json` + `meta.json`（含 jar sha256、脚本 sha256、导出时间）。
- 写 `extract_game_data.py` 的**幂等校验**：重复导出结果 byte 级一致；与 `docs/游戏速查/方块配方.md` 交叉比对，列出不一致项。

**验收**
- **27 个"输入输出完整"的配方 100% 可算**（33 个有 craftTime、29 个有 IO；注意 115 是旧口径"有 consumers"，不是配方数）；
- 12 个传送带 / 10 个钻头参数可查（9 个有 items·s⁻¹、8 个有 tier），缺的写明为什么缺；
- 8 张含 v160.7 已删方块的蓝图有明确归因（`alloy-smelter`→`surge-smelter` 改名、`thermal-pump` 删除）；
- 抽 3 个方块（冶炼炉/压机/发电机）用真机实测产出/发电速率，与导出参数推导值误差 ≤5%（数据层的"真机证伪"）。

**风险**：v159.3 源码与 v160.7 运行时的字段差异 → 以 jar 运行时 dump 为准，源码只用于理解语义。

### 阶段 1：蓝图 IR 与语料回归（1 天）

**做什么**
- `mbo/blueprint/`：`Blueprint`/`Tile` 模型 + `from_schematic`/`to_schematic` 适配 `tools/msch.py`。
- **锚点/旋转约定实验**：任选语料中一张多格方块蓝图，走"解析→重建→游戏内放置→读回"闭环，把坐标语义钉死写进 `conventions.md` + 单测。
- 语料回归：833 张 `.msch` 全量"解析→写回→再解析"，统计 tile/坐标/config 完全一致的比例，不一致的归因（版本/未知方块/逻辑块）。

**验收**
- 往返一致率 ≥ 99%（以 10 号文档实测通过率为基线）；
- 每张蓝图能输出 `block_counts + 尺寸 + 是否含逻辑块 + 是否含工厂建筑` 的结构化摘要（语料库索引的基础）。

### 阶段 2：生产计算器（1–2 天）

**做什么**（三层，逐层替换精度与速度）
1. **配方 DAG 传递（纯 numpy）**：目标速率 → 各层中间品需求 → 各建筑数量（连续值）。这一层没有优化器也能跑。
2. **整数化**：`ceil` 取整 + "共享中间品"合并（同一物品的多条产出路线按比例分摊）。
3. **MILP 精修**：OR-Tools CP-SAT，变量=建筑数（整数），目标=加权建筑数/电力/占地，约束=物料平衡 + 电力非负 + 目标速率下限。

**验收**
- 对 10 个原版可生产物品，`calc` 输出"建筑清单 + 各建筑台数 + 理论产量 + 总耗电 + 估计面积"；
- MILP 解与 LP 下界的差距有记录（多数应 ≤1 台/类）；
- 与人手工算的 3 个案例对得上（人的手算作为独立校验，这是"人负责审阅"的具体化）。

### 阶段 3：布局生成（3–5 天，MVP 的主战场）

**做什么**（严格按"模板优先，搜索兜底"）
- **模块模板库**（人工 + 语料挖掘）：每种生产方块一个参数化模板，例如
  `smelter_row(n, feed_side, out_side)` = n 台冶炼炉 + 两侧传送带 + 输出汇流；
  模板声明：占地矩形、输入端口位置、输出端口位置、每端口吞吐。
- **S1 模块选择**：阶段 2 的建筑清单 → 选模板 + n → 模块列表。
- **S2 模块间排布**：shelf packing（按行铺）+ 端口朝向对齐（优先让输出口对着输入口）+ 简单局部搜索（交换两模块位置/翻转朝向）。
- **S3 模块内变体**：模板参数枚举（n、镜像、旋转），选包围盒最小/端口最顺的。
- **连接**：模块间用传送带/桥/管道连接，先用**A\* / 最短路径**在"预留通道"上布线（比 MCMF 简单且够用），冲突时改道或加宽通道。
- **输出**：`to_schematic` → `.msch` + 一张 PNG 缩略图（PIL 已有，图块可用游戏贴图或纯色块）+ 指标 JSON。

**验收**
- 对 3 个目标（硅 3/s、石墨 1/s、合金 0.8/s）各生成 ≥3 张蓝图；
- 全部通过 L1 静态合法性（无重叠/越界/连接超范围），理论产量 ≥ 目标；
- 生成耗时 < 60s/张（CPU，单线程）。

**风险 / 对策**
- 传送带布线冲突 → 先给模块间留固定 2 格通道，宁可面积大一点，先保证可运行；
- 端口朝向对齐不佳 → 允许第二阶段再做朝向搜索，MVP 先"能跑通"。

### 阶段 2.5：E0 标定（0.5–1 天，**前置到布局之前**）

**为什么在这里**：E0 只需要 L2（单建筑 + 已知供料），**不需要布局、不需要布线**。放在阶段 4 会让"数据/模型对不对"这个问题拖到布局做完才暴露——如果 E0 误差 >10%，先修数据层，布局白做。

**做什么**
- 用 `spikes/sim/engine_probe.py` 的手法，对 4–5 种代表建筑（冶炼炉、压机、发电机、传送带、钻头）测"满料/缺料"两档的实际速率，生成 `calibration/v160.7/baseline.json` + 误差表。

**验收**
- 满料档：实测 vs 公式值误差 ≤5%；缺料档：`efficiency` 稳态值与离线模型的分支判断一致；
- 误差超标的项必须给出归因（craftTime 单位、电力不足、传送带容量、锚点），不能记一笔"已知偏差"就过。

### 阶段 4：真机验证闭环（2–3 天，E0 已完成）

**做什么**
- `mbo/validate/real_runner.py`：复用 `tools/mlogsim.py` 的 Server + Rhino 通道，把 `.msch` 放置到空世界，注入原料（核心或容器），跑 N tick，读产出计数/电力/efficiency。
- **读数工具闭环（E1 前置 Gate，约半天）**：主口径 = 产物汇入 container/vault/core 后按 `build.items` 差分；辅口径 = `progress` 回绕计数。**补测已证明主线可行**（0.684/s vs 理论 0.667/s，+2.6%），阶段 4 要做的是封装成 `RunResult.produced` + 在 1800 tick 下复验。
- **误差报表**：每个候选输出"离线预测 vs 真机实测"对比，记录偏差与原因（堵塞/缺料/效率）。

**验收**
- 至少 1 张自动生成的蓝图在真机里跑通（无崩溃、无死锁）；
- 实测产量与预测偏差 **≤5%**（硅这类简单链），偏差 >5% 的必须归因；
- 一次完整验证（起 JVM → warmup 13s → 跑 1800 tick → 收数据 → 退出）**端到端 ~46s**，且无残留 java 进程。

**风险**：服务端把蓝图放上地图的语义（锚点、方向、'世界是否推进'）——**这一项在调研期已经用 `spikes/sim/engine_probe.py` 实测打通（12 号文档）**，结论是"可行（部分）"：

| 环节 | 实测结论 |
|---|---|
| 整张 .msch 进引擎 | **能**：`Schematics.readBase64` + `Schematics.place(sch,x,y,team,true)`，Rhino 里直接可用 |
| 世界真推进 | **能**：60.1–60.3 tick/s（1807.4 ticks/30.07s） |
| 多格锚点 | **中心格**：origin = `(x-(size-1)//2, y-(size-1)//2)`（3×3 vault 传 (33,20)→占 32..34/19..21；2×2 看似左下是除尽巧合） |
| 电力 | **能**：`graph.production/consumption/satisfaction/stored` 真跑（battery stored 0→4000） |
| 缺料/堵死 | **能**（最可靠）：`efficiency` + `progress` 足以判定（kiln `effLow=0/5` vs `effAvg=1`） |
| 绝对产量计数 | **能**（补测）：产物汇入 container/vault/core，按 `build.items` 差分，稳态 0.684/s vs 理论 0.667/s（+2.6%）；progress 回绕计数完全一致，可作交叉校验 |
| 电力连线 | **不会自动连线**：空 config 的 4 个电力方块 = 4 张独立图、links=0、sat=0；语料蓝图写了 config 才有 links → **生成必须显式写 array config** |
| 成本 | 启动 1.8–2.3s + 造世界 0.5s + **1800 tick≈33s**，JVM ~150MB，可并发 4–6 |

因此阶段 4 的"退路"（人工粘贴验证）**不需要启用**；真正要解决的是产物绝对计数这一环，工作量约 1–2 天。

**新踩到的三个坑（必须写进 `real_runner.py`）**：
1. 服务端启动后 **~12 s 会用自己的地图换掉我们造的世界**（日志 `Game over! Team crux is victorious...`，tick 回退 757→17），`rules.canGameOver=false` 拦不住 → **必须 `--warmup 13` + tick 回退检测重试**；
2. 不能在"正在跑"的世界上 `setBlock`（会崩）→ 全部放置/插桩在 `State.paused` 下做；
3. `setBlock` 后必须 `Vars.indexer.addIndex(tile)`，否则方块不参与索引（item-void/container 会"看不见"物品）。

### 阶段 5：搜索与 Pareto（3–5 天）

**做什么**
- 分层搜索骨架（L0 配方组合 → L1 模块排布 → L2 模块内变体 → L3 布线），带预算与 anytime 输出；
- 硬剪枝（LP 界/重叠/超界/被支配）+ 软剪枝（分数 + 保底配额）；
- 规范化哈希去重（旋转/镜像）+ 模块指纹缓存；
- Pareto 存档（epsilon 网格）与 `runs/<id>/` 复现清单。

**验收**
- 同一 seed 两次运行结果完全一致（确定性）；
- 预算内产出 ≥ 8 个非支配解；
- 至少 1 个指标优于阶段 3 的"贪心版"（例如同产量下面积更小或物流更短）。

### 阶段 6：人机协同与学习（MVP 之后）

- 审阅队列（CLI 交互或简单 HTML）+ `HumanFeedback` 落盘；
- 规则库（阶段 1）→ 语料检索（阶段 2）先上线；价值模型（阶段 3）等有 ≥500 条带真机结果的候选再训。

## 2. 最小实验设计（贯穿全程，三层递进）

### E0 标定实验（阶段 4 前置）：离线模型可信吗？

| 项 | 内容 |
|---|---|
| 对象 | 单建筑或最小单元：冶炼炉满料、压机满料、钻头在中密度矿上、传送带满载、发电机带负载 |
| 变量 | 供给充足 vs 供给不足（测效率分支） |
| 指标 | 实际产出/tick、实际耗电、efficiency 稳态值 |
| 判据 | 与"公式推导值"相对误差 ≤5%；偏差进入 calibration 表 |
| 产出 | `calibration/v160.7/baseline.json` + 误差报告 |

**意义**：E0 不过，后面所有"预测产量"都是空中楼阁。这是整个项目里**最便宜也最关键**的一步。

### E1 最小可运行实验（MVP Gate）：生成 → 验证闭环

**目标**：`硅 3/s`（单产物、两输入、无副产物；3/s = **2 台** `silicon-smelter`，1.5/s×2，整机无取整浪费，是"能被精确判分"的最小算例）。

| 步骤 | 命令（拟定） | 成功判据 |
|---|---|---|
| 0 读数工具封装（前置 Gate，约半天） | `mbo verify <msch> --engine real --ticks 600 --selftest` | 对一个**手工已知产量**的样本（如 1 台满料 graphite-press）读出的产量与理论值误差 ≤3%（补测基准：+2.6%） |
| 1 算生产 | `mbo calc --target silicon:3/s --boundary coal,sand` | 建筑清单 = 2×silicon-smelter，60 电/s，边界 煤3+沙6 |
| 2 生成布局 | `mbo gen --target silicon:3/s --canvas 20x16` | 产出 `.msch`，静态校验全绿（无重叠/无越界/端口连通） |
| 3 真机验证 | `mbo verify <msch> --engine real --ticks 1800` | **实测 ≥2.85/s 且相对预测 ≤5%**，无死锁（判据见下） |
| 4 存档 | 自动写 `runs/<id>/` | 含 manifest（seed/gamedata/jar sha/命令/tick 窗口） |

**E1 是"项目活了"的标志**：一张机器生成的蓝图，在真游戏里跑出预测产量。

### E1 原型已跑通（2026-11-05，`MBO/spikes/gen/gen_e1.py`）

| 项 | 实测 |
|---|---|
| 画布 / 规模 | 24×24，**19 tiles / 31 占用格 / 175 字节**（粘贴码 236 字符） |
| 组成 | 2×`silicon-smelter` + 4×`conveyor` + 2×`item-source` + 2×`container` + 2×`power-node` + 1×`power-source` |
| 静态校验 | 全绿（无重叠/越界、端口连通、每炉相邻 node、电力连通块 = 1） |
| 预测 | 3.00 硅/s；coal 3.0/s、sand 6.0/s；耗电 60/s |
| 真机 1800 tick | **3.05 硅/s（误差 +1.7%）**，两台炉 `eff=1.00`，无死锁 |
| 端到端耗时 | 46 s（生成 + 写盘 + 起引擎 + 1800 tick） |

细节与踩坑见 `docs/14`。**剩余差距**：产物只写了 `.msch` / `.b64` / `metrics.json`，`report.md`、`trace.json` 与 `runs/<id>/` 目录化还没做（工程化，非可行性问题）。

> **为什么不是"2/s"**：硅单机 1.5/s，任何整数台数的产能都是 1.5 的倍数。写 2/s 就只能"多产 50% 然后装作达标"，判据失去意义。写 3/s 则"2 台刚好 3/s"，误差判据才有分辨力。
> **目标速率的通用规则（用户："以实际情况为准"）**：目标必须是"单机速率的整数倍可达值"。先跑 `mbo calc` 得到单机速率 r，取最小整数 n 使 `n·r ≥ 期望值`，把目标写成 `n·r` 并写进 manifest；判据始终是"实测 vs 预测的相对误差 ≤5%"，而不是"≥某个绝对数"。E1 的期望值取 2–3/s → n=2 → **目标 3/s**。

**E1 的算例已经被原型跑通**（`MBO/proto/mini_calc.py`，读真机 dump，实测输出）：

```
$ python -X utf8 mini_calc.py silicon:3/s --boundary coal,sand
目标: silicon 3/s
建筑清单:
  silicon-smelter  x2   size=2  power=30.0/s
建筑总数 2（占 8 格），总耗电 60.0/s
边界输入: coal 3/s, sand 6/s
```

→ 布局层要做的就只是把这 2 台 2×2 的冶炼炉 + 进料/出料传送带排进一个矩形里（目标 ~10×6），这就是 E1 的全部空间问题。**注意边界输入的口径**：煤与沙视为"外部供给"（核心/采矿口送入），否则会引入"矿脉在哪"的地图依赖——那是 MVP 之外的事。

### 2.1 测量协议（E1/E2 共用，先写死再动手）

没有这一节，三组数据不可比，谁都能得出"我赢了"。以下五条必须在第一次跑之前定死并写进 `runs/manifest.json`：

| 项 | 规则 |
|---|---|
| **给料方式** | 原料用 `core-shard` 预置初始量（逐项在 manifest 里列数量，如 E1：煤 600 / 沙 1200），加**一条**入料传送带；**禁用 `item-source`/`liquid-source`**（绕过物流=绕过被优化对象）。**电力允许用 `power-source` 供电**（用户已确认，2026-11-04）：三组统一用 `power-source`，并在 manifest 标 `power_source=true`；此时**电力指标只算"耗电"与"电力覆盖/连线质量"，不把发电占地计入面积**（否则等于用无成本的沙盒方块刷分）。若某组改自建发电机，必须单列且不与前者混排 |
| **预热窗口** | 服务端启动后等 `warmup≥13s`（避开地图替换），放图后先跑 **300 tick 预热**，统计窗口 = **300–1800 tick**（25 游戏秒稳态） |
| **产量口径** | 主口径 = **产物汇入 container/vault/core 后的 `build.items` 差分**（产物必须有实物落点，禁用 `item-void`）；辅口径 = `Σ(完成的 batch 数) × 每批产出`（`progress` 回绕计数）；**交叉校验** = 输入端物料消耗差，三口径两两偏差 >2% 判该次测量无效（实测：容器口径吸 0.684/s vs 理论 0.667/s，+2.6%；progress 回绕与之完全一致） |
| **死锁判据** | 任一机器 `efficiency < 0.05` 且 `progress` 连续 **≥120 tick 不变** → 记死锁；电力 `satisfaction < 0.98` 记"电力不足" |
| **读数分母** | 报告里必须区分三个量：`blocks`（建筑实例数）/ `tiles`（占格数）/ `footprint`（宽×高包围盒面积）。E1 的 2 台硅炉 = blocks 2 / tiles 8 / footprint 100（10×10 画布内）|

> 沙盒方块的态度：**物料类禁止、电力类允许**。`item-source`/`liquid-source` 等于绕过物流（物流正是被优化对象）；`power-source` 只影响"电从哪来"，不影响布线/布局质量判定，且能把变量从电力供给上摘掉——但它让"电力效率/发电占地"失去意义，所以该维度按上表口径作废并写明。

### 2.2 CLI 契约（先定接口，再写实现）

三条命令是 MVP 的全部对外接口；**参数名与 `MBO/proto/mini_calc.py` 的已跑通版本对齐**，避免文档与代码各说一套：

| 命令 | 入参（必填/可选） | 输出 | 退出码 |
|---|---|---|---|
| `mbo calc` | 必填 `<item>:<rate>/s`；可选 `--boundary a,b`（视为外部供给，不向上展开）、`--force item=block`、`--gamedata <快照id>`、`--json` | 建筑清单（方块×台数）、总耗电、各边界输入速率、`blocks/tiles/footprint` 三量、LP 下界与 MILP 解差距 | 0 可行 / 2 不可行（附 LP 证明）/ 1 参数错 |
| `mbo gen` | 必填 `<item>:<rate>/s`；可选 `--boundary`、`--canvas WxH`（默认 24x24，上限 128x128）、`--seed`、`--out <path.msch>`、`--budget <秒>` | `.msch` + 指标 JSON（8 项 + 三量）+ 静态校验报告（重叠/越界/端口/电力连通块数） | 0 成功 / 2 静态非法 / 3 超预算（可能仍输出最佳候选） |
| `mbo verify` | 必填 `<path.msch>`；可选 `--engine offline\|real`（默认 offline）、`--ticks 1800`、`--warmup 13`、`--seed-material <json>`、`--json` | 实测/预测产量双口径、死锁与电力不足标记、逐方块 efficiency/progress、`offline_vs_engine` 偏差 | 0 达标 / 2 未达标 / 3 引擎失败（含日志尾部）|

> `--boundary` 不是可选项：不声明边界，计算器会一路展开到矿（地图相关），E1/E2 的"目标产量"就无法定义。默认边界建议写进 `mbo/config/defaults.toml`（E1: `coal,sand`；E2: `coal,sand,copper,lead,titanium`）。

### E2 A/B/C 对比实验（MBO 第九节的原实验）

**目标**：`合金(surge-alloy) 0.8/s`——一个输入（铜/铅/钛/硅）、有中间产物（硅）、无副产物，是"有代表性但不至于炸变量"的复杂度。

> **用户已确认（2026-11-04）**：① 项目书里的"钛合金"就是 `surge-alloy`；② **合金厂确实需要配合逻辑运行**。这改变 E2 的范围：A 组基线（人工）可以含 mlog 处理器，因此 B/C 组若完全不带逻辑会显得"赢得不公平"。
> 处理方式：L1 IR **必须能解析、保留、原样写回**逻辑块（`docs/10` 已证明 1477 个逻辑块可解析、831/831 可写回）；MVP 的生成侧**不合成 mlog**，而是提供"逻辑模板槽位"——生成器只负责布局与物流，必要时把参数化模板（如分拣/溢流控制）嵌入，模板来源与参数在 `runs/manifest.json` 里记录。E2 报告里单列"逻辑使用情况"列（有/无、几块、模板 id），避免把"逻辑复杂度"混进布局指标。

> 版本映射说明：MBO 文档写的"钛合金"不是原版物品；原版最接近的是 **surge-alloy（合金/浪涌合金）**，配方 = 3 铜 + 4 铅 + 2 钛 + 3 硅（**无液体输入**），75 帧 / 0.8 s⁻¹ / 240 电。E2 用它，并在报告中明确这个映射（否则实验无法在原版复现）。

**为什么是 0.8/s 而不是 1/s**：`surge-smelter` 单机就是 0.8/s，整数台数下可选产能只有 0.8 / 1.6 / 2.4…。想要 ≥1/s 就得 **2 台合金炉 + 4 台硅炉（约 34 格、600 电/s）**——那是"放大一倍"的另一个实验，画布和 A 组基线都要重选。**MVP 定为 0.8/s**；1.6/s 作为阶段 5 的"扩展性验证"再做。

**三组方案**

> **目标产能的实测依据**（原型 `mini_calc.py` 真机数据）：`surge-smelter` 0.8/s 合金（3 铜 + 4 铅 + 2 钛 + 3 硅，75 帧，240 电/s）。
> 要 0.8/s 合金 → 1 台合金炉 + 2 台硅炉（产 3/s 硅，富余 0.6/s 可外送），共 **3 台机器 / 17 格 / 300 电/s**，边界输入 `铜 2.4 / 铅 3.2 / 钛 1.6 / 煤 3 / 沙 6 (per s)`。
> 这个规模的好处：足够复杂（4 输入 + 中间产物），又小到能在一张 ~20×20 蓝图里完整验证；语料里 **19 张工厂型（含 2 张混合型共 21 张）** 现成 surge-alloy 蓝图可作 A 组基线，其中**零逻辑 3 张**可直接对比。

| 组 | 方案 | 说明 |
|---|---|---|
| A 人工 | **A1 手搭**（人从零搭）为主基线；**A2 语料改造**（取现成图改产能）作参照 | 人工耗时**只统计 A1**（A2 只改几处，不可比）；两者都记录 |
| B 脚本自动 | MBO MVP 全自动（阶段 2→3），不开搜索，不人工干预 | 计时、成功率、指标 |
| C 人机协同 | MBO 生成候选集（Pareto 前 5）→ 人选 1 张 → 人做 ≤3 处小修改 → MBO 重算指标 | 记录人改了什么（diff），这是 L5 的偏好样本；**C 的语义是"人协助剪枝/微调"，不是"人重做"** |

**指标表（每次运行都填；每项必须有采集脚本入口或明确标"人工记录"）**

| 指标 | 定义/公式 | 采集方式 | 方向 |
|---|---|---|---|
| 产量达成率 | 实测产量 / 0.8 (s⁻¹) | 测量协议主口径 | ↑ |
| 面积 | `footprint = w×h` | IR 统计 | ↓ |
| 建筑数 | `blocks`（实例数） | IR 统计 | ↓ |
| 物流长度 | 传送带+导管 tile 数 | IR 统计 | ↓ |
| 物流吞吐量 | 稳态输入/输出物料总量 / 秒 | 真机（Σ机器消耗） | ↑ |
| 总耗电 | 稳态净耗电（发电−耗电，含太阳能/电池缓冲折算） | 真机 `graph.consumption` | ↓ |
| 启动时间 | 从放料到产量达稳态 95% 的 tick 数 | 真机（逐 tick 采样） | ↓ |
| 扩展性（代理） | 预留空列数 × 可接端口数（公式写进 `mbo metrics`） | IR 统计 | ↑ |
| 人工耗时 | 分钟（A1/C 组） | 人记录 | ↓ |
| 失败次数 | 崩溃/死锁/贴错导致的重来 | 日志 + 人记录 | ↓ |
| 搜索耗时 | 从启动到产出最优候选的墙钟秒数（B/C） | `runs/manifest.json` | ↓ |
| 候选方案数 | 预算内评估过的合法候选数 | 搜索器计数 | — |
| 剪枝数 | 硬剪枝/软剪枝各多少，硬剪枝按原因分类 | 搜索器计数 | — |

> 前 8 项对应 MBO.md 第四节的 8 项优化目标（一一对应，名称不改）；后 5 项是过程量，用于解释"为什么赢/输"。

**协议（防止自欺欺人）**

1. 目标、画布上限、可用方块集合**先写死**，三组一致（能量化才有意义）；
2. 每组重复 ≥3 次（B 组用不同 seed；A 组允许人重来，重来次数计入）；
3. 真机测量严格按 §2.1 测量协议（给料/窗口/口径/死锁判据）；
4. 所有蓝图与日志落 `runs/`，任何人可重放（manifest 含 seed/gamedata_id/jar_sha256/命令）；
5. **预算必须定义清楚**：B/C 组给"墙钟 ≤30 分钟 / 单机"或"评估 ≤5000 个候选"，二者选一并写死；
6. **结论允许是"MBO 只在某些维度赢"**——例如面积赢、人工耗时赢，但扩展性输给人。这比"全面超越"可信。

**预期结论（写下来，等被打脸或验证）**

- B 组在"建筑数少/面积小/无遗漏"上应明显优于 A（人的手误与遗漏是 B 的天然优势）；
- A 组在"物流自然、可读性、扩展性"上可能优于 B（MVP 的布线是贪心的）；
- C 组应综合最好，但它依赖人的时间——**这正是"MBO 文档要求人机协同"的实证**。
