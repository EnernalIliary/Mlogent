### 已确认的环境事实（影响实现）

- Mindcode 官方 jar 在本机只有一个可用版本：`C:\Users\lliary\src\mindcode-dist\mindcode.jar` = **v3.19.3**；v3.21.0 在本机**必死锁**（`UpdateChecker` → `dev.dirs` 读 PowerShell 子进程 stdout），原因见下。集成层默认用 v3.19.3，jar/JRE 路径可用 `MINDCODE_JAR` / `MINDCODE_JAVA` 覆盖。
- v3.21.0 死锁根因（上游 bug）：`Main.java:40` 只在顶层 parser 声明 `--no-update-check`，而 `ToolAppAction.java:41` 从子命令 namespace 读它，永远取不到 `TRUE` → 更新检查无条件执行。
- 诊断格式（实测 v3.19.3）：stderr 每条 `文件:行:列 类别: 消息`，退出码 1；**源文件若带 BOM，会在 `1:1` 报一条假 Parse error**，所以编译前必须剥 BOM。
- 本机 Java：`out/jre21/jdk-21.0.5+11-jre/bin/java.exe`（JRE 21）可用；`out/_mindcode/jdk-25.0.5+8-jre` 也可用。系统 PATH 里的 java 是 Java 8，**不可用**。

## 2. 接口契约

三个模块，谁都不许改别人的文件；都只通过下面的函数签名互相调用。

### 2.1 `tools/mlog_eval.py` — 统一结果信封与判定（共享脊梁）

```python
FAILURE_TYPES = ("compilation_error", "static_analysis_error", "runtime_error",
                 "assertion_failed", "timeout", "unsupported_environment",
                 "simulation_real_difference")
SUCCESS_LEVELS = ("execution", "static", "simulation", "real_runtime")
LEVELS = ("summary", "diagnostics", "full")

def result(*, ok: bool, stage: str, failure_type: str | None = None,
           message: str = "", diagnostics: list | None = None,
           artifacts: dict | None = None, next_steps: list | None = None,
           trace: dict | None = None, level: str = "summary",
           levels: dict | None = None, elapsed_ms: int | None = None) -> dict
def evaluate(*, mlog: str | None = None, static: bool = True,
             sim: dict | None = None, expectations: list | None = None,
             limits: dict | None = None, level: str = "summary") -> dict
def classify(exc: BaseException) -> str          # 异常 → failure_type
def summarize(env: dict) -> str                  # 单行摘要
```

信封（`result()` 的返回，`schema="mlog-eval/v1"`）：

```json
{"schema": "mlog-eval/v1", "ok": true, "stage": "simulation",
 "failure_type": null, "message": "", "level": "summary",
 "levels": {"execution": true, "static": true, "simulation": true, "real_runtime": null},
 "diagnostics": [], "artifacts": {}, "next_steps": [], "trace": null,
 "elapsed_ms": 123}
```

`levels` 是实施记录 §4 P1 的四个成功维度，**`null` 表示没跑、不是失败**；「执行器跑完了」绝不等于「程序正确」。
`level` 决定裁剪：`summary` 只留 ok/stage/failure_type/message/levels/next_steps；`diagnostics` 追加 diagnostics/artifacts；`full` 追加 trace。

## 5. 已知坑（写场景/接 Mindcode 时会撞上，已实测）

- `op` 只认长名（`greaterThan`），`op gt` 被**静默丢弃**且不报错；
- 空世界没有核心 → `unitCap=0` → 单位生下即死；场景要先给 `unitCap`；
- 卸载器不往相邻容器/核心推货，必须经传送带；
- 场景脚本别以 `for(...){}` 结尾（控制台回显值，`mlogsim` 等 `undefined` 会挂到超时）；
- `scene.py:147` 用 `str()` 处理 `code_inline`，JSON 数组会变成 Python list repr（已由投影层 join）；
- Mindcode 源文件带 BOM 会报 `1:1 Parse error: extraneous input '?'`；3.19.3 要 Java 22+。

### 差分实测（2026-11-17，真开服一次）

- 活世界的时钟是**真实时间**，协议层没有「停在第 N tick 采样」的原语；固定 0.2 s 轮询在 60 tick/s
  下会多跑 ~12 tick（把循环计数从 79 拉到 87）。改成自适应 sleep（`min(0.2, 剩余tick/60)`）后
  循环次数对齐，只剩 tick 相位差。
- 240 tick 的 `unit-control`：离线 vs 活世界有 5 处差异 —— 循环计数差 1（tick 相位）、
  `@counter` 差 1（同上）、单位坐标差 ~1.3 格（`unit-motion`，两侧都在跑游戏的 `Unit.update()`，
  差的是**地形与场上其它单位**：离线是 `blank-64` 凭空世界，活世界是 Fork）。
- 因此 `fidelity.annotate()` 的三条新规则：日志里镜像物理量的变量（`x/y/ux/uy/hp…`）归 `unit-motion`；
  日志里数值差 ≤1 的计数器归 `tick-model`；其余仍 `unexplained`（`instruction-set` 是 `verified`，
  已证实的东西不许拿来当借口）。
- `env` 政策定稿：`map`/`world_size` 默认降级为 note（离线主机只能伪造空白世界），
  `--strict-env` 可让它们重新 blocking；`update`/`sampling` 恒为 note；只有一侧报告的字段也是 note。

### 活世界（`--via world`）才暴露的三处接线

2026-11-18 把 `generated-unit-control` / `generated-resource-drain` 第一次真正铺进游戏后，
三个 bug 都是**离线测试结构上不可能发现**的，各自已加回归：

1. **扰动「执行了但没回话」**：活世界的 `js` op 只回 `sb.append(...)` 的行，扰动脚本却硬编码
   `print(...)`，于是 `_modifier_fire` 判 `executed=false`、报 “printed no MOD line”。
   → 统一走 `MOD_say()`，运行期 `typeof sb` 选通道（`tests/modifier` 的
   `test_reports_on_both_hosts` 钉住「world 侧不许有裸 print」）。
2. **链接名被广播冲掉**：`configureAny(compress(code, relativeConnections()))` 是给客户端看的
   同一条路，`readCompressed()` 用 `findLinkName()` 重新起名（`core-shard` → `shard1`），
   代码里的 `hub` 于是绑成 `null`。→ 广播后在本地按场景名重挂链接再 `updateCode()`
   （`tests/scenario` 的 `test_live_rig_wiring` 钉住语句顺序）。
3. **核心库存是累加的**：同一场景离线起 120、活世界起 285（那块地原本压着库存）。
   → 核心先 `items.clear()` 再补；普通容器保持累加语义（同上测试钉住 `clear` 在 `add` 之前）。

另有一条运维坑：世界服是常驻进程，`import scene` 在启动时就固定了，改 `tools/scene.py` 后
必须重启世界服，否则跑的还是旧模块（本次全部修复都是在重启之后才生效的）。
