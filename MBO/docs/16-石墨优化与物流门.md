# 16 · 石墨产线优化：一个源 + 一个物流门（溢流门 / 反溢流门）

> 目标（用户 m01667 + m01674）：**只优化石墨、保持简单**；把物流盲区里的
> **正溢（溢流门 overflow-gate）** 与 **反溢（反溢流门 underflow-gate）** 带上。
> 本文只讲这一件事：两张门都是 1×1 的分流方块，用它替掉“每台机器一条独立源 + 两条带”，
> 把石墨单元从 10 方块压到 6 方块，吞吐不变。

## 0. 结论表（真机 1800 tick，同一份 v160.7 数据、同一套采样口径）

| 方案 | 方块 | tile | 预测 | 实测 | 偏差 | wall | Gate |
|---|---|---|---|---|---|---|---|
| `cells` 基线（每台一个源 + 2 条带） | 10 | 22 | 1.3333/s | **1.3666/s** | +2.5% | 45.2 s | PASS |
| `split` + 反溢流门（推荐） | **6** | **18** | 1.3333/s | **1.3569/s** | +1.8% | 45.8 s | PASS |
| `split` + 溢流门 | **6** | **18** | 1.3333/s | **1.3591/s** | +1.9% | 45.8 s | PASS |

- 方块 **−40%（10→6）**、tile **−18%（22→18）**，吞吐差异（1.3666 vs 1.3569）在 ±1% 采样噪声内。
- 省掉的正是“2 条 3 格的输入带 + 1 个多余物料源”：分门方案里 **一条带子都不需要**。
- 三门（两种门）用同一套模板，只换方块名——门的差别只在“先给谁”，见 §1。
- `--layout` 默认 `auto`：单输入 + 2×2 + 偶数台 → 自动走 split（石墨即如此）；
  `runs/g1` 是**改造前** cells 模板的基线，复现基线用 `--layout cells`。

## 1. 门的语义（源码级，别再靠猜）

`Mindustry-Source/core/src/mindustry/world/blocks/distribution/OverflowGate.java`：
`overflow-gate` 与 `underflow-gate` 是**同一个类**，只差 `invert` 字段（`invert == enabled`，
默认 `enabled=true`）：

- `underflow-gate`：`invert=true`　`overflow-gate`：`invert=false`
- `from` = 物料进来的方向；`to = nearby((from+2)%4)` = **直行方向**（穿过门继续走）；
- `canForward` = 直行位是空的、同队、且 `acceptItem`；
- 若 `!canForward || inv`：先试两侧 `(from±1)%4`，哪侧收货走哪侧；两侧都收 →
  用 **rotation 字段当交替记忆位**（`rotation & (1<<from)`）决定先后，并翻转该位；
- 两侧都不收 → `inv && canForward ? to : null`。

⇒ 一句话：**溢流门 = 直行优先、堵了才分两侧；反溢门 = 两侧优先、两侧都堵才直行。**
两种门都自带“轮流分配”，不需要 sorter。

数据层（`gamedata/v160.7/gamedata.json`）：`overflow-gate` id 268、`underflow-gate` id 269，
都是 `size=1`、`category=distribution`、**容量 0**（不存货，纯分流）。

## 2. split 模板怎么摆

实测布局（`mbo gen graphite:1/s --boundary coal --layout split`，canvas 24×24）：

```
    12345678901
  3      S          ← item-source（配置 = 石墨所需的煤），rot=S 直对门
  4  CCMM+MMCC      ← 左仓 压机 门 压机 右仓（+ = 物流门）
  5  CCMM MMCC      ← 2×2 方块的下半行
```

规则（`mbo/layout.py::build_split`）：

1. 主干列 `tx = margin+4`；源在 `(tx, gy-1)`，门在 `(tx, gy)`；
2. 门左右各一台 2×2 机器：东侧机器原点 `tx+1`、西侧 `tx-s`（`s=2` 时 `tx-2`）；
   这样两台机器都**正交贴着门的那一格**（门的 `nearby` 才收得到）；
3. 输出容器贴在机器**外侧**（东 `mx+s`、西 `mx-s`），与机器相邻；
4. 多于一对机器时，门与门之间用一条 `rot=S` 的直行带连接（第 2 对起每对 +1 带）；
5. 门下方（直行位的尽头）留空——两种门在“没人收货”时都安全；
6. 末尾照旧跑 `route_power`（石墨压机不耗电，实测 `power_components=0`，这一步空转）。

## 4. 适用边界（写进 `layout.split_applicable`，不满足就回落）

| 条件 | 原因 | 不满足时 |
|---|---|---|
| 机器 2×2 | 模板按 2×2 摆，容器位置也按 `s` 推 | `--layout split` 直接报错；`auto` 回落 cells |
| **单输入**（石墨压机只要煤） | 一个门只能分流一种物料；硅炉要 coal+sand | `auto` 回落 cells 并记 warning |
| 台数为偶数且 ≥2 | 一对机器共用一个门 | `auto` 回落 cells 并记 warning |

实测：`silicon:3/s --layout auto` → 仍是 19 建筑/31 格、2.958/s，行为与改造前一致（回归通过）。

## 5. 校验器新增的两条（`mbo/validate.py`）

- `feeds()` 现在把**物流门**也算作“能送东西过来”（和传送带同桶），否则会误报缺输入；
- 新增门专项检查：门**必须有上游**（相邻 item-source / 指向它的带子 / 上一级门），
  且**至少有一个非电源下游**——防止“门被摆成孤岛、物料卡死”这种静态可查的错误。

## 6. 编码层交叉验证（顺带把“我们写的蓝图官方认不认”钉死）

用官方 API 写同一张图再比字节（`spikes/gen/api_probe.py`，headless 服务端）：

- headless 下 `Vars.schematics` 是 **null** → 必须自己 `new Packages.mindustry.game.Schematics()`；
- `inst.writeBase64(sch)` 可用；`inst.create(x,y,x1,y1)` 在 headless 返回 1×1/0 tile（**不可用**）；
- 同一张 6-tile 布局：官方 body 181 B、我们的 143 B；
  **tile 层 6/6 完全一致**（方块名 + 中心格坐标 + rotation）、方块字典一致、`w/h` 一致；
  差异只在 tags：官方额外写 `contentMap='{0:{coal:5}}'` 与 `labels='[]'`。
  ⇒ 我们的 writer 在 tile 层与官方等价，只是没写内容映射表；游戏能读（放置 + 生产均已验）。
- `Schematics.rotate(sch,1)`：16×12 → 12×16、tile 守恒（以后做旋转变体可直接用官方实现对照）。

## 7. 没做（明确的边界）

- **多输入机器**（硅炉/窑）的双门方案：需要“两条门链 + 汇合”，布局复杂度跳一档，本轮不做；
- 门的 `rotation` 交替记忆位没有刻意构造“先给东还是先给西”的偏好，实测均衡已够；
- sorter / router / junction / 交叉带仍属物流盲区（docs/15 §7）；
- 只验了石墨一条线的门方案；玻璃/硅保持 cells 模板未动（回归已验证）；
- **出口合流**（一个出口收全部产物）见 `docs/17`：`--merge pair|single|vault|core|void`。
