# E01 执行模型与预算

## 一句话

逻辑不是「每 tick 跑一遍程序」，而是**一个点数池**：每 tick 按 `edelta()×ipt` 充点，点够 1 就执行一条指令，卡顿时池子被削到 `5×ipt` —— 这解释了「为什么卡顿会丢逻辑」「为什么突发能跑得更快」。

## 规则 / 公式

### 1. 主循环（LogicBlock.updateTile）

```java
// LogicBlock.java:564-579
if(accumulator > maxInstructionScale * ipt) accumulator = maxInstructionScale * ipt;
while(accumulator >= 1f){
    executor.runOnce();
    if(executor.yield){ yield = false; break; }
    accumulator--;
}
accumulator += edelta() * ipt;
```

四个反直觉点，全部来自这 8 行：

| 点 | 机制 | 后果 |
|---|---|---|
| 累加在循环**之后** | 源码注释明确说不能前移；`accumulator` 是无初值字段（0）| 新建处理器**第一条 tick 执行 0 条**（只装载不执行）；之后每 tick 用上一 tick 的余量；WaitI 的 curTime 同步 |
| `yield` 分支在 `accumulator--` **之前** break | 让出的那一轮不扣点 | `wait` / `stop` 不消耗预算 |
| 削顶发生在循环**之前** | `min(池, 5×ipt)` | 卡顿多出来的点直接丢弃，不会攒成大突发 |
| 循环是 `while(>=1)` 不是 `for(i<ipt)` | 按点数消费 | 单 tick 实际执行数 = 池子里剩余点数 |

### 2. runOnce 与 @counter

```java
// LExecutor.java:111-121
if(counter.numval >= instructions.length || counter.numval < 0) counter.numval = 0;
instructions[(int)(counter.numval++)].run(this);
```

- `@counter` **先取后加**，所以它永远指向「下一条要执行的指令」。
- 越界或负数 ⇒ 归零（不是崩溃、不是停）。
- 改写 `@counter` 的效果在**下一条指令**生效，当前指令一定执行完。

## 实测与反例

- ✅【E】`@ipt` 只能被 `setrate` 改写，`set @ipt 5` 静默丢弃（@ipt 是 putConst，LAssembler.java:27）；实测 set 后 @ipt 不变（断言表 L1 系列）。
- ✅【E】micro 从空池到攒满 10 点需 5 tick ≈ 0.0833 s（L1-31）。 [实测: docs/断言表.md]
- 反例（不成立边界）：**「一个 tick 内一定跑完 ipt 条」不成立**。池子不足 1 点时一条都不跑；池子 >5×ipt 时也只跑 5×ipt。
- 【U】多人服务器 tick 率非 60 时，`edelta()×ipt` 的实际吞吐需要一次专用服务器实测（客户端 60 tick/s 是换算约定，不是全局保证）。 [src: knowledge/VERSION.md:1]

## 常见误解

1. 「ipt=25 就是每 tick 25 条」——长期对，单 tick 会因池子空而少跑。
2. 「wait 占预算」——让出那一轮不扣点。
3. 「@counter 自增发生在执行前」——先取后加。
4. 「卡顿后逻辑会加倍追赶」——削顶在先，追不回来。
