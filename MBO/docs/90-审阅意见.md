## 1. 必须改（阻断级，最多 8 条）

### 1.1 craft_time 单位冲突：秒 vs 帧，差 60 倍
- **位置**：`docs/01-总体架构与数据模型.md:121-125`（`craft_time: float # 秒 = craftTime/60`、`batch_rate = 1/craft_time`）vs `docs/11-游戏数据层.md:351-352`（`craft_time: float # 帧`）。
- **问题**：L0 快照若按 11 号存"帧"、L2 按 01 号当"秒"用，所有产量、电力、机器数全部 60× 错；且 `batch_rate = 1/craft_time` 在帧单位下会把"每帧产出"当成"每秒产出"。这是全链路根节点的量纲。
- **改成**：字段拆成 `craft_time_frames: int`（原值）+ 派生 `cycles_per_second = 60 / craft_time_frames`；01 §2.4 删掉"秒 = craftTime/60"，L2 只暴露 cps；加一条断言测试：surge-smelter 75 帧 → cps=0.8（对齐 `docs/11:267` 与 `docs/02:213`）。

### 1.2 E1 的 Gate 数字自相矛盾，且依赖一个尚未闭环的量
- **位置**：`docs/02-MVP路线与最小实验.md:181-187`（目标 2/s；判据"实测 ≥1.9/s、误差 ≤10%"）、`:192-201`（算例用 `silicon:3/s`）、`README.md:108`（"2–3/s"）、`docs/12-真机验证可行性.md:134` 与 `:143-145`（绝对产量"需变通"、sink 容器仍空、metaglass 从未出现）。
- **问题**：硅单机 1.5/s（`docs/11:199`），2 台=3.0/s。预测 2/s、实测 3/s，误差 50%，永远过不了 ≤10%；而把判据写成"≥1.9/s"，2 台的方案在 1.9 就判过，等于没验。更根本的是"实测产量"目前只能从 sink 容器读，12 号已实测该路径读不出数——E1 的读数工具本身没闭环。
- **改成**：目标定 3/s（2 台整机），判据"实测 ≥2.85/s 且相对预测 ≤5%"；产量口径改为"Σ 完成周期数 × 每批产出"，用 `docs/12 §1.3` 的 progress/eff 采样实现，sink 计数降为交叉校验；把"读数工具闭环"单列为 E1 的前置 Gate（约半天）。

### 1.3 E2 目标 1/s 在给定机队下物理不可达
- **位置**：`docs/02:207`（合金 1/s）vs `docs/02:213-215`（"0.8/s → 1 台合金炉 + 2 台硅炉、3 台/17 格/300 电"）vs `docs/02:106-108`（阶段3 验收合金 0.5/s）vs `README.md:111`（0.8/s）。
- **问题**：surge-smelter 单机 0.8/s（`docs/11:267`），1+2 的组合只能是 0.8/s。要 1/s 得 2 台合金炉 + 4 台硅炉（约 34 格、600 电/s），与 `docs/02:213` 自述的 17 格/300 电不是一个方案。照着验收必失败，最后只能改口径。
- **改成**：E2 目标统一 0.8/s。若确实要"≥1/s"，机队改 2+4 并重算面积/电力/`docs/02:213` 的依据，不能只改一行数字。

### 1.4 "统一读数口径 / 统一给料方式"只有要求，没有定义
- **位置**：`docs/02:239-243`（协议三条：统一 tick 数、统一原料注入方式、统一读数口径）；`docs/02:192-201` 的算例只给了 `--boundary`，没说原料怎么进入世界；`docs/12:216` 只说"不许快进"。
- **问题**：E1/E2 的结论完全取决于这三件事，而全文没有一处定义：原料从哪来（core 预置？传送带接入？item-source？）、读数从第几 tick 起（warmup 13s 扣不扣）、产量算毛值还是净值、允不允许 power-source（`gamedata.json` 里 15 个"发电"含沙盒 `power-source`）。换个人执行就是另一组数，A/B/C 三组不可比。
- **改成**：在 `docs/02` §E1 前加"测量协议"小节，至少写死——①给料：core-shard 预置固定初始量（逐项列数量）+ 单条传送带接入，禁用 item-source / power-source（若用必须标"沙盒"且不计入对比）；②窗口：丢弃前 300 tick，统计 300–1800；③产量：完成周期积分，同时记录输入端消耗差做交叉校验，偏差 >2% 判无效；④死锁判据：eff<0.05 且 progress 连续 ≥120 tick 不变。

### 1.5 两份互不兼容的 IR，且写回 API 指向 27.68% 的那条路

### 1.6 "游戏会自动重建电力连接"是未验证断言，且源码不支持
- **位置**：`docs/00:49`、`:52`（"Mindustry 放置蓝图时会自己重建电力连接，所以生成蓝图时可以少写 array config"）。
- **问题**：核对 `Mindustry-Source\core\src\mindustry\game\Schematics.java:508-521`，`place()` 只做 `tile.setBlock()` + `tile.build.configureAny(st.config)`，**不调用 `Building.placed()`**；自动连线在 `PowerNode.java:399-410` 的 `PowerNodeBuild.placed()`，且仅在 `links.size == 0` 时 autolink；`Tile.java:235-294` 的 `setBlock()` 同样不调 `placed()`。即空 config 的节点在正常加载路径下不会自动接上，生成的蓝图可能出现电力孤岛，而 E1/E2 全部依赖电力。00 用这条推断"可以少写 config"，是拿未验证结论去削实现工作量。
- **改成**：降级为"待验证"，并写清依据（哪段源码、哪条调用路径）；补一个 30 分钟实验（2 个 power-node + 1 个耗电块、config 写空、跑 300 tick 看 `sat` 与 graph 数）；结论出来前默认"必须写 array config"；Validator 增一条"连通块数 == 期望数"。

## 5. 我不确定的点

1. **11 号存在**。任务书说它"可能不存在"，实际有（33,827 B，2026-11-04 20:30）。我把它当游戏数据仲裁源用了；若审阅基线是不含 11 的版本，§1.1（craft_time）、§3 中 107 / 27 / 85s 几行的"文档B"要改为"11 号（新增）"，其余结论不变。
2. **电力自动连线到底成不成立**。我按 `Schematics.java:508-521` 判"不成立"，但没真机跑（本任务不许起 java）。这条需要 30 分钟实验定论；若成立，00 的"少写 config"可保留，但"默认必须写"仍是更安全的实现策略。
3. **A 组基线到底几张**。19/20/21 取决于口径；更关键的是 factory 且零逻辑的 surge 样本我复算只有 3 张，而 `docs/10:262-270` 说"19 张、6 张零逻辑"。若 A 组要求"无逻辑可对比"，样本只有 3 张，E2 的 A 组可能不够用。
4. **"3 台耗电 kiln"是笔误还是另有含义**。若是"5 台里只有 3 台接了电"，那 metaglass-2 本身有 2 台 kiln 是死重，用它做 E1 样本要重新评估。
5. **E2 的 1/s 是不是笔误**。我按 0.8/s 处理；若目标确实是"≥1/s"，机队、面积、电力、语料样本量都要重算，不只是改个数。
6. **是否允许沙盒方块**（item-source / power-source）参与"真机验证"。这决定 E1/E2 的结论能否算"生产"，也决定 15 个"发电机"里要不要剔掉 power-source。文档没表态。
7. **钛合金 → surge-alloy 的映射**是否被项目书作者接受。MBO.md 第七节写的是"钛合金"，游戏里没有该物品；`README.md:22` 自行映射，无确认记录。
8. **833 / 831 / 829 三个分母**。2 张超 128 上限、2 张解析失败、8 张缺方块文件，统计分母在各文档不同（`README.md:16` 用 833，`docs/10:18` 用 831）。剔除哪些、剔除后哪些结论要重算，需定一次并写进 00 的口径表。
