# M04 I/O and sensing

## In one sentence

mlog has only five proper channels for "reading the world": **sensor** (read an attribute), **radar** (find a unit), **ulocate** (find a building/ore/spawn point), **getlink** (get a link handle) and **lookup** (resolve content from a numeric id), plus **read** for memory blocks.

## Rules / formulas

### 1. Master table of argument order (text slots)

| Instruction | Text form | Output slot | Key token |
|---|---|---|---|
| sensor | `sensor <result> <object> <attribute>` | 0 | the attribute is an LAccess name or a content name |
| read | `read <result> <memory block> <index>` | 0 | index 0..31 (world 512) |
| write | `write <value> <memory block> <index>` | none | out of range is silently dropped |
| radar | `radar <t1> <t2> <t3> <sort> <building> <order> <result>` | 6 | RadarTarget×3 / RadarSort |
| ulocate | `ulocate <mode> <flag> <enemy> <ore> <outX> <outY> <found> <outBuild>` | 4,5,6,7 | LLocate / BlockFlag |
| getlink | `getlink <result> <index>` | 0 | 0..@links-1 |
| lookup | `lookup <type> <result> <id>` | 1 | ContentType token |

The third slot of `sensor` is the "attribute": for an engine attribute write the `@` name (`@enabled`, `@health`); for a content count write the content name (`@copper`).

### 3. The radar and uradar enums

| Enum | Values |
|---|---|
| RadarTarget (8) | any, enemy, ally, player, attacker, flying, boss, ground |
| RadarSort (5) | distance, health, shield, armor, maxHealth |

`radar` produces only **1** result (slot 6 is the sort direction `1`/`-1`, not a count). `uradar` is the same, and **its slot 5 is passed as null in the source, so it is a dead slot** (whatever you write changes nothing).

### 4. ulocate

| Mode (LLocate) | Meaning | Which outputs it writes |
|---|---|---|
| ore | find ore | only found (+ the coordinates on success) |
| building | find a building (by BlockFlag) | found / build / coordinates |
| spawn | find a spawn point | same as above |
| damaged | find a damaged building | same as above |

BlockFlag has 18 entries: core, storage, generator, turret, factory, repair, battery, reactor, extinguisher, drill, shield, launchPad, unitCargoUnloadPoint, unitAssembler, hasFogRadius, steamVent, blockRepair, synced.

**The trap on failure**: on a failed search `outX/outY/outBuild` are not written ⇒ they keep their old values; only `found` is always written.

### 5. getlink and lookup

- `getlink`: index `0..@links-1`, returns the linked object; out of range or unbound returns null (it does not crash).
- `lookup`: the first slot is a ContentType token (item/block/liquid/unit/…); it resolves a content object from a numeric id, and an invalid id returns null.

## Measured facts and counter-examples

- ✅【E】an unknown attribute name raises no error; it writes null into the result variable (overwriting the old value) — S-16.
- ✅【E】an unbound link name used as a sensor target ⇒ null (S-17).
- ✅【E】a building name (instead of an attribute name) in the third slot ⇒ null (S-15).
- ✅【E】@velX/@velY do not exist; the correct attributes are @velocityX/@velocityY (L2-24).
- ✅【E】radar slot 6 is the sort direction ±1, not a count; there is one output at a time (L2-17).
- Counter-example (a boundary that does not hold): **"a failed ulocate writes 0 into the coordinates" does not hold** — on failure nothing is written, so the coordinates are last call's values, a common source of race bugs.

## Common misconceptions

1. "sensor can read any field." — it reads only the 77 LAccess attributes plus content counts.
2. "radar can return several units at once." — it cannot; there is only 1 result slot.
3. "uradar slot 5 must be 0 to mean no limit." — that slot is dead; nothing you write matters.
4. "An out-of-range getlink errors." — it returns null.
