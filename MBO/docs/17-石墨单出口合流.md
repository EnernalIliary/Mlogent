# 17 · 石墨单出口合流（以及“1×1 容器 / 物品黑洞”）

> 目标（用户 m01897 / m01911）：石墨产线**只保留一个出口**，看能不能进一步压缩；
> 顺带确认“1×1 容器”和“物品黑洞”能不能用。
>
> 结论先说：**原版没有 1×1 容器**；1×1 的 `item-void`（物品黑洞）可以用，而且是最省的
> 单出口方案（13 tiles），但它是沙盒方块、产物被销毁，计量要换口径。已经做成
> `mbo gen --merge void`，真机 1.359/s，与容器方案持平。

## §0 结果（石墨 1/s，1800 tick，真机）

| merge | 出口 | 方块 | 格数 | 真机速率 | vs 预测 1.333/s | 判定 |
|---|---|---:|---:|---:|---:|---|
| `pair` | 每台 1 个 container | 6 | 18 | 1.3569/s | +1.8% | PASS |
| `single` | 合用 1 个 container | 6 | 15 | 1.3191/s | −1.1% | PASS |
| `vault` | 合用 1 个 vault(3×3) | 5 | 19 | 1.3591/s | +1.9% | PASS |
| `core` | 合用 1 个 core-shard(3×3) | 5 | 19 | 1.3591/s | +1.9% | PASS |
| **`void`** | 合用 1 个 item-void(1×1) | 7 | **13** | **1.3591/s** | **+1.9%** | PASS |

- 与 cells 老模板（10 blocks / 22 tiles / 1.367/s）比：`void` 方块 −30%、格数 **−41%**，吞吐持平。
- 五种方案都通过静态校验、`verify` 重编码 body 逐字节一致。
- `void` 的速率由**周期计数**测得（黑洞销毁产物，容器差分恒为 0）；同拓扑 `vault`
  的容器读数是 1.3591/s，两者完全一致 ⇒ 计量口径可信（交叉验证）。

## §1 先回答两个问题

### 1×1 容器：原版没有

| 方块 | 尺寸 | 容量 | 说明 |
|---|---|---|---|
| `container` | 2×2 | 300 | 最小存储 |
| `reinforced-container` | 2×2 | 160 | 同上 |
| `vault` | 3×3 | 1000 | |
| `core-shard` | 3×3 | 4000 | 核心，可当出口 |
| `router` / `duct` / `junction` / `unloader` | 1×1 | 1 / 1 / 10 / 0 | 不是存储 |
| `item-void` | 1×1 | — | 物品黑洞（沙盒方块） |

所以“1×1 容器”只能退而求其次：要么用 **1×1 物品黑洞**（收下即销毁），
要么用 2×2 容器换位置省格。

### 物品黑洞可以用（带两个前提）

`item-void`（`ItemVoid`）size 1、`category=distribution`，与 `item-source`、`power-source`
同属**沙盒方块**：编辑器/沙盒里能直接放，正式战役里造不出来。本项目 D3 已经允许
沙盒电力（`power-source`），所以按同一口径接受 `item-void`，但要在产物里写明：

1. **产物被销毁** → 不能再用容器差分计量，改用周期计数（§3）；
2. **必须错开门直行位**（§4），否则门会把物料直接推进黑洞、压机饿死。

## §2 三种“合流到一个出口”的几何

主干仍是 split 模板（docs/16）：`item-source` → 物流门 → 左右两台压机。
机器底边在 `gy+s-1`，出口放在 `ey=gy+s` 这一行：

```text
single（2×2 容器 + 1 条带）        vault/core（3×3，两侧直贴）
  S                                S
 MM+MM                            MM+MM
 MM MM                            MM MM
  C>                             [VAULT]
15 tiles / 6 blocks               19 tiles / 5 blocks

void（1×1 黑洞 + 2 条带）
  S
 MM+MM
 MM MM
  >x<                            13 tiles / 7 blocks
```

- `vault`/`core` 3×3 中心放在 `(tx, gy+3)`，顶行同时贴住两台机器底边（零带子）；
- `single` 2×2 中心 `(tx-1, ey)`：西机直贴，东机 1 条 `rot=W` 的带子送进来；
- `void` 1×1 在 `(tx, ey)`：两侧各 1 条带（西 `rot=E`、东 `rot=W`）。

`single` 虽然只多省 3 格，却比 `vault` 慢 3%（1.319 vs 1.359）：带子上常驻 1 件货，
而计量是“窗口首尾容器件数差”，1 件货 = 0.04/s 的量化误差；本身不亏产能。

## §3 计量口径：不要信“总产量”字段

`GenericCrafter` 里能读的量只有三个：`efficiency`（效率）、`progress`（当前周期进度，帧）、
`totalProgress`。**`totalProgress` 不是件数**——源码是 `totalProgress += warmup * Time.delta`，
按“活跃 tick”累计，和产出件数无关，不能当计数器。

黑洞出口下的正确口径是**周期回绕计数**：

- 每 0.3 s 采一次 `progress`，相邻两样本 `b < a - 0.5` 即认定完成 1 个周期；
- 产量 = Σ(回绕次数 × 每周期产出件数)，再除以窗口秒数；
- 采样间隔 18 tick ≪ 周期 90 帧（1.5 s），不会漏计；机器停转时 progress 不动，不会误计。

`engine.summarize` 现在同时给 `rate_containers` / `rate_cycles`，出口有容器时优先用容器，
`measured_by` 字段记录用了哪一种。交叉验证：`vault`（容器 1.3591）≈ `void`（周期 1.3591）。

## §4 为什么黑洞不能放在门正下方

物流门的“直行位”是穿过门之后的下一格 `(tx, gy+1)`。若黑洞放在那里：

- `overflow-gate`（直行优先）：物料全部直接推进黑洞 → 两台压机都饿死；
- `underflow-gate`（两侧优先）：两侧压机都收时才直行，一般没事，但一旦两侧堵住就会开始销毁物料。

所以模板把黑洞放在 `(tx, gy+2)`，走**两侧带子**进去，门的直行位始终空着。
这条约束由模板本身保证，单元测试 `test_void_not_on_gate_forward` 会守着它
（门直行位必须是空格、两侧带子朝向分别是东/西、黑洞恰好在正中）。

## §5 命令与产物

```bash
cd MBO
python -X utf8 -m mbo gen "graphite:1/s" --boundary coal --layout split --merge void
python -X utf8 -m mbo verify m-void          # 重建 + 重编码字节一致
python -X utf8 -m mbo preview m-void         # PNG / --ascii
```

- `runs/m-void/`：7 建筑 / 13 格，粘贴码可直接进游戏；
- 产物仍是 docs/03 定义的 5 件（blueprint.msch / .b64.txt / metrics.json / report.md / trace.json）；
- `metrics.json` 的 `engine.metrics.measured_by` 会写 `containers` 或 `cycles`。

## §6 建议

| 场景 | 选哪个 | 理由 |
|---|---|---|
| 只求最省格数的“最优蓝图” | `void` | 13 格，吞吐不降；沙盒方块、产物销毁 |
| 要能计量、要贴近正式玩法 | `core` | 3×3、可读 `core.items`、产量精确，真实产线也这么接 |
| 要能反复用蓝图（不依赖沙盒） | `vault` / `pair` | vault 省 1 个方块，pair 最直观 |
| `single` | 不推荐 | 省 3 格但引入带子与 3% 的计量噪声，性价比低 |

下一步可做：把“出口选择”推广到多输入产线（硅/玻璃），并给 `merge` 加“每对 vs 全产线共用”两种粒度。

## §7 更小的方案（→ docs/18）

`void` 的 13 格仍不是极限。把 `item-source` / `item-void` 当作蓝图的**输入/输出标记**（I/O port）后，
连门和带子都可以去掉：源与黑洞各占一个“同时与两台机器相邻”的格子，得到 **10 格 / 4 方块 / 5×2** 的
`--layout direct` 模板（实测 1.3589/s，+1.9%），并附“不可能 <10 格”的下界证明——见 `docs/18`。
本文的 §4（黑洞不能占门直行位）只约束 `split` 模板，`direct` 没有门，不受影响。
