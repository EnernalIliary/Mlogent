## 修复与行为边界

- 启动失败（包括 `SystemExit`）统一清理；关闭可重复调用，等待进程退出，必要时强制结束，回收 Windows job、管道和日志。清理失败记录在 `cleanup_errors`，不遮蔽原启动异常。
- stdout pump 异常设置 EOF 并通知等待者。
- JS 结果持续不可读时按预算报超时，并附近期 stdout，不再返回空成功；轮询使用单调时钟。
- 无场景文件、仅投影单位影子时也初始化锚点，修复 `ax/ay` 未赋值。
- 日志板使用世界对象的数据目录；查询/编辑/蓝图/门的目录与审计依赖显式传入。
- 默认 reset 仍走 nextmap/gameover；只有 hard reset 才 stop/host。单位镜像保留安装前后两次代次检查与停止时两次清扫。

## 后续收敛方案

当前不宜继续按单个操作新增文件。已有业务模块足够，剩余问题主要在路由、依赖装配和生命周期。

### 1. 完成剩余路由

- `scene/scene_probe` 执行并入现有场景模块，与 feed/布局函数区分清楚。
- `tap` 交互归入门模块；console/js/say/pause/save/load/shutdown 作为应用控制命令集中处理。
- 建立一张可校验的操作注册表，检查重复注册、未知操作和 MCP/客户端兼容性；替代主模块不断增长的分支链。

### 2. 集中运行期和启动装配

- 以明确的配置对象统一 ROOT、数据/日志/审计、蓝图/门、握手文件路径和启动参数。
- 用具名服务对象替换 `SimpleNamespace(**globals())`，在装配处绑定实际业务服务；业务模块不回查启动模块。
- 统一管理 JVM、TCP、投影导演和 feed 监听线程的停止/等待，避免只回收 JVM 而后台线程仍在运行。
- 将 CLI 参数解析与启动装配移出兼容入口。`world_server.py` 最终保留启动和旧接口导出，保留命令行、握手格式与旧客户端行为。

这一步最多按运行期、CLI/路由的真实职责增加模块，不继续为每条命令拆文件。

### 3. 整体验收与整理

- 执行整仓门禁、隔离世界端到端与发布包解包验证，单独记录环境跳过项。
- 验证启动失败清理、关闭期间请求、线程退出、多槽投影和旧客户端调用。
- 通过后再统一整理导入、长依赖列表和提取遗留空行；避免格式清理与行为迁移混在同一差异中。
- 不因本轮拆分完成而直接删除兼容入口；先明确调用方和弃用策略。
