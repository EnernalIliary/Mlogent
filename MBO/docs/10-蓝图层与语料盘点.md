## 1. `.msch` 容器格式要点

格式在 `tools/msch.py` 顶部有完整注释（:1–50）。对照 Java 实现（本仓库 `Mindustry-Source` 为 v159.x，格式与 v160.7 一致）：

### 1.1 外层

```
"msch" (4 bytes)  +  version (1 byte)  +  zlib(deflate) 压缩的 body
```

- header 逐字节比对：`Schematics.java:543-548`；version 字节读于 `:550`，`> version(=1)` 直接抛 "Unknown version"（`:51`, `:552`）。
- `tools/msch.py` 对应：`MAGIC = b"msch"`（:52）、`parse_bytes`（:361）。
- 语料实测：version=1 有 830 个，**version=0 有 1 个**（`acoaco-schematics/surge_合金/surge1_fromcore.msch`）。v0 是老格式，tile 的 config 是裸 `int` 而不是 TypeIO 对象（见 §1.3）。

### 1.2 body 结构

| 顺序 | 内容 | 源码 | msch.py |
|---|---|---|---|
| 1 | `width, height`（int16 ×2） | `Schematics.java:555` | `parse_bytes` |
| 2 | `tagCount`（uint8）+ tagCount × (`UTF key`, `UTF value`) | `:560-563` | – |
| 3 | `blockDictLen`（uint8）+ blockDictLen × `UTF 方块名` | `:589-594` | – |
| 4 | `totalTiles`（int32） | `:596` | – |
| 5 | 每个 tile：`blockIndex`（int8）+ `position`（int32，`Point2.pack(x,y)`）+ `config`（TypeIO object）+ `rotation`（int8） | `:604-607` | `Stile`（:186） |

关键细节：
- **tags 里有两个特殊键**：`labels`（JSON 字符串数组，分类标签，`:581-586`）和 `contentMap`（JSON，`{contentType.ordinal: {name: id}}`，用于把 config 里的 Content id 重映射到本版本，`:568-578`）。**语料里没有一张图带 `contentMap`**，只有 `name`(831)/`description`(830)/`labels`(770)/`steamid`(11)。
- **方块字典按"首次出现顺序"去重**（`write` 用 `OrderedSet<Block>`，`:655-656`），不是按 id 排序；读写往返后字典顺序可能变化。
- **空气 tile 不入 tiles**：`if(block != Blocks.air)` 才 add（`:608-610`），msch 同样跳过（:417-418）。所以"面积 − tile 占用"要靠方块 size 补算。
- **旧方块名有 fallback**：`SaveFileReader.fallback.get(name, name)`（`:592`），找不到或 LegacyBlock 一律降级成 `air`。这就是语料里 `alloy-smelter` 的来源（老版本名）。
- **游戏侧硬上限**：`limitSchematicSize = true`（`:52`），读入时 `width > 128 || height > 128` 抛错（`:557`），`total > 128*128` 抛错（`:598`）。**语料里有 2 张违反**（§3.5）。
- 写回时游戏**强制**写入 `labels` 与 `contentMap` 两个 tag（`:633`, `:643`），我们的写回器不需要跟（保留原 tags 即可，往返实测一致）。

### 1.3 config 的 TypeIO 编码

config 是 `TypeIO.writeObject` 的产物（`TypeIO.java:42-155`，读 `:157`+）：

| tag | 类型 | 线格式 | 语料中出现次数 |
|---|---|---|---|
| 0 | null | 1 字节 | 43772 |
| 1 | Integer | int32 | 274 |
| 3 | Float | float32 | 2 |
| 4 | String | bool 存在位 + UTF | 1465 |
| 5 | Content | byte contentType + short id | 15253 |
| 7 | Point2 | int32 x + int32 y | 14136 |
| 8 | **Point2[]** | byte 长度 + packed int ×n | 3266 |
| 10 | Boolean | 1 字节 | 452 |
| 11 | Double | float64 | 2 |
| 14 | **byte[]** | int32 长度 + 原始字节 | 1477 |
| 6/16/18/21/22 | IntSeq / bool[] / Vec2[] / int[] / Object[] | 见 TypeIO | 0（语料未出现） |

- 全部出现过的类型合起来只有 **10 种 tag**。语料没出现的不代表不会出现（MBO 生成器要能写：难度不大，TypeIO 全 24 种都能实现）。
- **tag 5 Content 的 id 是"该 contentType 内部的 id"**：`item` id 对照 `data/game/items.json`、`liquid` 对照 `liquids.json`、`block` 对照 `blocks.json`、`unit` 对照 `units.json`。msch 只解出 `{"__content__": "item", "id": 12}`——**不翻译成名字**，调用方必须自己查表（这一点很容易踩，见 §6.3）。
- **tag 14 byte[] 用在逻辑块上** = 逻辑载荷（§1.4）；也可以出现在别的方块（如 message 用 String，不是 byte[]）。

### 1.4 逻辑块的内层载荷（第二层 zlib）

逻辑方块（`micro-processor` / `logic-processor` / `hyper-processor`）的 config 是 byte[]，里面又是**一层 zlib**（`LogicBlock.java:141-158` 写、`:279-325` 读；msch `parse_logic` :322）：

```
version (uint8)            # 逻辑格式版本，0 或 1
byteLen (int32) + bytes    # UTF-8 汇编源码（LAssembler.write 的一行一条语句）
linkCount (int32)
linkCount × { UTF name, int16 x, int16 y }   # 链接：名字 + 坐标（v1 相对处理器自身，v0 绝对且被游戏忽略）
```

- 语料实测：**1477 个逻辑块（=1254 micro + 167 logic + 56 hyper），全部内层 version=1**，没有 v0。
- 链接总数 **6210**；语句总量 **421,269 行**，其中单个蓝图 `foxitOS-CMD-pack/schematics/1625479455558.msch` 独占 **313,839 行 / 322 条链接**（占了语料 74%）。
- 上限：压缩后 16000 字节（`maxCompressedLen`，`LogicBlock.java:37`）、6000 条链接（`:38`）。

## 2. `tools/msch.py` 能力边界（实测）

### 2.1 能做什么

- `parse_file` / `parse_bytes` / `parse_base64` / `decode_variant`：全 24 种 TypeIO tag 都能读（`_read_object` :224），**解析层零缺陷**——831 张图全部复现了坐标/旋转/config。
- 结构访问：`logic_tiles()`(:214)、`block_counts()`(:217)、`name`/`description`(:207/:211)、`labels`。
- 逻辑载荷：`parse_logic` 解出版本、源码行、链接表（含相对坐标换算）。
- `build_schematic`(:462)：能写回"config 是 null/bool/int/float/str/bytes/content/point"的 tile。

### 2.2 不能做什么（写完回必须补的）

| # | 缺陷 | 位置 | 影响 |
|---|---|---|---|
| 1 | **数组 config 不能序列化**（`list` 直接抛 `cannot serialize config of type list`） | `_write_object` :492（分支只覆盖 7 种） | **601/831 蓝图写不回去**——所有带 `power-node`/`beam-link`/`power-source`（Point2[]）和 IntSeq 的图 |
| 2 | 解析时**丢掉了 TypeIO tag 号**，写回只能猜 | `_read_object` :224 | tag 8 vs tag 21、float vs double 无法区分；语料里 3266 个 tag8 + 2 个 float + 2 个 double 受影响 |
| 3 | `_pack_point` 用 `struct.pack(">i", ...)`，x ≥ 0x8000 会 `struct.error` | :318 | 极端坐标（负/超大）崩溃 |
| 4 | `raw_config` 只对逻辑块的 byte[] 填充 | :427-429 | 不能靠"原样回吐 config 字节"绕过 1、2 |
| 5 | 不生成 `contentMap`/不强制 `labels` | — | 与游戏 `write` 行为不一致（游戏会强制写），但读回来语义等价，实测无影响 |
| 6 | 不检查 128×128 / 16384 tile 上限 | — | 会把游戏拒收的蓝图当合法（§3.5） |
| 7 | 不校验 tile 重叠、不做方块尺寸占位 | — | 空间/合法性检查必须由 MBO 自己做 |
| 8 | 不解释逻辑指令语义 | 只有文本行 | mlog 语义分析要另建（不在本层职责内） |

### 2.3 往返实测（最重要的表）

方法：解析 → 写回 → 再解析 → 比对 `(block, x, y, rotation, config)` 多重集 + 宽高，再比对**未压缩 body 是否逐字节相同**（最硬的保真证据）。

| 写回实现 | 通过 | 失败原因 |
|---|---|---|
| `msch.build_schematic`（原样） | **230 / 831 = 27.68%** | 601 张全是 `serialize: MschError: cannot serialize config of type TaggedList` |
| **自写 `build_schematic_ext`**（本调研补的：补全 24 种 tag 且保留原 tag 号） | **831 / 831 = 100%** | 无 |
| body 逐字节相同 | **830 / 831 = 99.88%** | 唯一差异 `acoaco-schematics/surge_合金/surge1_fromcore.msch`：body 302 → 242 字节，原因是原文件方块字典有 6 项但只用到 4 个（写回按"首次出现"重建字典，丢弃未用项）——语义等价，且它就是唯一的 version=0 文件 |

> 实现要点（可直接搬进 MBO）：在 `MBO/spikes/bp/scan_corpus.py` 的 `build_schematic_ext` / `_write_object_ext` 里，**运行期 monkeypatch 读侧**给顶层 config 打 tag（`TaggedList` / `TaggedDouble`），写侧按 tag 还原：tag8 = byte 长度 + `struct.pack(">I", packed & 0xFFFFFFFF)`（绕开 :318 的溢出）、tag6/21 = short 长度 + int32、tag16 = int 长度 + bool、tag18 = short 长度 + 2×float、tag22 = int 长度递归。
> 若后续要"从根上修"，可让 gate 的持有人给 `tools/msch.py` 加数组分支（位置就在 `:492 _write_object` 的 `isinstance(obj, dict)` 之后补 `isinstance(obj, (list, tuple))` 分派到 tag 8/6/21）——但**本调研按约束没有改 tools/**。

### 3.2 分类启发式（脚本里 `FACTORY_SHARE_THRESHOLD = 0.75`）

把每个方块按 `blocks.json` 的 `category` 归桶：

- `prod` = production + crafting（钻机/冶炼/混合机/压机…）
- `logi` = distribution + liquid（传送带/桥/路由器/管道…）
- `power` = power（电力节点/电池/发电机…）
- `logic` = logic（处理器/显示器/开关/内存…）
- `other` = defense/turret/units/effect/未知

`share = (prod + logi + power) / tile 总数`：
- `share == 0` → **logic**（只有逻辑件和小杂件）
- `share ≥ 0.75` → **factory**
- 其余 → **hybrid**
- 解析失败 → **unparsed**

结果：**factory 574 / hybrid 180 / logic 77 / unparsed 2**。这个阈值把"处理器 + 一点点传送带"的图判成 hybrid 而不是 factory，符合"MBO 关心的是生产/物流/电力主体"的取向；阈值是常量，想更严可以调到 0.85（工厂型会降到约 5xx，未实测）。

已知误判（6/77）：`logic` 桶里有 6 张**没有任何逻辑块**，是"墙体/文字像素画"（`share=0` 被划进来），例如 `foxitOS-CMD-pack/schematics/1681812719599.msch`（75×65 / 3569 tiles，全是 `copper-wall`，就是 §3.3 表里"逻辑型 tile 最大 3569"那张）。MBO 若要用"逻辑型"做 mlog 训练集，需再加 `n_logic_tiles > 0` 过滤；本报告 `files[]` 已逐图给出 `n_logic_tiles`，可直接筛。

## 5. 对 MBO IR 设计的建议

**结论：`tools/msch.py` 复用为 codec（read 全用、write 暂不用），MBO 侧建统一 `Blueprint` IR，唯一真相是 IR，`msch.Schematic` 只出现在 IO 边界。**

理由：①msch 解析已验证、零缺陷、纯只读、符合"规则用程序建模"；②它的数据结构没有 layer 分离（坐标/旋转/config 混在 `Stile`，统计靠临时函数），而 MBO 需要 topology/partition/statistics 多层；③写回缺 5 项能力，硬改会动 tools/（gate 禁止）。

### 5.1 草案（签名级）

```python
# MBO/blueprint/model.py
from dataclasses import dataclass, field
from typing import Literal, Union

# ---------- 序列化层：与 .msch 一一对应，可无损写回 ----------
@dataclass(frozen=True)
class ConfigValue:
    """config 的原始 TypeIO 形态。tag 必须保留，否则写回不合法。"""
    tag: int                      # TypeIO tag（0/1/3/4/5/7/8/10/11/14/…）
    value: object                 # null→None；content→(ctype, id)；point→(x,y)
                                  # point_array→tuple[(x,y)…]；byte_array→bytes

@dataclass
class Tile:
    block: str                    # v160.7 规范名（已过 fallback 表）
    x: int                        # 中心格坐标（≠ 左下角）；origin = (x-(size-1)//2, y-(size-1)//2)，见 §6.4 与 docs/13 §2.2
    y: int
    rotation: int                 # 0..3
    config: ConfigValue | None
    logic: "LogicPayload | None"  # 逻辑块专用：version / code / links

@dataclass
class LogicPayload:
    version: int
    code: str                     # 汇编源码，一行一条
    links: list["LogicLink"]      # (name, rx, ry) 相对处理器坐标

@dataclass
class Blueprint:
    width: int
    height: int
    tiles: list[Tile]
    tags: dict[str, str] = field(default_factory=dict)   # name/description/steamid
    labels: list[str] = field(default_factory=list)
    source: "SourceInfo | None" = None                   # 文件路径 + 版本字节 + sha256

# ---------- 派生层：只读视图，不进序列化 ----------
    def occupancy(self) -> "Grid": ...          # (w,h) 每格 占位方块 index / -1
    def counts(self) -> dict[str, int]: ...
    def rect(self) -> tuple[int, int, int, int]: ...
    def block_size(self, name: str) -> int: ...  # 来自 GameData

# ---------- 语义层：把 config 解释成 graph，供 Solver ----------
@dataclass(frozen=True)
class Link:
    src: int                      # tile 下标
    dst: int | None               # 解引用成功则是下标；外部/越界则 None
    kind: Literal["item", "liquid", "power", "logic", "point"]
    raw: object                   # 原始 config，便于回溯

@dataclass
class BlueprintGraph:
    bp: Blueprint
    links: list[Link]             # bridge/power-node/logic link 全部解引用
    ports: dict[str, list[int]]   # 产物/原料/液体的进出口 tile
```

### 5.2 config 分派表（IR 解析必须按方块分派，不能"看类型猜"）

| 方块类 | 读取时 | 写回时 |
|---|---|---|
| sorter/unloader/duct-router/item-source/liquid-source/constructor/payload-source | tag 5 → `(ctype, id)` → 查 `items/liquids/units/blocks.json` 得名字，**存名字+id 双份** | 名字→当前版本 id，tag 5 |
| bridge*/mass-driver | tag 7 → 先判定是"绝对世界坐标"还是"相对偏移"（语料两种都有，见 §6.4），存 `(x, y, is_relative)` | 按原样写 tag 7 |
| power-node*/beam-link/surge-tower/power-source | tag 8 → 相对偏移列表 | 重算偏移后写 tag 8（byte 长度 + packed） |
| message/reinforced-message | tag 4 String | tag 4 |
| 逻辑块 | tag 14 → 内层 zlib → `LogicPayload`；写回用 `build_logic_data`（msch 已有） | tag 14 |
| switch/door | tag 10 bool | tag 10 |
| 单位工厂/照明 | tag 1 int / tag 11 double | 原 tag |
| 其余 | tag 0 | tag 0 |

### 5.3 落地建议

- `MBO/blueprint/io.py`：`load(path) -> Blueprint`（调 msch + fallback 名映射 + Content id 解析）、`save(bp, path)`（**自写 writer**，把 `MBO/spikes/bp/scan_corpus.py` 的 `build_schematic_ext` 抽出来做正式实现）。
- 解析结果要"自检"：`save(load(x))` 后 body 比对，作为 CI 门禁（本调研已证明可达 99.88% 逐字节一致，剩下 1 张是词典未用项，可豁免）。
- 生成侧只从 IR 出发，禁止直接拼字节；写回前调用 Validator 检查 128×128 / 16384 tile / 重叠 / 未定义方块。

## 6. 风险与坑清单

### 6.1 版本混杂
- `.msch` 版本字节有 0 和 1 两种（v0 的 config 是裸 int，`mapConfig` 做映射：`Schematics.java:672-679`；v0 的 MassDriver/ItemBridge 存的是**相对偏移**）。MBO 读到 v0 必须走 `mapConfig` 等价逻辑，否则 config 全错。语料里只有 1 张 v0。
- 旧方块名靠 `SaveFileReader.fallback` 翻译（`:592`）；我们手上没有这张 fallback 表，**建议从 `Mindustry-Source` 抽取成 `data/game/legacy_names.json`**（`alloy-smelter`、`thermal-pump` 是已知的两项）。在没表之前：解析时保留原名、标记 `unknown_block`，生成时禁止使用。
- Content id 是"作者版本"的 id：没有 `contentMap` 时游戏按当前版本的全局 id 解释（`Schematics.java:568-578` 只在有该 tag 时才重映射）。语料实测 0 越界，但**这是巧合而非保证**——MBO 必须在 load 时校验每个 `(ctype, id)` 并在越界时报错，而不是静默错位。

### 6.2 尺寸上限
游戏读入硬限制 128×128、16384 tiles（`Schematics.java:52,557,598`）。语料 2 张违反。**MBO 的 Validator 必须先判这两条**，否则生成的图在游戏里加载失败。

### 6.3 config 语义与"同名不同类型"
- 同一个 tag 在不同方块上含义完全不同（tag 5 可能是 item、也可能是 liquid/unit/block；tag 7 在 bridge 上是目标格、在别处可能是相对偏移）。**必须按"方块类型 → config 类型"分派**（§5.2），不能只靠 tag。
- `sorter` / `inverted-sorter` 的 config 可以是 null（698 + 1253 次）——null 表示"不过滤"，不是"未配置错误"。
- 逻辑块的 byte[] config 与"普通 byte[]"无法从 tag 区分，只能靠"方块是否 LogicBlock"判断。

### 6.4 坐标与旋转约定
- **锚点**：`Stile.x/y` 是方块的 **footprint 中心格**（⚠️ 早期稿写"origin=左下角"，已被 `docs/12` §补C 的真机实测推翻；源码 `Schematics.java:432` 用 `tile.tileX()/tileY()` 给人"原点"印象，但运行时放置以中心格为准）。来源：`Schematics.java:432` 用 `tile.tileX()/tileY()` + 相对偏移；`create()` 里 `offsetX = -minCorner`（`:419-420`）保证蓝图坐标从 (0,0) 起、**y 向上增长**（Mindustry 世界 y 向上）。
- 多格方块占 `[x, x+size-1] × [y, y+size-1]`；生成时若按"中心"放会整体偏半格——这是最容易出的 off-by-one。
- **rotation** 是 0..3 的字节，顺时针递增（0=上/北、1=右/东、2=下、3=左）；不响应旋转的方块（墙、存储器）该字节无意义但必须写出（游戏 `write` 原样写 `:664-666` 区间的 `writeByte(rotation)`）。
- **bridge/mass-driver 的 Point2**：语料中 2327/6552 落在蓝图 bounds 内、4225 在外（例如 `multi_binding/Eco/wireless_1plast(water).msch` 里出现 `(-4,0)`、`________________________` 类文件里出现 `(-267,-244)`）。说明**导出时保留了原世界的绝对坐标，而不是蓝图相对坐标**；`power-node` 的 Point2[] 才是相对偏移。MBO 若做链接语义，必须：①按 `point ∈ bounds` 判定"内部链接"，②外部链接标记为 `external` 并禁止参与优化，③自己生成时统一用相对/绝对中的一种并写测试固定下来。**这一条需要真机放置一次确认（运行时 `BuildPlan.pointConfig` 会做平移：`entities/units/BuildPlan.java:88-104`）——列为待验证项。**

### 6.5 数据质量
- 2 个文件损坏（§3.1），扫描脚本必须容错并把失败明细写进报告，别让 1 个坏文件中断全量。
- 存在 `air` tile（被解析器丢弃，`files_with_air` 见 json），存在 tile 重叠（像素画式蓝图），**不能假设 tiles 覆盖不重叠**。
- 覆盖率高的图（0.9559 中位）说明人类样本接近满铺；MBO 若以"空间利用率"为目标，**要先用本语料的分布当 Pareto 基线，否则指标会显得离谱**。

### 6.6 工程坑
- Windows 下 `python -c "中文"` 会乱码 → 一律写成 `.py` 文件，用 `python -X utf8 脚本.py` 跑（本脚本即如此）。
- 路径含中文（`F:\OneDrive\桌面\AtomicStates`）：`pathlib`/`json.load(open(..., encoding="utf-8"))` 都已实测可用；`subprocess`/`glob` 里用绝对路径最稳。
- `tools/`、`data/`、`logic-corpus/` 只读；gate.py 会校验 `tools/` 副本一致性，本调研**未修改任何既有文件**，新增文件仅 `MBO/spikes/bp/scan_corpus.py`、`MBO/spikes/bp/corpus_report.json`、本文件。
