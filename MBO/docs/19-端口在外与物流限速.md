# docs/19 · 端口在外 + 物流限速：石墨蓝图的三条新下界

> 起点是用户 m02384 的两句话：**「限制输入和输出标记只能在绘制区域外。并且速率由物流元件决定。」**
> 以及 m02395：**「能脚本化的推理都脚本化试一下」**——所以本文件的每条结论都有脚本产出，
> 不是手算：`spikes/gen/search_ported.py`（枚举 + 随机搜索）、`spikes/gen/probe_one_merge.py`
> 与 `probe_one_merge2.py`（真机反例）、`mbo/logistics.py`（容量网络最大流）。

---

## 0 结论：三条 Pareto 前沿（石墨 1/s，2 台压机）

`item-source` / `item-void` 从此只当**蓝图边界之外的输入/输出标记**，不再嵌进工厂内部。
三条候选都满足该口径，取舍在"端口少"与"工厂格少"之间：

| 端口方案 | `--ports` | 工厂格 | 端口数 | 方块 | 预测 | 真机 | 偏差 | run |
|---|---|---|---|---|---|---|---|---|
| 每台一进一出 | `both` | **8** | 4 | 6 | 1.333 | **1.2817/s** | −3.9% | `runs/p-both` |
| 单源经门 + 每台一出 | `gate` | 9 | 3 | 6 | 1.333 | **1.2865/s** | −3.5% | `runs/p-gate` |
| 单进单出（带→路由器→黑洞） | `one` | 12 | **2** | 8 | 1.333 | **1.3588/s** | +1.9% | `runs/p-one` |

三条全部 `eff_avg=1.0`、`eff_low=0`、`deadlock=false`、`verify` 重编码 body 逐字节一致。

**和上一代的关系**：`docs/18` 的 10 格 direct 蓝图（4 方块 / 10 格 / 5×2 / 1.359/s）在新口径下
**失效**——它的源与黑洞都嵌在工厂矩形内（`ports_outside=False`）。所以本文件不是"更小"，
而是"在把端口赶出工厂之后，重新求一次最小"。

## 1 两条口径怎么落成代码

### 1.1 端口在外（`logistics.ports_outside`）

工厂 = **非端口方块**的外接矩形；端口格只要落在该矩形内（含边界）就算违规。
`validate.static_check(..., strict_ports=True)` 把违规升级成 error；老模板默认只给 warning，
避免 `cells`/`split`/`direct` 的历史 run 全红。

`--layout ported` 的三个变体把端口一律放在工厂外框的**上下两排**（或侧排）：
输入标记贴机器顶边、输出标记贴底边，靠相邻关系直接投料/收货，不需要跨边界的传送带。

### 1.2 速率由物流决定（`mbo/logistics.py`）

一个物品一张图，做**容量网络最大流**（Dinic）：

- 每个方块拆成 `in` / `out` 两个节点；运输/节点方块（带、管道、路由器、交叉器、两种门）
  `in→out` 容量 `TILE_CAP = BELT_RATE = 4.9`；
- 传送带 `out` 只连**正前方**（方向性），卸货目标必须接受该物品；
- 门/路由器 `out` 可以连所有相邻运输方块，以及（`want="out"` 时）相邻汇点；
- 机器：`in` 方向 `in→T` 容量 = 每秒需求，`out` 方向 `S→out` 容量 = 每秒产出；
- 端口：`item-source` 从 `S` 取料（`SOURCE_CAP=100`），汇点 `in→T` 容量 1e12。

于是 `estimate()` 给出 `rate = min(machine_cap, rate_input_limited, rate_output_limited)`
和 `bottleneck`。**这条模型的意义**：任何"带子接错方向 / 门没接上 / 黑洞收不到货"的布局，
估值会是 0，而不是按机器台数硬算 1.333。

模型对历史 6 张图的复算（全部 est=1.3333、bottleneck=machine，真机 1.3191–1.3666）：

| run | 模板 | est | 真机 | 偏差 |
|---|---|---|---|---|
| `d10` | direct 10 格 | 1.3333 | 1.3589 | +1.9% |
| `g1` | cells | 1.3333 | 1.3666 | +2.5% |
| `g1-split` | split 门 | 1.3333 | 1.3569 | +1.8% |
| `m-void` | split + void | 1.3333 | 1.3591 | +1.9% |
| `m-vault` | split + vault | 1.3333 | 1.3591 | +1.9% |
| `m-single` | split + container | 1.3333 | 1.3191 | −1.1% |

## 2 枚举搜索：结果不是拍脑袋来的

`spikes/gen/search_ported.py` 在 9×7 网格上按四个维度组合：

1. 机器排布：两台机器的相对位置（水平/垂直）× 缝隙宽 0..3；
2. `bridges`：同时与两台机器正交相邻的格子（共用投料位/出货位候选）；
3. 输入方案：单源经桥接元件（门/路由器）分给两台，或每台一个源；
4. 出口方案：每台一个汇点，或单汇点 + 每台至多一条带子接力。

对每个候选先做 `ports_outside` 硬过滤，再用 `estimate` 算速率（要求 ≥ 1.3333、容差 1e-3）。
结果（工厂格数最小的前沿）：

| 端口数 | 工厂格 | 说明 |
|---|---|---|
| 4 | **8** | 每台机器各自一进一出，几何上就是 2s²，已经触底 |
| 3 | 9 | 单源经反溢门 + 每台一个黑洞（门占 1 格） |
| 2 | 12 | 单进单出：门 1 格 + 路由器 1 格 + 两条带子 2 格 |

**交叉验证**：随机撒 3000 张 / 命中 618672 个可行解，最优仍是 `(4 端口, 8 格)`——
结构化枚举没有漏解。2 端口方向的下界是 12：8 格机器 + 1 格门（把单源分给两台）
+ 1 格路由器（把两路产出一合） + 2 格带子（机器与合流点之间各 1 格），缺一不可。

## 3 一个反例：两级带子合流会被节流

最初的 `one` 变体是"机器下方三条带子合流：西 `E` → 中 `N` → 东 `W`，中间带子朝黑洞"。
`estimate` 说 1.3333，真机只有 **0.7952/s**（`eff_avg=0.573`，两台机器都饿）。
`spikes/gen/probe_one_merge.py` 的四组对照定位了原因：

| 布局 | 真机 |
|---|---|
| 三带合流（中带朝黑洞） | 0.7952/s |
| **两条带子直接指进同一个黑洞** | 1.3569/s |
| 三带合流但中间带子朝反方向 | 1.3544/s |
| 三带合流 + 容器（容器只贴西带） | 0.7956/s |

结论：**带子被侧向投料时会掉吞吐**，而"带子→黑洞/路由器"是正常通道。
`probe_one_merge2.py` 再验两种修法：`带→路由器→黑洞` = **1.2868/s（eff=1.0）**、
中间带子两侧各一个黑洞 = 1.3540/s。最终 `one` 变体选了路由器方案——
它同时满足"端口在外"（黑洞在路由器下方一格、工厂外框之外）。

这条反例说明当前模型的一个**已知盲区**：`logistics` 只算静态容量，不建模带子的
侧向投料节流；所以它对"带子合流"这类几何会高估（1.333 vs 0.795）。
判别口径：**估值与真机差 >5% 时，先怀疑侧向投料/合流，而不是怀疑机器**。

## 4 三个模板的几何

```
ports="both"（工厂 8 格）        ports="gate"（9 格）          ports="one"（12 格）
   S   S                              S                          S
  MM MM                             MM+MM                      MM+MM
  MM MM                             MM MM                     MM MM
   x   x                              x x                       >n<
                                                                  x
```

`S`=item-source（输入标记） `x`=item-void（输出标记） `+`=反溢流门 `n`=路由器 `>v<^`=带子朝向。
三个变体的端口都在工厂外接矩形之外：输入端在机器顶边之上，输出端在最底行之下。

## 5 复现

```powershell
cd MBO
python -X utf8 -m mbo gen graphite:1/s --boundary coal --layout ported --ports both --crop --out p-both
python -X utf8 -m mbo gen graphite:1/s --boundary coal --layout ported --ports gate --crop --out p-gate
python -X utf8 -m mbo gen graphite:1/s --boundary coal --layout ported --ports one  --crop --out p-one
python -X utf8 -m mbo verify p-one          # 重建 + 静态 + 重编码字节一致
python -X utf8 -m mbo preview --all         # runs/index.html 画廊
python -X utf8 spikes/gen/search_ported.py  # 枚举 + 随机搜索（脚本化推理）
python -X utf8 spikes/gen/probe_one_merge.py
```

CLI 的一行摘要会同时打印预测速率、静态结果、真机速率与 Gate 判定；
`trace.json` 里记了 `layout` / `ports` / `crop`，`reproduce` 字段给出完整命令。

## 6 适用边界

- 只支持**单输入、2×2、偶数台**的产线（`split_applicable`）；玻璃/硅这类双输入产线还没适配；
- 三个变体都假设"两台机器并排"；≤1 台或 ≥4 台时需要新的排布（端口方案会变）；
- `item-source` / `item-void` 是沙盒方块：蓝图在正常存档里能读，但要给源配物品、黑洞会销毁产物；
  这正是用户 m02107 定下的"它们是 I/O 标记"的口径；
- 电力：石墨压机不耗电，所以本文件的格数不含电力方块；耗电产线要加 `route_power` 的格数。

## 7 与 docs/18 的关系

`docs/18` 证明的是"端口可以嵌在工厂里时的 10 格下界"；本文件在"端口必须在外"的新口径下
重新求前沿（8/4、9/3、12/2）。两者不冲突：**换了约束就重新求一次下界**，这正是脚本化搜索
（m02395）的价值——约束一变，重跑搜索即可，不用重新推导。
