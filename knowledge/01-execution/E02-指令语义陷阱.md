# E02 30 instruction-semantics traps

## In one sentence

Almost every mlog trap grows from one root: **it has null (an object slot), and `num()` reads null as 0**; the rest fall into three groups — slot order, 1-tick timing, and hard caps. Each entry gives "wrong form → right form → why". [src: knowledge/VERSION.md:1]

## Rules / formulas

### A. Vectors / coordinates (4 items)

1. **Mixing coordinate units** —— ✗ using the result of `sensor x @unit result` directly as a tile → ✓ divide by 8 first (`op div result result 8`). Why: sensor x/y are world pixels and `tilesize=8`, while getblock/setblock take tiles.
2. **Reading radar slot 6 as a count** —— ✗ `radar enemy any any distance turret 5 result` → ✓ slot 6 takes only `1` / `-1` / `0` (sort direction), and there is a single output. Why: defs=[6]; slot 6 is the ±1 order.
3. **Putting something in uradar slot 5** —— ✗ hoping to reach the 6th parameter through slot 5 (the building filter) → ✓ that slot is dead: the source passes null and `buildFrom()` returns false. Why: of the 7 parameters, slot 5 takes no part in construction.
4. **Writing the coordinates first in getblock** —— ✗ `getblock result x y layer` → ✓ `getblock layer result x y`. Why: in the source layer is token 0; cmd_index.json has it wrong here (see instructions.json.meta.discrepancies).

### B. Objects / null (5 items)

5. **Testing "read empty" with `equal x 0`** —— ✗ → ✓ `jump ... equal x null`. Why: `LVar.num()` returns **0** for null (Lvar.java:56-58), while `numOrNan()` is the one that returns NaN.
6. **Treating NaN as a sentinel** —— ✗ testing `equal r nan` after `op div r 1 0` → ✓ an assigned NaN lands in the object slot (`setnum` :87-97: `invalid(value)` ⇒ `objval=null;isobj=true`), that is, it "becomes null" in the integer sense. Why: `invalid = NaN || Inf`.
7. **`set` with an unknown name** —— ✗ expecting `set foo 1` to have no side effect → ✓ it **writes foo as null, overwriting the old value**. Why: assertion table S-16, measured.
8. **Using an unbound link name as a sensor target** —— ✗ → ✓ check `@links` first, or validate with `getlink`; an unbound name as target ⇒ the result is null (S-17).
9. **Reading an empty container** —— ✗ expecting 0 → ✓ test for null. Why: with a payload container you read a count (vault=100); without one the mlog level sees null (internally Float.NaN): `op equal b 0`→1, lessThan/greaterThan→0 (S-14).

### C. Numbers (6 items)

10. **`op select` as a two-way choice** —— ✗ `op select r c a b` → ✓ use a jump branch, or `op add` plus a multiplicative mask. Why: v160.7 silently swaps select for noop (`@RegisterStatement("noop")`); the instruction keeps its index and no result is written (L1-25). [measured: assertion table (docs/断言表.md)]
11. **Reading @velX / @velY** —— ✗ gets null → ✓ `@velocityX` / `@velocityY` (L2-24).
12. **Bare name or @status- in the status slot** —— [v159.3] accepts only the bare name `wet`; [v160.7] treats the bare name and `@status-wet` as equivalent (L1-23/24). Across versions, write the `@status-` form.
13. **Throwing a big number at colour** —— ✗ `draw color 99999999 0 0 0 0` → ✓ pack each channel after keeping it in 0..255. Why: each DisplayCmdStruct field is **10 bit signed**, the `unpackSign` range is **−511..511** (LogicDisplay.java:286-288), and an out-of-range value is read as a negative number.
14. **Using equal to test numeric equality** —— ✗ `op equal r a b` is true for both null and 0 → ✓ when you must tell them apart, use `strictEqual` (one of the 8 ConditionOp entries).
15. **`set` on a built-in constant** —— ✗ `set @ipt 10` / `set @unit u` → ✓ `setrate` / `ubind`. Why: @ipt and @unit are `putConst` (LAssembler.java:27), so SetI silently drops the write.

### D. Timing (5 items)

16. **`wait 0` as a delay** —— ✗ → ✓ it only yields this tick and **costs no budget** (L1-30); to delay 1 tick use `wait 0.0166` (the argument is in seconds). [measured: assertion table (docs/断言表.md)]
17. **Expecting sub-frame precision** —— ✗ `wait 0.5` to wait half a frame → ✓ the argument is in **seconds** (`wait 0.5`=30 tick) and the granularity is 1 tick (L1-29, `curTime += Time.delta/60f`). [measured: assertion table (docs/断言表.md)]
18. **Assuming a @counter write jumps immediately** —— ✗ expecting the rest of the current instruction to run afterwards → ✓ the current instruction always finishes; the jump takes effect at the **next** one (runOnce reads before it increments).
19. **Assuming every instruction costs budget** —— ✗ → ✓ the `yield` branch breaks before `accumulator--`, so `wait`/`stop` cost no points.
20. **Synchronising through processor order** —— ✗ the read/write order of two processors in the same tick is **undetermined** (assertion table L3-05, still open) → ✓ use `sync`, or an explicit flag/memory handshake.

### E. Memory / text (4 items)

21. **Out-of-range memory cell** —— ✗ writing `memory[63]` (a memory-cell has only 64 cells, a memory-bank 512; the class default of 32 is overridden per instance) → ✓ read `@memoryCapacity` first; an out-of-range read returns null (NaN) and an out-of-range write is silently dropped. [src: MemoryBlock.java:64-81]
22. **Stuffing long text into print** —— ✗ expecting the buffer to grow → ✓ it holds 400 characters (LExecutor.java:46) and **drops the excess** once full (:1057/:1100), with no error.
23. **Building an over-long string with format** —— ✗ → ✓ it truncates at 400 (:1155-1156). Note that `Vars.maxTextLength=150` is the **chat** limit and has nothing to do with print.
24. **A program above 1000 lines** —— ✗ → ✓ the parser caps at 1000 (LParser.java:185) and the canvas also `truncate(1000)` (LCanvas.java:148), so the excess lines **vanish silently**.

### F. Interaction / units (6 items)

25. **Filling in only the control parameters you use** —— ✗ putting a side-effecting expression in an unused slot → ✓ p1..p4 are **all evaluated** (LExecutor.java:577/584) and the side effects still happen.
26. **Reading every output after ulocate fails** —— ✗ → ✓ on failure it **writes only outFound** (false); outX/outY/outBuild keep their old values (defs=[4,5,6,7]).
27. **Misplaced ucontrol within arguments** —— ✗ → ✓ `within x y radius 0 result`: slot 5 is the output and slot 4 stays 0.
28. **Where ucontrol getBlock writes its output** —— ✗ assuming the last two slots → ✓ slots **4/5/6** are type/building/floor, in that order.
29. **fetch argument order** —— ✗ following the constructor order → ✓ the text order is `fetch <type> <result> <team> <index> <extra>`.
30. **One ubind holds the unit forever** —— ✗ → ✓ once the unit dies `@unit` becomes null and every ucontrol turns into a no-op; each round, test `equal @unit null` before ubind.

## Measurements and counter-examples

- ✅【E】19 of the 30 items line up with PASS/PASS(E) rows in the verification-record master table (S-14..S-18, L1-23..L1-31, L2-24, and so on).
- Counter-example (a boundary that does not hold): **item 6's "NaN becomes null" holds only on the assignment path**; reading NaN out of an internal value such as `@unit` still gives a NaN object, which does not surface at the mlog level.
- 【U】Item 20's processor order needs a two-processor race experiment (both writing the same variable in the same tick, run for 1000 tick and tallied).

## Common misconceptions

1. "null and 0 are the same" — under `num()` they are; under `jump equal` and `strictEqual` they are not.
2. "instruction count = ipt" — ipt is a points-per-second rate, not instructions per tick.
3. "the traps in the docs are all version bugs" — most are slot order and null semantics, stable across versions.
